DynaFlow: Learning Free-Form Multi-Agent Orchestration, by Ruhao Liu, Qi Li, and Shizun Wang, from the National University of Singapore, with Xinchao Wang as the corresponding author, and code and a project page released publicly.

The problem this paper tackles is the rigidity of multi-agent systems. Almost every deployed multi-agent setup is built on a predefined collaboration structure: fixed agent roles, a fixed communication pattern, a workflow diagram drawn before the task arrives. The paper's argument is that the right structure depends on the task, and a fixed structure pays a real price. A simple query needs one agent. Independent subtasks benefit from parallel execution. Dependent stages need reliable access to upstream results. Applying one pre-designed graph to all three cases adds unnecessary communication, latency, and computation, and on the hard tasks it does not give you the structure you need. The authors call the capability they want Free Orchestration: the ability to decide when collaboration is useful at all, and to construct a task-specific workflow during the solve, not before it. They note the existing work in this direction and its limits. Some systems search for effective workflows using execution feedback but build them from a finite set of operator templates. Others generate query-specific agent systems at inference time but produce the complete coordination structure in a single decision, without ever observing intermediate execution results. DynaFlow's design choice is to make workflow synthesis a native action of the solving agent, sitting in the same action space as ordinary tool calls.

The mechanics are worth laying out, because the implementation is unusually concrete. The main agent has three moves: answer the query directly, call an ordinary tool, or generate a workflow program. The program is written in JavaScript against a minimal execution interface. It provides an agent function for sub-agent calls, parallel for concurrent calls, and pipeline for dependent stages, and intermediate outputs are passed through ordinary code variables. Choosing JavaScript as the workflow language is a deliberate bet: the main agent already writes code fluently, so the orchestration vocabulary does not need to be a new syntax to learn, and the budget-constrained runtime can enforce limits on call count and wall-clock time without a custom interpreter. The sub-agents are frozen, they use the base checkpoint of the same backbone with no orchestration training, and they run inside that runtime, which returns both the outputs and the execution trace. The main agent then sees that feedback, appends it to its history, and decides the next move, which can include synthesizing a follow-up workflow that adapts to what the first one produced. So the orchestration is a loop over decisions, each informed by observed execution, rather than one-shot planning. A useful detail from the paper's own analysis: in the base model, the agent answers roughly 47 percent of questions directly without any workflow, and the trained model keeps a substantial direct-answer share, which is the point of having the decision in the action space, you should not orchestrate what one pass can solve.

The training is a two-stage supervised fine-tune of the main agent only, and the compute budget is stated explicitly, which is more than most orchestration papers give you. Stage one fine-tunes on 2,257 distilled demonstrations, where a stronger teacher model produces reasoning and a first workflow action for each query. Stage two fine-tunes on a curated subset of 712 examples, filtered for defects in the distilled data: unsupported premises, biased verification, and information-flow problems, where an intermediate result is needed downstream but never actually passed. The curation step is doing real work here, because the filtered-out defect classes are exactly the ones that would otherwise teach the main agent to skip verification, to trust a biased check, or to reference a variable that was never produced, and a low-rank fine-tune on noisy distilled data would happily absorb all three. The fine-tune is a low-rank adaptation, rank 16, with two epochs per stage, learning rates of 5 times 10 to the minus 5 in stage one and 1 times 10 to the minus 5 in stage two, totaling about 69 GPU hours, with stage one at about 52 and stage two at about 17, and that number covers fine-tuning only, excluding teacher trajectory generation, evaluation, and the LLM-based judging. The backbone is Qwen 3.5 27B, with thinking enabled, and all the baselines run on the same backbone, which is the comparison that makes the headline number mean something.

The evaluation spans six benchmarks covering mathematical reasoning, scientific question answering, and multi-hop retrieval. In Forced mode, where the agent must use the workflow interface, DynaFlow reaches an overall accuracy of 88.08 percent, beating the strongest evaluated baseline by 10.90 percentage points on the same backbone. The baseline set includes chain of thought, five-sample chain of thought with self-consistency, Self-Refine, and AFlow with its released MATH workflow, all with the same 27B model, and DynaFlow is ahead of the entire set, with the margin over the strongest single configuration exceeding 12 points on the 688-question retrieval subset. In Dynamic mode, where the agent may answer directly, it answers nearly half the questions without any workflow and still lands close to the Forced-mode accuracy, which the authors read as evidence that the when-to-collaborate decision was learned rather than just the how. The workflow analysis is the qualitative finding that I think matters most for practitioners: after training, the generated workflows show more explicit use of verification steps and more refinement of upstream outputs before they are consumed downstream. The paper frames cross-stage information flow, actually passing and checking intermediate results, as the key dimension that separates a useful orchestration from a decorative one, and their stage-two curation was aimed exactly at that defect. The case studies in the paper make the mechanism visible: on a multi-hop retrieval question, the base model tends to fan out sub-agent calls and concatenate their raw outputs, while the trained model builds a pipeline where an early identification result is checked against the source before it is used as the query for the next retrieval stage, which is the difference between a workflow that aggregates and one that reasons across its own intermediate results. That behavioral shift is what the 10.9 point margin is made of, and it is the part of the result that does not depend on the backbone being a particular size.

The skeptical read. The cleanest thing about this paper is that it isolates orchestration from executor capability: every sub-agent is the same frozen base model across DynaFlow and all baselines, so the measured gain is attributable to the orchestration policy and its training data, not to better workers. That is a stronger experimental design than most multi-agent results, where a better backbone and a better workflow change together. What I would re-verify: the 69 GPU hour budget is for the low-rank fine-tune on a 27B model, which is cheap, but the teacher trajectory generation and the LLM-based judging are excluded from that number, and the distilled demonstrations are the load-bearing asset of the whole system. If the teacher is much stronger than the backbone, part of the 10.9 point gain is a distillation gain wearing an orchestration costume, and the paper does not fully decompose those two effects. The six-benchmark spread also deserves a look before you generalize: the margin is largest on the multi-hop retrieval subset, where workflow structure should help most, and the pattern of which benchmarks contribute what to the overall number is the thing to check if you are deciding whether to adopt the approach for your own task mix. The bottom line: DynaFlow is the clearest demonstration yet that free-form workflow synthesis, as a learned action with execution feedback in the loop, beats both fixed topologies and one-shot generated workflows on the same backbone. If you are running multi-agent systems today on a hand-drawn collaboration graph, the result to take away is that the graph is a trainable parameter, and the information-flow defects in the training data, not the architecture, are where the quality lives.
