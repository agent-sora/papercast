"RunningTab," by Jinheon Baek, Soyeong Jeong, and Yumin Choi, from KAIST and DeepAuto.ai. The paper targets a failure mode of agent-based knowledge work that is underdiscussed because it does not show up in the usual benchmarks. An LLM agent is handed a task that must be assembled from a workspace of files, a hiring summary from resumes and interview notes, a budget review from a year of spreadsheets. The agent uses a terminal to search and read the files directly, no index, no retriever. It finds the right annual report, extracts the figure it needs, and then hands in a report that does not contain the figure. The content reached the context window. It is gone. Nothing kept track of what the task asked for, what had been read, and what had been listed but never opened, and all of it slipped away under the weight of new observations.

The authors name this setting direct workspace interaction, a long-horizon version of direct corpus interaction where the goal is not a short answer but a new deliverable assembled from many files. Their diagnosis is that reaching the files is only half the task. The terminal solves the access problem. The unsolved problem is the record: which requirements of the task are still open, which files satisfied them, and which listed files were candidates that never got opened. The context window is a terrible place to keep that record, because it is exactly the buffer that gets overwritten.

The fix is what the paper calls an environment-side tab, a per-task record of what the task still owes, kept by the environment rather than by the model. The division of labor is the point, and it is the reverse of most agent-memory designs. The agent adds its requirements to the tab, its own statement of what the task needs. The environment does the rest. Every time the agent reads a file, the environment records an entry in a read log, the text the agent actually saw plus the path it came from, with provenance. Every file the agent lists but does not open is recorded as a candidate. The tab then presents each open requirement beside its best-matching read-log excerpts and its top unopened candidates. The agent can resolve a requirement against a matching passage it has already seen, or set the requirement aside with a stated reason. And there is a finish check. If the agent tries to stop with requirements still open, the tab hands them back. That final gate is doing more work than it looks like, because it converts a silent omission, the deliverable goes out missing content, into a visible, recoverable event.

The contrast with prior agent-memory work is deliberate. In the standard designs, the model writes the record itself, a plan in context, notes on what it read, a compact state it rewrites each turn, or an orchestrator model that supervises the record in multi-agent systems. In every one of those, a model writes the record and a model marks items complete, and both of those are exactly the operations that fail under context pressure. In RunningTab, the environment writes the read log from what the agent actually read and listed. The agent contributes only its requirements. Items are marked done only against a captured excerpt, or set aside with a reason. And because the tab lives outside the context window, it is never displaced, and it is returned exactly once, when the agent tries to finish.

The experimental setup validates the framework on three benchmarks with three large language models. The three benchmarks are Workspace-Bench, where agents assemble deliverables from office files; TheAgentCompany, where they carry out company tasks; and OfficeQA Pro, where they answer questions from decades of archives. The baselines include plain direct workspace interaction, and several variants where the model is instructed to keep track of the task itself, listing what the task asks for at the start, re-checking the deliverable at the end, or both. The headline result is that RunningTab is the best performer on every benchmark, every metric, and every model tested, and the instruction-based baselines that make the model track the task remain far less effective. That last comparison is the most important one in the paper. It shows the gain comes from the record the environment keeps on the agent's behalf, outside the context window, not from prompting the model to be more careful about tracking.

The analysis of what the tab actually holds is the part I find most interesting. On Workspace-Bench, the tab typically holds a median of four to five requirements per task, six to eighteen read-log entries drawn from five to eleven distinct files, holding twelve thousand to forty thousand characters of excerpted text, and one hundred forty seven to two hundred ninety four files that were listed but never opened. When the agent pulls the review, between sixty nine point nine and eighty eight percent of its open requirements are shown beside a read-log entry whose excerpt contains a line with the words of the requirement. In other words, for most requirements, the tab points the agent at a passage it has already read. And the recovery experiment is sharp. About one in five of the rubric values shown to the agent is absent from its deliverable under plain direct workspace interaction. The authors check whether the tab held those missing values: for GPT-5.4 nano, the tab holds ninety four point eight percent of them. The content was captured by the environment. Then they test usability: given the task and the requirement with its values masked, the same model recovers only eight point four percent of the held values without the tab, forty five point eight percent from the tab's review of that requirement, and seventy eight point one percent from the whole read log. The review recovers more than half of what the full log provides while using a small fraction of the text.

Why the environment side matters is not just a matter of who writes the record, but of what the record is allowed to contain. A model-written plan is a claim about the task. It can be wrong about what the task requires, and it can be wrong because the model never actually read the file it thinks it read. The environment-side read log is different in kind. It is a transcript of what the agent actually saw, captured at the moment of the read, with the path attached. The requirement-to-excerpt matching then runs against observed evidence, not against the model's memory of the evidence. The one-hundred-forty-seven to two-hundred-ninety-four unopened files per task in the tab are the second half of the record, and they matter because a large fraction of workspace tasks fail not on content the agent read but on content the agent listed, almost opened, and then never did. The candidate list is the environment's way of saying, you saw this file exist, and you never looked inside it. That is a category of failure no amount of in-context planning can detect, because the file never entered the context.

The honest limits. The tab only captures file content the agent actually read, so it cannot recover a value the agent computed, like a sum, or a value it saw only in a directory listing. The framework adds environment-side bookkeeping, which means the harness has to instrument file reads and listings, and that instrumentation is a real engineering surface. And the benchmarks are all knowledge-work deliverable tasks, so the transfer to settings where the deliverable is code or to interactive settings with frequent mid-task requirement changes is not yet demonstrated.

My verdict is that this is a small, clean, and genuinely useful result: the record of what a task owes should be kept by the environment, not by the model, and the ninety four point eight percent capture rate is the number that justifies it. If you are building agents that assemble deliverables from a corpus, this is a design pattern worth stealing, and the finish check alone is probably worth the integration cost.
