TokenRouter, an efficient serving system for token-level large language model routing, from Tianyu Fu, Tengxuan Liu, and Ruoxi Wang at Tsinghua University and Carnegie Mellon University. This is a systems paper, and it is aimed at a specific and real failure mode: the last two years of routing research have shown that routing at the token level, where the model serving a request can change on every single decoding step, beats query-level routing on both cost and quality. But nobody could actually serve it fast. Every production serving stack, vLLM, SGLang, assumes a single model. This paper builds the serving layer that makes token-level routing viable, and reports decoding throughput gains anywhere from two to sixty-four times over existing implementations.

To see why this is hard, you have to understand what token-level routing does that query-level routing does not. In query-level routing, a whole request goes to one model and stays there. Production systems love this because it plays perfectly with continuous batching. Token-level routing breaks that. A single request now bounces between a small model and a large model, sometimes many times within one response. The motivation is concrete: a method called R2R can match the quality of a thirty-two-billion model while routing only about five percent of tokens to the thirty-two-billion model and decoding the rest on a one-and-a-half-billion model, whereas query-level routing would have to send roughly forty percent of entire queries to the big model. That is a four-to-eight-fold reduction in expensive compute, and that is the prize this systems paper is trying to make real.

Three things go wrong when you bolt token-level routing onto a single-model serving system. First, step desynchronization. Different models have very different per-step latencies. If you keep all requests in one synchronized batch, every step waits for the slowest model, and the fast models sit idle. Second, batch admission delay. Because the target model switches so often, a request frequently arrives at a model that is already mid-batch, so it waits for the next batch, creating bubbles and fragmenting the batches that continuous batching depends on. Third, implementation complexity. None of these systems expose a way to make a per-step routing decision, so implementing token-level routing means deep surgery on a large codebase, carefully coordinated with continuous batching and prefix caching.

The design principle is request-centric programming, model-centric execution. On the programming side, a developer describes a routing algorithm by tracing how one request flows across the cooperating models. There are three callbacks. route, called after each decoding step, looks at the forward pass output, hidden states, logits, sampled tokens, and returns a destination index, zero meaning stay local, nonzero meaning hand off to a peer model. send, called on a handoff, packages the state the peer needs: the request id, the suffix of tokens the peer has not seen, whether the request is finished, and a position anchor so the peer knows where to resume. receive, called when a peer request arrives, converts it back into the local format. That is the whole interface. It is enough to express five different routing algorithms they evaluate: CITER, R2R, R-Stitch, Co-LLM, and ME. CITER, R2R, and Co-LLM all follow the same shape, a small model detects an uncertain token and bounces it to the big model, which returns control after one token. R-Stitch is symmetric, with the two models passing control back and forth based on token entropy. ME generalizes to more than two models, choosing the next model after every token according to ensemble weights.

On the execution side, the runtime is model-centric. Each model is hosted by its own autonomous subserver with its own scheduler, its own KV cache pool, and its own copy of the routing callbacks. The subservers run independently and talk to each other through peer requests. Externally there is a single server endpoint that looks exactly like a standard single-model server, so this is a drop-in replacement; a client that works against any ordinary serving endpoint works unchanged against TokenRouter, which is what makes the abstraction portable across the five routing algorithms. To fix step desynchronization, they add a third decoupled loop on top of the two a normal server has, the client-server loop and the decoding loop. This inter-model loop lets a routed request leave its local batch, let the remaining local requests keep advancing at the local model's pace, and come back when the peer is done, so the small model is never idle waiting on the large model and vice versa. The handoff mechanism is the clever part. A naive handoff treats a returning request as a brand new call, which means redoing prefix matching and KV cache allocation, expensive. Instead they introduce a pending state, a third status between running and finished. A pending request is skipped by the scheduler but its serving state is preserved, so resumption is just flipping pending back to running and appending tokens, and the request rejoins the batch as if it had never left. That turns a model switch from a cache rebuild into roughly a token append, and it is the single biggest contributor to the speedup, because it removes the very stalls that made token-level routing look impractical.

The second half is the delayed-batching scheduler, which fixes the admission delay. Under eager asynchronous scheduling, a request that arrives while the model is mid-batch has to wait for the whole step to finish. The fix is to buffer incoming requests and only launch a batch once the buffer reaches a threshold B. This trades a little extra waiting for early arrivals against much less waiting on average, because later arrivals get batched together. The threshold is not hand-tuned. They model the routing process as a discrete-time Markov chain, parameterized by the concurrency, the routing probability, and the per-step latency of each model, and derive a closed-form throughput as a function of B, then search for the B that maximizes it. The trade-off they are balancing is sharp: B too small and you have big admission delays, B too large and requests pile up in the queue and starve the small model of work.

Now the results. They run on an eight A100 80-gigabyte server, with the small model on one GPU and the large model on two GPUs with tensor parallelism. They evaluate five routing algorithms across three workloads, low-effort reasoning, high-effort reasoning with much longer outputs, and multi-turn agentic tasks, mostly routing between Qwen3 0.6 billion and Qwen3 32 billion. The headline is a two to sixty-four fold throughput improvement over the stronger baseline across all fifteen algorithm-workload combinations, and a two to sixty-four fold reduction in end-to-end latency. The ablation is honest and worth reading. At concurrency eight, the base implementation sits at about 133 tokens per second. Extended CUDA graphs lift it to 231, a 1.71 fold gain on its own. Asynchronous execution and delayed batching then push it to 297 and then 372 tokens per second, for a 2.76 fold total over the official R2R implementation at the same concurrency. Scaling across model pairs against the official R2R gives 1.99 to 3.21 fold, so the gain is not an artifact of one particular model scale.

One number I would actually take from this: under a strict per-user latency target, as they ramp concurrency from one to sixteen, TokenRouter's throughput grows eight-and-a-half-fold while keeping over half of its single-user speed, whereas the official R2R reaches only five-fold and keeps about a third of its single-user speed. That is the argument that the speedups are not bought by trashing tail latency.

The skeptical read. First, the sixty-four-fold headline is real but misleading as a single number; it is the ceiling of a wide range, and the median across the fifteen combinations is much closer to the two-to-three-fold you would expect from removing desynchronization and admission stalls. I would report the geometric mean, not the max. Second, the whole system is built on SGLang, and the comparison against "standard serving" is a baseline they constructed themselves by putting a dispatcher in front of per-model SGLang servers, so the most relevant competitor is one the authors defined. I would want an independent re-implementation. Third, the DTMC throughput model assumes a fixed routing probability and i.i.d. per-step latencies, which is a decent first-order model but real routing decisions are correlated within a response, so the derived optimal B is more of a good starting point than a proven optimum. And fourth, the agentic workload uses a third party's trajectories, so the multi-turn claim rests on someone else's data distribution.

Bottom line: TokenRouter is the missing serving layer for token-level LLM routing, with a genuinely clean abstraction, a handoff mechanism that reduces a model switch to a token append, and a scheduler whose threshold is derived rather than tuned. The speedups are substantial and directionally trustworthy, though the headline multiple overstates the typical case and the strongest baseline is self-constructed, so I would re-verify the numbers against an independent serving stack before betting production capacity on them.
