EvoOntology: A Self-Evolving Ontology Layer for Data Agents. The first three authors are Meiduo Chong, Shaolei Zhang, and Ju Fan, all from Renmin University of China, with the fourth author, Xiaoyong Du, also at the same institution.

The paper starts from a problem anyone who has run a text-to-SQL agent over a real database will recognize. A data agent that answers natural-language questions over heterogeneous data, meaning databases, CSV files, and documents at once, has no prior knowledge of what that data looks like. It can only reach it through generic tools, a SQL interface, a file reader, a query API. So it has to probe blindly: issue exploratory queries, guess where a concept lives, inspect irrelevant rows, and start over for the next task. The authors call this the agent-data gap. Their proposal is an intermediate layer, an ontology, that sits between the agent and the raw sources and represents domain concepts, how those concepts map onto physical tables, and the business rules that govern them. The key twist is that the layer is not authored by a human and not injected into the prompt. It is built automatically and then continuously revised, and it is exposed to the agent as an MCP server rather than as a blob of context.

The ontology state has three components, kept in a versioned graph. The schema layer defines object types and reference rules, so the agent knows what kinds of entities exist and how they relate. The content layer stores the actual domain knowledge: terms with their meanings, mappings from semantic concepts to exact fields, constraints like how revenue is defined, and evidence entries that record which observed data supported each claim. The tool layer exposes executable interfaces, a browse tool that takes a query and returns ranked terms, and a resolve tool that, given term identifiers, returns the full semantics: the mappings, the relations, the constraints, and the evidence. Encapsulating all of this as an MCP server matters for context budget. Instead of dumping the semantic layer into the prompt, which the paper notes is impractical for large data sources, the agent retrieves only the semantics relevant to the current step.

Construction is handled by a builder agent that issues probe queries over the underlying sources and grounds every ontology entry in what it actually observes. After that, a self-evolution loop takes over. The loop runs four steps per round. Diagnose: the evolution agent reads the data agent's interaction trajectories and clusters failure traces, looking for signatures like a missing term, a missing mapping, or a constraint conflict. Attribute: each diagnosed deficiency gets a level tag, content, tool, or schema, which states a hypothesis about which layer is at fault. Patch: the agent proposes a typed, hypothesis-conditioned edit at that level only, not a free-form rewrite. Gate: the candidate ontology is accepted only if it wins a paired evaluation on a held-out validation set, run conditionally on the backbone that produced the failures. Edits that regress performance are rejected, and the ontology keeps its parent version.

The experiments run on three benchmarks, DDR-Bench, InsightBench, and BIRD, across four backbones: GPT-5.5, GPT-5.6-sol, Claude Sonnet 5, and Claude Opus 4.8. On DDR-Bench, the headline metric is trajectory-wise accuracy. The baseline, a bare agent with no ontology, scores 69.5 on average. The initial ontology, built once by the builder agent, lifts that to 81.8. After the accepted evolution rounds, the evolved ontology reaches 89.5. Individual backbones improve monotonically across rounds: GPT-5.6-sol goes from 64.2 baseline to 93.5 after five accepted rounds, and Claude Opus 4.8 from 78.2 to 92.3 after four. The curves flatten by the last rounds, which the authors read as the failure signatures becoming rarer once the ontology covers the recurring cross-file concepts. On InsightBench and BIRD the same three conditions hold in the same order, with BIRD execution accuracy rising from the low 60s to the high 70s after evolution. The gap between the static semantic layer and EvoOntology is the clearest single result: on Claude Sonnet 5, injecting the layer into the prompt drops trajectory-wise accuracy by 15.0 points, while the tool-exposed ontology lifts it by 8.8. And the ReAct-plus-memory condition, which stores past trajectories as retrievable episodes, improves over the bare baseline by 6.3 points but still sits 13.7 points behind the evolved ontology, because episodic memory replays what was done without exposing typed, composable structure.

There is a cost story worth noting, because ontology layers often buy accuracy by blowing up context. On DDR-Bench, the initial ontology increases input tokens per turn from 3.2 thousand to 4.1 thousand, but it shortens trajectories from 14.6 turns per task to 11.2, cutting total cost from 52.6 thousand to 50.4 thousand tokens per task. The evolved ontology pushes trajectories down to 8.4 turns and total cost to 42.0 thousand, roughly 20 percent below the baseline, while performance climbs. So the layer amortizes schema discovery across the workload instead of repeating it per task. One more data point: the content layer itself grows fastest in the first three evolution rounds, after which accepted additions taper, which is consistent with the performance curves flattening as the ontology covers the recurring cross-file concepts.

The ablations are the part I would trust most. The four steps of the evolution loop are removed one at a time, and the final evolved score on DDR-Bench is compared against the full loop, which averages 89.5. Removing the gate causes the largest drop, 11.2 points, because unfiltered candidate patches admit regressions that later rounds cannot always undo. Removing the attribution step drops 6.3, because without a level tag the loop makes content edits when the failure was really a manifest problem, and vice versa. Removing diagnose drops 4.8, and replacing the typed patch with a free-form rewrite drops only 1.7. So the gate and the attribution are the load-bearing pieces. There is a second ablation over the three editable levels: evolving content only recovers 8.7 over baseline, schema only 3.6, and tool only 13.2, while the full three-level loop recovers all 20.0 points. Interestingly, the tool layer contributes the largest single-level gain, even though most of the accepted rounds were content edits: tool-level edits, mainly how content is exposed through the manifest and the MCP tools, account for 57 percent of the cumulative gain, content for 34 percent, and schema for 9 percent.

Now the skeptical read. The mechanism is sound, and the paired-evaluation gate is the right instinct; most self-improving agent loops die from accepting edits that quietly regress held-out behavior, and this one measures that directly. But there are things to re-verify before adopting it in a real pipeline. First, the evolution loop is driven by a held-out validation set per data source, which means you need a labeled task distribution for the domain you are deploying in, and the quality of the whole layer is bounded by how well that validation set matches production queries. Second, the backbone-conditional gating means the ontology that wins for one model can lose for another, so the layer is not a portable artifact you can share between teams running different backbones; expect to maintain one ontology lineage per backbone, or accept cross-backbone drift. Third, the construction and evolution cost is real: a builder agent plus multiple evolution rounds of diagnose, attribute, patch, and paired evaluation is a nontrivial amount of LLM compute per data source, and the paper's token accounting covers the serving side, not the build side. Fourth, the ontology is only as good as the evidence grounding, and probe queries can miss concepts that no training-workload question ever touches; the paper's own failure signature list shows the loop finds missing terms and missing mappings, but a concept that never fails in the training workload never gets diagnosed.

Bottom line: this is a clean, well-ablated implementation of the idea that the semantic layer for a data agent should be a versioned, tool-exposed artifact that evolves from the agent's own failures, and the paired-evaluation gate is what makes the self-evolution safe. It is worth building if your workload is a recurring set of tasks over a fixed set of sources, and worth re-deriving the validation protocol for before trusting it on new domains.
