The paper is called "The Last Mile to the Real World: Agent-Native Primitives as Reusable Building Blocks for Solving Real-World Tasks." The first three authors are Haibo Jin, Peng Kuang, and Xiaopeng Yuan, working at the University of Illinois Urbana-Champaign, with co-author Lucheng Fu at the Georgia Institute of Technology.

The starting observation is a number you would not be surprised to hear but rarely see stated so bluntly. Take your frontier model, pair it with the harness the vendor built for it, and run a public benchmark of real-world tasks. On Terminal-Bench version 4.0, at maximum reasoning effort, GPT-5.6 Sol running inside Codex resolves 37.3 percent of the tasks. Claude Opus 5 running inside Claude Code resolves 51.8 percent. So even the best model-plus-its-own-harness combinations clear barely half the problems, and the cheaper one clears less than four in ten. The authors argue these failures are not model failures. The model can usually reach the resource it needs. It fails at the step from reaching a resource to actually applying it. A tool call has to ground its arguments, and those arguments often live in the output of some earlier call. Each result has to reach the later steps that consume it. And when something breaks, you have to trace the failure back to the specific piece of work that caused it. They call this whole region the last mile to the real world, and they claim it is exactly the part every harness rebuilds from scratch on its own.

The proposed unit of structure is what they call an agent-native primitive. A primitive is a reusable wrapper around a single resource. The resource might be a tool, a code repository, a navigation environment, a mathematical reference method. What makes the primitive "agent-native" is that it has a resident language model inside it. That resident model applies the resource in context and talks to the other primitives. The key inversion is that the competence to use the resource lives inside the resource, not in the caller. So when you add a new tool to your system, you do not have to retrain or re-prompt your top-level agent to learn how to use it well; the tool ships with the skill of using itself. The top-level system just has to decide which primitives to compose.

On top of that unit sits a framework called HEELO, which is an acronym for Harness Engineering around Evolving Agent-Native Primitives for the Last Mile to Real-World Tasks. HEELO builds each task's harness out of a library of primitives. It has four verbs. First it composes: for a given task it picks the primitives that task needs and wires them into a task-specific graph. Then it verifies: it checks the result against evidence from the task's own environment, not just against the model's self-report. Then it revises: when a failure is detected, HEELO traces it back to the primitives the failure implicates and edits those primitives. And finally it admits: after validation, new or improved primitives get promoted into the shared library. So the library is meant to grow over time, which is what the "evolving" in the name refers to. The paper also points to companion studies that prove bounds: activation cost is bounded by the task's own demand no matter how large the library gets, and that per-task composition beats the best single fixed harness under stated conditions.

There is a design tension the authors are explicit about. A per-task graph is more flexible than a fixed harness, because it can include only the primitives a particular task actually needs, but composing a new graph for every task is more work than running one pre-built pipeline. The bound they cite is what justifies the approach: because the activation cost scales with the task's demand rather than the library's size, you can keep a large library without paying a per-task cost proportional to everything in it. The trade-off is shifted from inference time to the composition and verification steps, which run once per task. That is the engineering bet the framework is making, and it is the part that would matter most to anyone deciding whether to adopt it: the cost model has to hold in practice as the library and the task complexity both grow.

Because each task domain stresses the last mile differently, the authors instantiate eight primitive families, each built as the solution to one kind of real-world task: Dev, Harness, Tool, Code, Agent, Navigation, Math, and one more for general composition. The evaluation then runs across more than twenty benchmarks, and the headline numbers are where I want to slow down, because they are large.

For Dev-Primitives, they run on each comparator's own backbone and raise Terminal-Bench 4.0 resolution from 37.3 percent under Codex to 55.5 percent. For Harness Primitives composed per task on top of the mini-SWE-agent seed harness, they raise Pass-at-one from 73.0 percent to 80.5 percent on 100 SWE-bench Verified tasks, and from 60.0 percent to 72.2 percent on 45 Terminal-Bench 2.0 tasks, which they note is above Codex's 79.0 and 56.7. Tool Primitives raise the ToolBench pass rate from 55.8 to 75.1 percent. Code Primitives raise repository delivery from 0.3180 to 0.5134. Agent Primitives raise mean accuracy over eight math, code, and question-answering benchmarks from 58.8 percent for a single agent to 75.3 percent. Navigation Primitives raise GAIA-Text-103 accuracy from 45.6 to 58.3 percent. And the Math Primitives put an annotated reference method into the top five for 95.0 percent of held-out Putnam problems, against 84.2 percent for the strongest reranker they compare against.

A practical detail worth noting for anyone who wants to reuse this: the verification step is what makes the loop safe. Because HEELO checks each composed result against evidence from the environment before it lets a failure trigger a revision, a bad primitive edit cannot silently propagate; the gate only admits a changed primitive after the environment confirms the task still completes. The paper also reports that the benefit comes specifically from applying each resource inside its primitive rather than at the caller, and that which primitives run is decided by the task, not by a global policy. That second point is what keeps the per-task graph from degenerating into one fixed harness with extra steps.

The deployment story is a platform called heelo.dev, which is a library of these primitives for real-world actions, exposed through an MCP server. On the 46 real-world tasks on that platform, Claude Opus 5.5 with Claude Code and GPT-6.1 Sol with Codex each complete 9 of the 46 on their own. When connected to HEELO through the MCP server, they complete 39 and 35 respectively, with 1.9 times and 2.3 times less time and 1.55 times lower cost per completed task.

Now the skeptical read. The gains are real on the page, but almost every one of them is a before-and-after measured on the authors' own harness with the authors' own primitives, so there is no external reproduction in the paper. The comparison on Terminal-Bench 4.0 is against Codex as a fixed baseline, and the 37.3 to 55.5 jump is a big claim that would want an independent harness to confirm. The formal bounds are in companion studies, not this paper, so the "activation bounded by task demand" result is something you would have to read a second paper to verify. There is also a structural cost that the paper does not fully price in: if every resource carries a resident language model, you are paying for many model inferences per task, and the cost and latency story rests heavily on the MCP-mediated platform they built, which is not something a reader can drop into an existing pipeline unchanged. The 46-task platform number is their own task set, not a public benchmark. What I would trust is the core architectural idea, that pushing the competence to use a resource into the resource itself and letting a top-level system compose primitives per task is a cleaner decomposition than teaching one monolithic harness to do everything. What I would re-verify before adopting anything is the absolute numbers on the public benchmarks and whether the per-resource model overhead stays acceptable once the library grows past a handful of primitives.

The bottom line: HEELO is a coherent framework for decomposing real-world task execution into self-contained, composable primitives, and the reported benchmark improvements are substantial. I would treat the specific percentage gains as promising but unreplicated, and the real contribution as the architectural pattern rather than any single number.
