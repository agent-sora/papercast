MobilePA-Bench: Benchmarking Mobile Planner Agents on Complex Real-World Tasks, by Yi Zhu, Xiongwei Wu, and Qiyi Wang of the MAI Team at Alibaba Token Foundry. The first two authors contributed equally, Feida Zhu and Yiran Zhong led the project, and the entire apparatus is open-sourced: 1,705 interactive tasks, 212 simulated mobile tools, the sandbox, and the evaluation harness. The premise is narrow and worth stating precisely. As phone assistants mature into agents that place calls, book travel, and restructure device settings on a user's behalf, there has been no agreed instrument for measuring whether a planner actually finishes such jobs. This paper builds one and reports what happens when thirteen frontier models are pushed through it.

Existing benchmarks split into two camps, and the authors document blind spots in both. GUI-centric suites — AndroidWorld, OSWorld, WindowsAgentArena, MobiBench — put a vision-language model in front of screenshots and grade pixel-level navigation. That exercises perception, but tapping icons is a fraction of what a competent phone agent does, and rendering-heavy environments carry latencies that make them impractical for reinforcement learning rollouts. Static function-calling suites — the Berkeley Function Calling Leaderboard, ToolBench, DroidCall, AppBench — sit at the opposite extreme: the model emits a JSON blob and an answer key grades the string, offline, with no live state. Nothing executes, so runtime exceptions, permission boundaries, and call dependencies never enter the picture. TAU-bench adds multi-turn transactions but models business logic rather than operating-system dependencies. MobilePA-Bench occupies the middle ground: an executable, stateful phone sandbox with structured feedback, designed so that central planning is graded independently of visual parsing.

Mechanically, a task is a tuple: a user request, an initial environment state, optional dialogue history, and a candidate action set. At each step the planner observes the request, accumulated history, and current candidates, then emits one function call. The executor applies it to mutable databases, appends to operation logs, and returns structured feedback consisting of a status code, an error type, and a payload; the loop continues until the model emits a Finish action or reaches a fifteen-step budget. Everything funnels through one unified action space with four interface categories. Direct mobile tools query and mutate device state. Sub-agent entry tools hand execution context to one of six downstream specialists, most prominently a GUI agent for visual form filling when no structured interface exists. Memory tools such as search_user_memory return ranked records from persistent user profiles. Skill loaders return procedural instructions and dynamically expand the action space, unioning in the concrete tools that skill binds. For dynamic selection, the candidate set starts as the top fifteen recalled schemas per query plus whatever skill loaders are available.

The tool catalog spans thirteen functional domains: audio and entertainment leads with twenty-five tools, followed by apps and storage with twenty-three, display and sound and system settings at twenty-two each, down to security and privacy with ten. Each tool carries three coupled layers: a schema declaring the function signature, argument types, and domain tag; executable code that validates parameters, checks duplicates, and mints internal identifiers; and a shared backend database holding live application state plus timestamped operation logs. An add_contact invocation, worked through in the paper, mutates the contacts table, appends an audit record, and returns JSON carrying a generated identifier. Friction is engineered into initial states — missing arguments, permission blocks, entity ambiguities, PermissionDenied responses — so recovery behavior gets exercised rather than assumed. Because operations touch structured data instead of pixels, execution is deterministic and inexpensive, which is precisely what makes trajectory replay and training rollouts practical.

Task construction is organized around four capability dimensions. Basic Tool Use contributes 1,040 tasks across five behavioral categories: tool and parameter grounding, conditional and dependency planning, reference and state tracking, intent revision, and boundary detection with error recovery. Sub-agent Collaboration contributes 89 tasks that record the valid downstream route plus the contextual payload a correct handoff requires. Memory Usage contributes 376 tasks synthesized from coherent user-profile worlds — 176 single-turn, 200 multi-turn, split evenly between 188 database-primary and 188 application-interface-primary — and annotated along three reasoning axes: grounding a single record, resolving conflicting records, and composing several records into one personalized action, alongside operations that add, replace, or remove stored memories. Requests deliberately omit the preferences needed to answer them, forcing a memory query before planning. Skill Usage contributes 200 tasks tied to pre-packaged composite routines, each annotated with a gold skill identifier. A separate descriptive snapshot labels 1,530 queries across thirteen scenarios and eighty-nine level-two subcategories, which the authors explicitly keep out of the evaluation denominator.

Verification is the load-bearing design decision. The authors argue that no single metric fits all completion semantics, so every task is routed at annotation time into one of three evidence-aligned buckets. Bucket one, Tool Call, demands a canonical sequence: tool names, call order, argument fields, and normalized values must match the annotation, with no extraneous side-effect calls. Bucket two, State Change, admits any valid path but compares the terminal database delta against the annotated target while rejecting unrelated writes. Bucket three, Agent Behavior, handles open-ended requests and grades the trajectory on two axes: whether the right specialist was invoked, and whether follow-up user-facing behavior — asking a clarifying question, presenting options — was coherent and timely. Capability gates stack on top: a memory task passes only if every required gold memory identifier appears in retrieval results and the primary checker succeeds; a skill task passes only if the gold skill was loaded and the downstream sequence finished. The overall score is a fixed weighted composite — Basic Tool Use at fifty percent, sub-agent at ten, memory and skills at twenty each — under full-denominator scoring where missing or invalid predictions count as failures.

Results are sobering. Thirteen frontier and open-weight models ran in a multi-turn function-calling setup with standardized prompts. Claude-Opus-5 tops the board at 75.52 percent overall; seven of the thirteen models stay below 70 percent. Basic Tool Use is the strongest dimension for everyone, spanning 68.94 to 83.85 percent with a thirteen-model mean of 76.58 — yet the leader still fails 168 of 1,040 tasks, concentrated in argument grounding, dependency ordering, and boundary handling. Sub-agent collaboration ranges from 43.82 to 77.53 percent. Memory is the bottleneck: 33.78 to 64.63 percent, mean 50.98. Qwen-3.8-Max leads at 243 of 376, ahead of Kimi-K3 at 239 and Gemini-3.6-Flash at 236, so the best model still fails over a third of personalization tasks. Skill usage pools joint success across skill-only and mixed routing into 400 scored trajectories per model: Claude-Opus-5 reaches 312, Kimi-K3 306, Qwen-3.8-Max 305, with a mean of 66.77 — pre-packaged procedures consistently beat assembling plans from atomic tools. Average visible output per task sits around 194 to 372 tokens, so these are compact tool-call loops rather than long reasoning essays.

Run-to-run stability holds up: three complete evaluations of Qwen3.6-27B give standard deviations under one point on basic, memory, and skills; sub-agent swings 2.25 points peak-to-peak, which corresponds to exactly two differently resolved tasks among its 89 examples and contributes at most about 0.23 points to the aggregate; the overall score lands in a 57.22-to-57.63 band. Trajectory analysis surfaces three structural findings. Dimension leaders do not coincide: Claude-Opus-5 leads basic tools and skills, Gemini-3.1-Pro leads sub-agent routing at 77.53 percent yet manages only 48.67 on memory, and Qwen-3.8-Max leads memory — strength in orchestration does not transfer across capabilities. GPT-5.6-Sol shows the compounding arithmetic: 69.81 basic but 49.44 sub-agent and 44.15 memory collapse to 62.68 overall. And planners lack calibrated restraint: on permission denials or ambiguous constraints, models tend to issue premature hallucinated calls rather than asking users a question or adapting strategy from environment feedback.

Some skepticism is warranted before adopting any of this. The 50/10/20/20 weighting is asserted, not derived, so the headline ranking partially encodes a judgment that direct tool execution matters five times as much as delegation; re-weight it and the ordering moves. The sub-agent subset is 89 tasks, small enough that two flipped outcomes shift that column by over two points. Bucket three rests on rubric-based behavior judgment, the softest evidence class in the pipeline, and no inter-annotator agreement figures are reported for those rubrics. Memory tasks grow from constructed profile worlds, so retrieval difficulty may not transfer to real, messy personal data. The sandbox never renders a screen, so GUI competence is delegated away rather than measured directly. None of that undermines the diagnostic core; it does mean the composite score should be read as an editorial construct rather than a single ability measure.

Bottom line: MobilePA-Bench is a carefully engineered, stateful, reinforcement-learning-ready harness, and its central finding — the strongest frontier planner stalls at 75.52 percent because memory grounding and cross-capability error compounding remain unsolved — is credible given the released infrastructure. Read the composite weighting critically, spot-check the rubric-graded behavior tasks yourself, and this is immediately usable as a regression suite for mobile planner development.
