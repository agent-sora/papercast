"SuperNav, an agentic navigation system for any task in any scene," by Jinkai Zhang, Jingyi Xu, and Yuanhong Yu, from Zhejiang University, with collaborators at Shenzhen University and Causa Robotics. This is a robotics paper with a familiar agentic flavor, and its central bet is that you do not need to fine-tune a vision-language model to make it navigate. You need a harness. The model interprets the request, understands the scene, and makes the decisions; a set of tools and skills turns those decisions into physical motion.

The problem is the twin of task generality and scene generality. A general-purpose service robot has to handle a wide range of human requests in environments it has never seen. Finding a specific object is one task; finding a place to rest is another, because there the robot has to interpret an abstract need and decide which objects in the scene can satisfy it. These differences change not just what the robot is looking for but how it explores, how it tracks progress, and how it knows when it is done. The two existing families of methods each fail at one of the two axes. Modular zero-shot pipelines have task-specific logic baked in: the workflow decides when the model participates, how exploration transitions into confirmation, and when execution ends, so a new kind of request often needs a new workflow. End-to-end methods fine-tune a vision-language model on instruction-and-trajectory pairs, and their generalization is bounded by the coverage of the navigation training data. The authors run cross-environment evaluations and find substantial task-completion gaps for the fine-tuned baselines, which is the motivation for not touching the model weights at all.

The design follows the split you have seen in general-purpose computer-use agents. A pretrained multimodal large language model does the reasoning. A harness organizes execution through an agent loop, exposing agent-oriented tools for observation, motion, turning, goal-progress tracking, and task termination, plus navigation skills, which are just markdown packages of procedural guidance the model can read on demand for search, verification, and recovery. The model picks a tool call from its current context, the tool executes and returns feedback, and that feedback feeds the next decision. The skills do not add any capability and do not enforce any action sequence; they only shape the context.

The piece I would spend the most time understanding is the unified visual-point interface, because it is what connects a language model to motion. An observation returns four RGB images, labeled front, right, back, and left relative to the robot's heading. To move, the model calls point-navigate with a view identifier and a normalized horizontal and vertical coordinate in the range zero to one, picking a point directly in one of those images. It can point at a candidate object or at visible floor. The tool executes the movement internally and returns new four-view images plus execution status and concise diagnostics, so the model gets re-observation for free without a separate observation call. Critically, this interface separates destination selection from the mechanism that executes it, and there are two interchangeable backends behind it. The geometric backend, which they call the Geo-based Executor, uses depth, camera calibration, and pose to map the selected image point to an environment location and then plans and follows a path to a reachable goal. The learned backend is inspired by NoMaD's goal-conditioned generative policy, but instead of a destination-image goal it takes the marked point in a reference observation and predicts local displacement increments plus a stopping signal, turning toward the selected view and executing short motion segments within a single tool call. Both backends speak the same destination-and-feedback protocol, so the decision workflow is identical regardless of which one is underneath.

Context management matters here, because navigation is long-horizon. The harness keeps goal records for pending and completed items and a textual interaction history for inspected areas, candidate clues, and failed attempts. To stop the image context from ballooning, it strips the media payload from an image once it has been processed and superseded by newer observations, but it keeps the textual history, the task state, and the image paths, so the model can re-request an earlier image from the workspace if it needs to. It is media-only pruning: you lose repeated image transmission, you keep the access to prior evidence. Termination is handled by the model itself. It judges from the observations and progress records whether the request is satisfied or execution is blocked, then calls the termination tool. The paper is explicit that a successful closure confirms the session ended, not that the task succeeded. Scoring evaluates success separately from the model's declaration. That separation is a small but important honesty point.

Now the numbers, and they are the reason this is worth your time. They build an instance-navigation benchmark in Habitat-GS using InteriorGS scenes: 150 single-object tasks and 150 ordered multi-object tasks with two to five targets, with arrival requiring a navmesh geodesic distance under one meter to an approved target viewpoint. They also run 200 demand-driven tasks from AI2-THOR via Demand-Bench, where success means entering each of one to eight ordered admissible two-meter bounding-box regions in order. The decision backbone is GPT 5.6 Terra. On single-object navigation, the geometric SuperNav reaches 78.00 percent success with a success-weighted path length of 0.4127. The strongest fine-tuned baselines are nowhere near: NaVid gets 24.67, UniNaVid 34.00, StreamVLN 13.33, and OmniNav's Action Former 27.33. On multi-object, both backends tie at 34.00 percent success, with the geometric backend yielding more efficient paths. On the harder demand-driven set, geometric SuperNav reaches 59.50 percent success with 0.1801 SPL, against 37.50 percent for the best baseline, OmniNav's Action Former. The learned backend is a step behind on every axis: 68.00 on single-object, 34.00 on multi-object, and 45.00 on demand-driven, with notably weaker path efficiency, 0.2059 versus 0.4127 SPL on single-object.

For category-level navigation they use a shared 120-episode HM3D-OVON val-unseen subset and 1,000 HM3Dv2 validation episodes. On the OVON subset at the one-meter threshold, the geometric SuperNav gets 73.33 percent success and 0.4105 SPL without any OVON-specific training or adaptation. At the stricter 0.25-meter threshold it drops to 68.33 percent and 0.3837 SPL. On the 1,000-episode HM3Dv2 set it reaches 86.50 percent at one meter. They compare against a list of published methods, MTU3D, SoftNav, AstraNav-Memory, OmniNav's slow system with chain-of-thought, L3MVN, VLFM, SG-Nav, ApexNav, among others, though they are careful to note the evaluation subsets and protocols differ, so those are directional rather than like-for-like. There is also a real-quadruped deployment, which is what the Causa Robotics affiliation is for, and it is the evidence that the interface is not a simulation artifact.

The ablations are the most informative part for anyone who wants to know what is actually doing the work. On the 120-episode OVON set at the 0.25-meter threshold, removing the navigation skills drops success from 68.33 down to 35.00. Replacing the agent-oriented tools with front-only interaction drops it to 52.50. Removing both skills and tool design lands at 31.67, which is basically the floor. So the harness components are not decorative; the skills alone are worth more than the interface restriction, especially at the stricter threshold. Swapping in an external grounding tool for candidate selection does not beat the model's own direct pointing, which is a useful negative result. And a configuration variant with GPT 6 Astra medium instead of GPT 5.6 Terra high actually improves both success and SPL to 71.67 percent and 0.4579 SPL, which tells you the harness is model-agnostic in a useful sense, a stronger decision model lifts the whole system.

Let me be straight about what I would trust and what I would re-check. What I would trust is the core architectural claim, that a frozen general-purpose model plus a well-designed tool-and-skill harness can beat fine-tuned navigation policies on generalization, and the visual-point interface is a genuinely clean way to decouple destination choice from the motion backend. The ablation showing skills worth more than the interface is a strong, specific result. What I would re-verify before deploying this on a real robot is the demand-driven and multi-object regime, where success rates drop to the 34 to 59 percent range and the paper concedes that long ordered sequences remain challenging. The learned backend's path efficiency is much worse than the geometric one, so if you do not have reliable depth, calibration, and pose on your platform, the numbers you get are the 0.13 to 0.20 SPL range, not the 0.41. The engineering gotchas are the practical ones. This is an agentic loop, so you are paying for a multimodal model call on every single step, with four images per observation, plus the tool round-trips. On a real quadruped the geometric backend needs sensed geometry and localization, which is exactly the part that is hard to get right off the shelf. Plan for the per-step inference cost and the depth-pose pipeline before you assume the simulation success rates transfer.

Here is the bottom line. SuperNav shows that a pretrained multimodal model, given a unified visual-point tool interface, procedural skills, and careful context management, can navigate across task types and unseen scenes without any navigation-specific fine-tuning, and it beats the fine-tuned baselines it was compared against. If you are building a general-purpose service robot and want to keep your vision-language model general while still getting reliable motion, this harness is a credible blueprint, provided you budget for the per-step agentic inference cost and you have a solid depth-and-pose stack behind the geometric executor.
