Recurrent Looped Transformer is from Yifan Zhang, Jichen Feng, and Shihan Qin, at Princeton University and the University of Pennsylvania. This is an architecture paper on the topology of how a transformer computes over a sequence, and it falls squarely in the class of changes worth tracking, which is why it gets an episode even though its upvote count is low. The core observation is a mismatch: state tracking problems require an update at every input, the state has to change once per token, but the depth a standard transformer applies to each token is fixed regardless of how long the sequence is. The total computation per token is constant, so the computation path through the network does not grow with sequence length, and that is exactly the wrong shape for a problem where the amount of state you need to carry does grow.

Their proposal, the Recurrent Looped Transformer, or RLT, splits the model's layers between two parts. One is a parallel causal encoder, which encodes all the observed tokens in parallel the way a normal transformer does, building an encoder memory. The other is a recurrent decoder. At each token, the decoder takes the encoder's output for that token and merges it with the previous token's final decoder state. So the decoder state is carried forward and updated at every position, and the computation path grows with sequence length, but only at a fixed cost per token, because each step reuses the same decoder layers rather than adding new ones. That is the loop: the same set of decoder layers is applied repeatedly, once per token, so depth in the time direction is bought by recurrence instead of by more parameters. The prompt and the response use the same transition rule, so the model does not have separate machinery for encoding the context and generating the continuation.

One design detail is the gating on the merge. The recurrent merge is not a plain sum of the new token's encoder output and the previous decoder state, it is a gated combination, so the model can learn how much of the previous state to carry forward versus how much to let the current token overwrite. That gating is what lets the architecture behave like a normal feed-forward transformer in the limit, where the gate closes and the previous state is dropped, and behave like a true recurrent state machine when the gate stays open, and the split sweep is in effect a study of where that gate is most useful, with the results saying it is most useful when the decoder is a substantial fraction of the depth and the task requires carrying state forward. There is also a training-time detail that matters for the cost story: they use truncated backpropagation through time, a window of 128 tokens, which covers the full training sequences for these short algorithmic tasks, so the recurrence does not add a training-cost penalty in this regime, but on longer sequences the truncated window would mean gradients do not flow across the full sequence, which is a real constraint if you wanted to use this on genuinely long inputs.

The experiments are small and clean, which is appropriate for an architecture paper. They compare five different splits of eight layers, from four encoder plus four decoder up to eight encoder plus zero decoder, against an eight-layer decoder-only transformer, over three random seeds. All models are the same width, 512, with four attention heads and an FFN width of about 1,365, so the comparison is controlled. The tasks are six algorithmic problems: parity, addition, modular arithmetic, and a couple of permutation-tracking tasks including a swap-based task on the symmetric group on five elements. Training is modest, a few thousand steps, batch size 512, AdamW with weight decay 0.1 and gradient clipping, and the learning rate warms up to 10 to the minus 4 then decays.

The results are striking within that small regime. On parity, trained on at most 40 bits, two of the RLT splits generalize to 256 bits with 100 percent accuracy in every seed, while the plain transformer stays at chance, about 50 percent. On the swap-based permutation tracking, tested at eight times the training length, the four-plus-four RLT split reaches 97.3 percent final-state accuracy against 0.85 percent for the transformer. On modular arithmetic beyond the training lengths, RLT reaches up to 93 percent against 33 percent. And there is a depth trend: accuracy increases as you give more layers to the recurrent decoder, which is direct evidence that the recurrent depth is the thing doing the work. The ablation that matters most is the feedback: if you remove the recurrence, the feedback that carries the previous state forward, parity and the permutation task drop to chance at every split, so the gains are not from the encoder-decoder split, they are specifically from the recurrent merge. There is also a scheduling result: if you update the feedback once per four-token chunk instead of once per token, tokens within a chunk can run in parallel, and 64-bit parity stays at 99 percent, but the permutation task drops from 100 to 20 percent, because permutation tracking genuinely needs per-token updates.

A skeptical read. The results are clean and the ablations are well-chosen, the feedback ablation in particular isolates the mechanism rather than just showing the split helps. But this is a small-model, algorithmic-tasks study, width 512, a few thousand steps, and the gap to the plain transformer on these tasks is so large that it is not a good test of whether the architecture helps on the harder, noisier problems where transformers already do reasonably well. I would want to see the RLT on a task where the plain transformer is already above chance, because that is where the claim that the growing computation path matters is actually stressed, and the current tasks are mostly ones where the plain transformer is at or near chance, which makes the comparison look bigger than it is. The second thing I would re-verify is the cost accounting. The paper says fixed cost per token, which is true, but the per-token cost is higher than a single transformer forward pass, because the decoder runs its full depth at every position, and the total compute over a long sequence grows with length, which is the intended tradeoff, but it means this is a compute-for-capability architecture, and you are paying at inference time in a way the standard transformer is not. On these short algorithmic tasks that is invisible, but the whole point of the growing computation path is that you want to use it on long sequences, and that is exactly the regime where the inference cost and the truncated-backprop training cost both become real, so the cost story needs to be re-examined at the sequence lengths where the architecture is actually useful rather than the lengths where it was tested. The third: the five-layer split sweep shows the decoder needs to be a substantial fraction of the depth to get the benefit, which suggests this is not a drop-in replacement for an existing transformer, it is a different design point that you would have to re-choose the split for per task, and the chunking result, that some tasks need per-token updates and others tolerate chunked ones, means the right configuration is task-dependent.

Bottom line: the Recurrent Looped Transformer is a clean, well-ablated demonstration that giving a transformer a computation path that grows with sequence length, by carrying a recurrent state through a shared decoder, fixes state-tracking generalization that a fixed-depth transformer gets at chance. Before you would adopt it, I would want the same result on tasks where the plain transformer is already competent, and a full inference-cost accounting, because right now it is a strong result in a small, controlled regime where the comparison is set up to favor the recurrent design.
