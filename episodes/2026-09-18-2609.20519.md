SoL-Pi: Recursively Scaling Auto-Research Loops for Efficient Agent Harness. The first three authors are Haozhe Liu, Tian Ye, and Sensen Gao, from NVIDIA, Nanyang Technological University, and MIT.

The paper tackles a systems problem that has been quietly getting worse as coding agents move from supervised code completion to unattended, around-the-clock exploration. Once an agent runs long trajectories of reasoning, tool use, and feedback, token efficiency stops being a nice-to-have and becomes a first-order cost concern. Most efficiency work so far has aimed at the model or the infrastructure: faster attention kernels, quantization, cheaper substitute models. The authors take an orthogonal direction. They hold the underlying model fixed and instead optimize the harness, the software layer that mediates every interaction between the model and its environment. The twist is that they do not hand-tune that harness. They let an AI optimizer discover it, using a recursive-self-improvement-inspired search, and they specifically engineer the search so the improvements it finds transfer to tasks it never saw.

That last clause is the whole contribution, and it is worth pausing on, because a recent study the authors cite found that evolved harnesses tend to overfit the tasks used during search and deliver only marginal gains on unseen tasks. So the design is built around three principles. Breadth and depth: a broad pool of hypotheses is generated, then promising candidates are implemented, reviewed, and hardened repeatedly. Independent validation: held-out evidence is only evaluated after a candidate is frozen, and those results never flow back into the search, so a validation failure rejects a candidate instead of being patched into a task-specific solution. And scalable orchestration: each search runs as a disposable, isolated lineage, so one failure does not couple into the others.

The search scale is large by the authors' own accounting. Roughly 150 proposed directions, about 500 executable environments, more than 3,000 runs, and more than 60,000 agent-environment interactions. The search set itself has 535 environments: 495 repository tasks built from GitHub issue and pull request pairs, where the agent sees the pre-fix repository and a hidden regression test that is verified to fail before the accepted patch and pass after it, plus 40 synthetic tasks with executable success verifiers, mostly using a Terminal-Bench-2-style interface. The edge case matters: they reserve EdgeBench entirely for final validation, so the benchmark the headline numbers come from is never visible to the optimizer.

The search yields four mechanisms that pass a two-gate filter. Every capability metric has to stay within a predeclared tolerance, and the candidate has to improve at least one declared efficiency metric. The four retained mechanisms are Action Fusion, Online Context Compact, ObservationPack, and Evidence-Preserving Reducer, and they target different points in the loop. Action Fusion combines a file edit and its follow-up test or build command into a single tool request, collapsing three API calls into two and removing an intermediate model round trip. Online Context Compact uses plan-step completion as the trigger to reconsider compaction: at each completion boundary the harness estimates remaining model requests from observed growth, caps that estimate by what would fill the context window, and only compacts when projected input savings exceed the estimated cost of rewriting the prompt cache. ObservationPack handles large tool outputs: results above 10 kilobytes are archived locally, sent in full for the next two provider requests, and then replaced by a stable handle, the original size, and a short excerpt of the head and tail, with exact pages retrievable on demand. Evidence-Preserving Reducer compresses build and test logs of at least 4 kilobytes using a cheaper auxiliary model, extracts a compact receipt, and runs a deterministic verifier over the receipt's schema, source hash, exit status, and exact quotes, falling back to the original log if verification fails or no size reduction is achieved.

The numbers are where I would focus. On the 51 public EdgeBench tasks, the authors report two operating points. The Efficiency point, the fixed four-mechanism stack, scores an average of 42.0 against 44.8 for the baseline Pi harness, while using 1.10 billion tokens, 49.0 percent fewer than Pi, and cutting token cost by 33.2 percent. It retains about 93.7 percent of Pi's average score. The Performance point, which picks the single mechanism with the highest score for each backend, lifts the average to 47.2, a 5.3 percent gain, while still reducing token traffic by 6.1 percent and improving token efficiency by 9.8 percent. The paper frames the headline as reducing recorded token traffic by 44.7 to 49.0 percent and API cost by about a third, with estimated hourly savings of 8.75 to 13.50 dollars relative to native Codex and Claude Code harnesses.

Generalization is the point the authors most want you to trust, and the cross-benchmark evidence is mixed in a way worth stating plainly. On 63 CPU-only Terminal-Bench 4 tasks, Codex and Pi each solve 18 tasks while SoL-Pi solves 15, so it is actually three tasks behind on raw completion. But its total model cost is 211.12 dollars versus 286.45 dollars for Pi, a 26.3 percent reduction, and its cost per solved task is 14.07 dollars versus 15.91. On the IMO 2026 evaluation, six problems with each solution required to be formally verified, SoL-Pi and Pi both pass three problems; SoL-Pi costs 62.69 dollars versus 75.95, and 20.90 dollars per passed problem versus 25.32. There is also a swarm setting: five groups of four workers with a shared evidence board, where the SoL-Pi swarm reaches 1,127 cycles at 60.11 dollars versus 1,366 cycles at 82.12 dollars for the Pi baseline swarm, a 26.8 percent cost reduction under the same budget.

So what would I trust, and what would I re-verify before adopting any of this? I trust the methodological framing. The hard separation between search feedback and held-out evaluation, the frozen acceptance rule, the fixed capability tolerances isolated from the optimizer's control, the disposable lineages, the fact that EdgeBench is never in the loop, all of that is exactly the discipline the cited overfitting result demands. The mechanism designs themselves are sensible and cheap to reason about, and the fallbacks are honest: the reducer falls back to the original log on any verification failure, ObservationPack keeps the full result for the first two requests.

Where I would push back or re-check is in the headline. The Efficiency point scores below Pi on EdgeBench, so the framing of comparable performance with a big cost cut is doing real work, and the gap is not noise to be waved away. More importantly, on Terminal-Bench 4 SoL-Pi solves fewer tasks than both baselines, so the efficiency gain is purchased with a completion deficit on that benchmark. That is consistent with a harness that aggressively suppresses token traffic, but it means the trade-off is not free, and the paper's own single-component table shows the components trading some prefix reuse for less repeated input. I would want to see the per-mechanism capability deltas on the full 134-task EdgeBench, not just the 51 public ones, before concluding the four-mechanism stack is drop-in safe. The auxiliary model in the reducer, a separate cheaper model, is an additional moving part and an additional failure surface in production. And the 150-direction, 535-environment search is a one-shot result by the authors' own admission, not an established scaling law.

Bottom line: this is a well-disciplined demonstration that an AI-driven search, with held-out validation kept strictly out of the loop, can find harness-level mechanisms that cut token cost by a third while roughly holding capability, and the four retained mechanisms are concrete and reusable. Treat the cross-benchmark completion deficit on Terminal-Bench 4 as a real cost of the efficiency, not a rounding error, and re-verify the capability gap against the full benchmark before you ship any of it.
