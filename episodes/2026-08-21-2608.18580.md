FACET: Preserving Source Intent and Executable State in Terminal Task Synthesis, by Kou Shi, Zun Wang, and Qisheng Su, with ten more authors including Feng Zhao as corresponding author. The affiliations are the MoE Key Lab of BIPC at the University of Science and Technology of China, Shanghai AI Laboratory, and Fudan University.

The problem this paper attacks is concrete: training terminal agents needs scalable, executable supervision, and every synthesized terminal task is a tightly coupled bundle of an instruction, an initialized environment, a reference solution, and an executable verifier, packaged in the Harbor format that Terminal-Bench uses. If those artifacts are generated under inconsistent assumptions you get tasks that cannot be solved or that grade incorrectly. Two failure mechanisms dominate multi-stage synthesis pipelines. First, information loss: source material rich in capabilities, dependencies, intermediate states, input-output contracts, and procedural constraints gets progressively compressed into a simplified task description, preserving only a fraction of the available structure. Second, artifact drift: an instruction references a file never realized in the environment, a solution assumes a different schema or dependency version, or a verifier tests a state the generated task cannot produce. Passing textual specifications between generation stages mitigates neither problem, because text is not a shared realized state.

FACET, short for Fine-grained Agentic Construction of Executable Tasks, works in three stages. Stage one builds the supply side. Skills are scraped from public skill packages on OpenClaw, ClawHub, and GitHub, filtered to remove unsafe instructions, private-website or non-public-resource dependencies, unreadable records, and duplicates, then normalized into structured records of description, tools, inputs, outputs, procedural steps, and provenance. That yields more than 71 thousand valid skills. An extraction agent hypothesizes application contexts per skill; embeddings retrieve similar hypotheses from other skills; the pairs are grouped into scenario-skill candidates, and a model-based judge keeps only those relevant, complementary, non-redundant, and executable as a terminal workflow.

Stage two reconstructs richer scenarios instead of converting skills directly into tasks, which produces shallow workflows using only each skill's most obvious capability while omitting cross-skill dependencies and intermediate states. Five modules run in sequence: skill analysis identifying capabilities and preconditions, scenario exploration proposing concrete settings, association and filtering keeping scenarios that genuinely use the skills, evolution and recovery organizing them into a workflow with explicit state transitions, and information expansion adding concrete resources, formats, constraints, and observable success conditions. The result is described along five dimensions: goal, context, capability roles, initial-intermediate-final states, and inputs-outputs-tools. A model integrates these into one natural-language scenario, then generates a solution reference from it and an instruction reference from both, and a consistency-alignment model checks that both references share initial state and target outcome and that every instruction requirement maps onto some solution step.

Stage three is where the engineering judgment lives. Rather than generating a whole environment in one model response, which is unreliable for file-rich tasks involving datasets, archives, or binary assets, an environment agent plans a manifest of directories, files, services, and dependencies, then materializes it inside a restricted base image, using network access plus shell and Python to fetch public resources, localize them into the build context so evaluation needs no network, and augment fixtures with extra records, metadata fields, distractor entries, and cross-file relations so they are not template-like. The image builds and initializes with at most three repair iterations, each conditioned on the observed failure trace and the original specification so the agent cannot simply delete task requirements to obtain a clean build. Then comes the core idea: executable-state sharing. After the container is realized, its actual state becomes read-only grounding for all downstream generators. Instruction, solution, and verifier are generated sequentially against the same files, schemas, ports, and package versions; if repair renames a path or changes a fixture, every later generator sees the updated reality. The solution executes first so the verifier can be written against observable initial and final states, favoring behavioral and state-based checks over exact command matching so alternative correct solutions pass. Validation enforces four conditions from a clean container: environment builds and initializes, verifier fails on the initial state, reference solution executes, verifier passes on the final state. A router assigns each failure to exactly one artifact by execution trace and repairs only that artifact, up to five iterations, discarding survivors.

The dataset comparison is honest about tradeoffs. FACET contains 6,078 validated tasks averaging 22.77 executable tests each, far above Terminal-Lego at 16.60, Nemotron-Terminal at 6.18, or Tmax at 3.29, with trajectories averaging 11.86 turns against Endless-Terminals' 4.53. But evaluated with DeepSeek-V4-Pro through Terminus-2 on a 100-task sample, its pass@1 is 27.00, lowest in the table, because conjunctive dense checking makes completion genuinely hard; pass@3 rises to 35.00. Across teacher rollouts with parseable results, 89.40 percent of individual checks are satisfied yet only 20.94 percent of rollouts fully succeed, and among unsuccessful rollouts 54 percent miss just one or two checks, meaning most failures contain real progress hidden by binary scoring. Structured-data tasks solve more reliably than narrative-document ones.

Downstream results carry the argument. Using the Terminus-2 agent powered by DeepSeek-V4-Pro, 1.2K complete successful trajectories were selected from rollouts over roughly 6K validated tasks, and three Qwen3.5 models were fine-tuned with LLaMA-Factory, then evaluated on Terminal-Bench 2.1 with the same scaffold and three attempts per task: 4B goes from 17.60 to 24.72, a 40.5 percent relative gain, 9B goes from 27.34 to 35.58, and 27B goes from 40.82 to 47.57. The fine-tuned 27B lands within 1.49 points of Qwen3.5-397B at 49.06 under the identical setting, a model roughly fifteen times larger.

The generation-order ablation is the part I would actually cite. On the same 100 scenario-skill pairs: Forward, their order of environment first, then instruction, solution, solution-aware verifier, delivers 99 tasks to validation with 46 initially valid and recovers to 83 after repair. Reverse, verifier before solution, drops to 91 delivered, 22 valid, 63 final, with cross-artifact contract mismatch causing 56.5 percent of its failures. Joint, all three artifacts in a single call, sits between at 96 delivered, 36 valid, 65 final but shifts errors toward fixture grounding at 38.3 percent and infrastructure failures at 21.7. The paired sign test over the 88 pairs reaching validation under all schemes gives 29 versus 9 favoring Forward over Reverse, p equals 0.0017; Forward versus Joint at 27 versus 18 is not significant. So solution-before-verifier is the defensible claim, not sequential ordering generally.

Two operational details worth flagging for anyone reproducing this pipeline. The acceptance criterion is formalized as a conjunction evaluated from a clean container: buildable environment, verifier failing at the initial state, reference solution executing without failure, and verifier passing at the final state; the non-trivial-initial-state clause is what blocks degenerate tasks whose verifiers pass immediately, and it is enforced before packaging rather than after release. And targeted repair is genuinely artifact-scoped: build failures route to environment repair with a three-iteration budget, solution execution failures to the solution, test collection or assertion defects to the verifier, and instruction-state mismatches to whichever side the trace implicates, so a single broken assertion never triggers regeneration of an otherwise valid bundle.

Skeptical notes. The construction funnel shows first-pass validity of only 38.35 percent among 7,446 candidates entering task validation, with targeted repair recovering 3,222 tasks; that is substantial compute per surviving task, and the paper never prices the pipeline in tokens or wall-clock. Repair budgets differ across compared orders, five rounds for Forward against three for Reverse and Joint, which the authors flag themselves. Trajectories come from a single scaffold, limiting diversity. Cross-dataset P@1 comparisons use independently sampled 100-task sets, so treat that table as descriptive. Bottom line: grounding every artifact in the same executed container state is the right primitive for task synthesis, and generating the solution before the verifier is empirically justified. Re-verify yield economics on your own infrastructure before treating this as a cheap data pump.
