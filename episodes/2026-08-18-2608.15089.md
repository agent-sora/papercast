StateM: Reaching 95.3 percent raw accuracy, or a $15 frontier run, on Terminal-Bench 2.1 via harness scaling. That is arXiv 2608.15089, from Ziheng Qin, Yaxin Lu, and Zhangyang Atlas Wang, joined by Kai Wang, who list their affiliation on the paper's first page as, literally, "Somewhere on the Earth." The work was done in the authors' personal time. The claim deserves attention anyway: without changing a single model weight, their agent runtime lifts GPT-5.5 xhigh from an 83.1 percent reference to 92.1 percent on Terminal-Bench 2.1, and reaches 95.3 percent raw accuracy with GPT-5.6 Sol xhigh across 445 public-submission trials. Let me walk through what the system actually does, what the evidence does and does not cover, and where you should verify before adopting any of it.

The premise is familiar to anyone who has babysat a long agent run: the underlying model clearly knows how to do each step, and the run still fails. The agent drifts off-plan, loses track of mutable task state, skips a required check, repeats an unproductive action, or stops before the deliverable is verifiably complete. Benchmarks score the completed job, not the fraction of steps the model understood. The paper frames the dominant alternative responses — more pretraining, more post-training data, longer reasoning, more agents — as orthogonal to its question: how much apparent model failure is actually failure of the surrounding harness, the layer that maintains state, constrains execution, verifies progress, and recovers from errors? They call systematically improving that layer harness scaling. Prior art splits into two camps with a real tradeoff: state-machine and graph-based runtimes give you explicit workflow state, persistence, and recovery, but organize execution around developer-authored controllers that fragment reasoning and are expensive to modify. General-purpose CLI agents preserve autonomy, but their plans, instruction files, and self-review stay advisory — nothing in the runtime checks whether conditions for moving on were actually met.

StateM is a YAML-configured state-machine runtime with a command-line interface, designed to be operated by the agent itself. Formally, a runbook defines a set of phase-level states, an initial state, a set of terminal states, a set of permitted transitions, and a per-state specification holding the phase-local prompt, hooks, checks, and artifact references. States represent meaningful stages — plan, implement, contract-check, self-review, repair, handoff — not single model calls. Each node has a fixed anatomy: an entry hook that loads durable progress and injects phase instructions, the state body where the model works with full autonomy inside the phase, an exit hook that persists progress and writes receipts, and a before-transfer block of blocking checks; a failed check keeps the run in the node. Edges can carry guards that route by check results, receipts, or previous failures — verification failing sends you to a repair state, passing moves to handoff. Two design hypotheses motivate this: control-signal dilution, where a compact plan drowns in its own growing command-and-output trace, and mutable-state ambiguity, where current obligations must be reconstructed from an append-only history instead of read from authoritative state. Separately from the runbook, each run gets a persistent record — run identifier, current state, transition history, hook and check outcomes, timestamps, evidence pointers — which is what makes recovery after a restart or context compaction a query, not archaeology. A run is active, paused on an unresolved external condition, or complete at a terminal state; a pause explicitly does not count as completion. Crucially, the runbook is a normal workspace artifact: the agent inspects and proposes changes to it, the user reads, edits, and versions it. Agent-added run-local checks are allowed and logged; weakening user-owned invariants is not. And the authors are candid about scope: this is a set of control points, not a correctness oracle — semantic self-review stays fallible, and nothing catches a requirement nobody encoded.

Now the numbers. Terminal-Bench 2.1 has 89 tasks; five trials each makes 445 trials in a full evaluation, scored at trial level. Agents are Codex-based. The GPT-5.6 Sol xhigh submission used StateM-Codex agent version 0.144.1, produced 445 trials with 439 no-error completions and six timeout errors, consumed about 1.178 billion tokens, carries a standard error of 0.87 percentage points, and reports a model cost of $1,062.95. With GPT-5.5 xhigh, StateM scores 92.1 percent against an 83.1 percent model-matched public reference — roughly nine points without touching weights — solving 88 of 89 tasks at least once, which is 98.9 percent five-trial coverage, and numerically clearing the separately reported 91.9 percent from GPT-5.6 Sol Ultra. With GPT-5.6 Sol xhigh and the profile frozen after GPT-5.5 development, the system posts 424 out of 445, or 95.28 percent raw accuracy, versus an 84.9 percent reference — a gain of about 10.4 points — and solves all 89 tasks at least once. The same frozen profile raises the cheaper GPT-5.6 Luna tier from 76.7 to 85.4 percent, numerically above the 84.9 percent Sol xhigh reference.

Transfer follows model distance. Within the GPT family, zero runbook changes transfer the gains. Across providers it fails cleanly: applying the frozen profile to DeepSeek-V4-Flash drops its 82.7 percent baseline to 82.0. But adaptation succeeds. Starting from the same runtime, runbook structure, applicable controls, and golden rules, provider-specific adaptation brings the full 89-task suite under standard timeouts to 392 of 445, or 88.09 percent. On a disclosed common core that excludes only the latency-bound gpt2-codegolf task, that is 392 of 440, or 89.09 percent. Extending the timeout solely for gpt2-codegolf yields 3 of 5 successes, and combining gives a descriptive aggregate of 395 of 445, about 88.8 percent — matching the reported GPT-5.6 Sol max at one decimal. The complete DeepSeek final-score evidence cost roughly $15 in API usage, and the adaptation under $38. On BusinessBench, family-level profiles developed on one split and evaluated frozen on held-out instances move the held-out family macro from 84.67 to 85.22 and instance micro from 84.44 to 85.78 — modest — while the development split jumps 86.07 to 91.71, and one exploratory mechanism-matched subgroup gains about 10 points. Round-one family results are genuinely mixed: budget-approval up about 12 points, machine-operating reaching 100, but refactorbench down 2.78 and woocommerce-stock down 3.70. At the task level, the intervention map is concrete: dna-insert goes from 0 of 5 to 5 of 5 behind service-deployment verification checks; dna-assembly from 1 of 5 to 5 of 5 behind primer and assembly-invariant gates; database write-ahead-log recovery from 2 of 5 to 5 of 5 behind preflight preservation checks. Finally, a hyper-agent loop turns failures into versioned practices — a lesson becomes a prompt change, a check, or an activation rule, screened for generality before promotion — and one profile-development run continued for 22 hours across context compactions, with the observed slowdown traced to unfolded terminal output rather than lost control state.

What would I re-verify? First, the references are model-matched public submissions, not rerun, agent-version-matched controls — the GPT-5.5 reference ran Codex agent version 0.125.0 against StateM's 0.144.1, so part of the nine-point delta could be agent-side drift the paper cannot isolate. Second, the authors themselves state the results evaluate the combined runtime plus an evolved, benchmark-adapted control profile; they do not isolate the state-machine abstraction, and the engineering hours behind the Terminal-Bench runbook are unpriced — the $38 figure covers only adapting an already mature profile to a new provider. Third, BusinessBench uses single stochastic trajectories per arm on unequal families, with two of seven families regressing. Fourth, task coverage is empirical coverage over five trials, not single-run reliability — do not quote it as pass rate. The 88.8 percent aggregate also mixes timeout regimes by construction; disclosed, but descriptive only.

Bottom line: the mechanism here — externalized phase state, checked transitions, and versioned practices that survive compaction — is cheap to implement and plausibly worth several points on long-horizon benchmarks regardless of which model you serve. Treat the headline numbers as a well-documented systems result rather than a controlled ablation, and re-baseline against a current agent version before crediting StateM with the entire delta.
