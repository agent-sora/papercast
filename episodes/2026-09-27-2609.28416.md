Agent-Editing World Model, Rethinking World Modeling for LLM Agents, by Shuang Sun, Guoxin Chen, and Fanzhe Meng, from the Gaoling School of Artificial Intelligence at Renmin University of China. The full list adds Jia Deng, Huatong Song, Jinhao Jiang, Wayne Xin Zhao, Hongteng Xu, and Ji-Rong Wen, with the corresponding author being Wayne Xin Zhao.

The paper starts from a critique of the standard recipe for language world models in agentic settings. Existing systems train a model to predict the next environment observation, which for a tool-using agent means predicting tool responses. The authors' argument is that this is mostly wasted capacity: tool responses are high-entropy and execution-dependent, and when the agent has real execution available, reconstructing the exact stdout of a command or a web page offers limited value. The training cost is real and the payoff is small, because the agent can just run the command and read the actual output instead of trusting a predicted one. What agents actually suffer from is task-state contamination, where unsupported assumptions and outdated plans persist in the conversation history and quietly distort every subsequent decision. The old plan that assumed the file existed, the hypothesis that the search result disproved, all of it sits in context and keeps influencing the model, and a critic that appends a correction does not remove the original, so the wrong state remains in the context the model reasons from.

So the proposal inverts the world model's job. Instead of simulating the environment, the model learns how reasoning and actions shape future task progress. The system, AEWM, has two capabilities. The first is an Action Judge that classifies each step in a trajectory as CRITICAL, EXPLORATORY, or NOISY, which decides which steps are worth intervening on. A CRITICAL step is one the task genuinely depends on, an EXPLORATORY step is one that is gathering information the agent may or may not need, and a NOISY step is one that is redundant, contradicts the current state, or is based on an assumption the evidence has already invalidated. The second is State Revision, which edits the noisy reasoning-and-action continuations directly: it rewrites the contaminated portion of the history, from the same observed state, rather than appending a critique that the base model may ignore. The revision is generated from the same observed history, which means it is grounded in what the agent actually saw rather than in the model's internal belief about what it saw. The integration layer, EditAct, runs real execution and then applies revisions, so it changes the actual state the agent reasons from going forward. That distinction matters: a critic that says your last step was wrong leaves the wrong step in context; a state editor removes it.

Training spans three domains, Search, Terminal, and Software Engineering, using mid-training followed by supervised fine-tuning on trajectories from those environments. The choice of domains is deliberate: it covers a read-heavy agentic task, a write-and-observe shell task, and a code-editing task that spans both, so the state-revision capability has to work across different failure modes rather than a single environment's idiosyncrasies.

The training recipe is concrete. Mid-training on roughly 52.2 billion tokens of cross-domain trajectories, then supervised fine-tuning with 60,000 examples for the Action Judge and 60,000 for State Revision, 120,000 examples total. The base is a 35B parameter, 3B-active mixture-of-experts Qwen backbone, which matters because the whole EditAct system runs an editor model in the loop at inference time, so its cost profile depends on how cheap that model is per call, and a 3B active count keeps that per-call cost in a range that is plausible for an interactive agent rather than a batch job.

The results come in three layers. First, the Action Judge itself: 70.5 percent macro-F1 on the authors' judgment benchmark, which beats the strongest frontier-model baseline by 10.6 points. The comparison set includes Gemini 3-Pro, GLM 5.2, Qwen3.7-Max, GPT 5.5, and DeepSeek-V4-Pro, and the per-domain F1s for AEWM run from about 61 on Search to 78 on Terminal, with Terminal the strongest domain and Search the weakest. The baselines cluster in the 45 to 61 range across the same three domains, so the gap is consistent rather than a single lucky split. Second, the downstream effect of EditAct, shown on the 35B backbone as agent-only versus EditAct on the same six benchmarks: BrowseComp goes from 40.9 to 48.1, a gain of 7.2 points; DeepSearchQA from 69.4 to 78.6, plus 9.2; Terminal-Bench 2.0 from 37.1 to 48.3, plus 11.2, the largest jump; Doc2Repo from 42.8 to 48.9, plus 6.1; NL2Repo from 22.4 to 25.3, plus 2.9; and SWE-Bench Pro from 40.6 to 43.8, plus 3.2. Those per-benchmark deltas measure the editor against the same backbone running without it. The abstract's headline range, 3.2 to 6.7 points, is a different comparison: it is the average improvement over the strongest baseline method, ReAct and the step- and trajectory-level Best@3 variants, and the range spans the three backbone sizes the authors test, Qwen3.5-4B, 9B, and 35B, with the smallest backbone gaining the most. Third, the offline variant: AEWM-RFT, which is plain rejection sampling fine-tuning on verified EditAct trajectories, beats Self-RFT by 2.2 points on BrowseComp, 2.6 on Terminal-Bench, and 2.5 on Doc2Repo, without any online AEWM guidance at inference. That is the cheapest version of the idea, and it is the one a practitioner would most likely adopt, since it converts the editor into a training-time signal rather than an inference-time dependency.

Skeptical assessment. What I would trust: the conceptual reframing. The argument that predicting tool responses is low-value when execution is available, and that the real failure mode is stale state persisting in context, is a correct diagnosis of a real problem in long-horizon agents, and the fix of editing state rather than critiquing it is the stronger intervention. The three-tier evaluation, judge quality, online effect, and offline distillation, is also a good structure: it tells you whether the capability exists, whether it transfers to real tasks, and whether you can buy it once as a training signal. The Terminal-Bench gain of 11.2 points is the most deployment-relevant number in the paper.

What I would re-verify: the judge's own evaluation. The 70.5 percent macro-F1 is measured on the authors' own benchmark, and a classifier that decides which steps get rewritten is a high-stakes component, a false NOISY label on a CRITICAL step could delete a necessary action. The paper should say more about the asymmetric cost of the three error types, and the 3.2 to 6.7 point downstream range, while respectable, is measured against the strongest baseline rather than the base agent, so the total effect of adding the whole system is larger than the headline suggests and the marginal effect is smaller. The 35B editor in the inference loop is also a real latency and cost line item that the paper does not fully price out. One more thing to hold open: the State Revision is generated from the same observed history, but the paper does not report how often the revision is a no-op versus a substantive rewrite, and that ratio is the difference between an editor that is actually changing state and one that is mostly confirming what the agent already believed.

Bottom line: AEWM is a well-argued correction to the world-model-for-agents recipe, replacing environment simulation with state editing, and it demonstrates the effect where it matters, higher task scores across all three domains on the 35B backbone and an average gain of 3.2 to 6.7 points over the strongest baseline across three backbone sizes. The offline AEWM-RFT variant is the practical takeaway: you can distill the editor's benefit into the agent itself and drop the runtime dependency.
