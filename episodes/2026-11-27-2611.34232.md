OS-Omni: Benchmarking Generalist Computer-Using Agents on Long-Horizon Workflows Across Platforms, from Hui Shen, Yunta Hsieh, and Jianing Ma, at the University of Michigan, the University of Pennsylvania, Touchstone AI, and the Massachusetts Institute of Technology. The claim: no existing benchmark tests whether a single agent can carry a realistic user goal across multiple operating systems and persistent application state, so the authors built a live, cross-platform benchmark that scores agents only on the final state of the machine.

Start with the gap. Computer-using agents have been evaluated for a few years now, but almost every benchmark isolates one software surface at a time. Browser benchmarks test web navigation. Mobile benchmarks test phone apps. Desktop benchmarks, and OSWorld in particular, test a single operating system in a virtual machine. Each of those tells you something real, but each leaves open the obvious question: can one agent do the job a real user actually assigns, where the job hops between a desktop, a phone, a spreadsheet, a calendar, and a message thread? A user planning an event might compare supplies in a shopping service, add items to a cart, update a budget spreadsheet on the desktop, create follow-up calendar entries on a phone, export a document, and send a message with the details attached. None of those steps is impressive in isolation. The request only becomes hard because it crosses platform conventions, spans many intermediate decisions, and can only be judged by inspecting the resulting cart, records, calendar entries, exported file, and message.

The authors extend the OSWorld execution-based paradigm along two axes at once: cross-platform evaluation, and long-horizon workflows. These two axes are coupled, and that is the whole point. Changing the platform changes the interaction bottleneck, because a calendar update that is a two-click desktop dialog may require picker wheels, modal sheets, and soft-keyboard input on a phone. Extending the horizon changes the memory and coordination burden, because adding one contact is easy while reconciling a directory with stale duplicates is not. And final-state evaluation changes what counts as success, because a document can look visually complete while its exported file is formatted wrong, and a shopping workflow can appear done while the cart and the budget record disagree. So OS-Omni scores tasks strictly by inspecting the persisted system state, not by similarity to a reference trajectory or intermediate visual progress. The reward is a function of the terminal environment state, R of tau equals g of s-sub-T, where g is the task-specific evaluator.

The environment is released in versioned waves of three hundred tasks each, v1, v2, and so on, with each version adding more mock applications and harder tasks. This paper covers v1, which contains forty-eight tasks per platform and twelve cross-platform workflows that pair a desktop with an Android phone, across Windows, Ubuntu, macOS, iOS, Android, and web. Cross-platform tasks use a single-screen setup: an Ubuntu or Windows desktop displays a companion Android device through scrcpy, so the agent interacts with both through the desktop interface using mouse and keyboard, including transferring artifacts between devices. That is a pragmatic design choice that avoids separate platform endpoints. Reproducibility is handled per platform: Linux reverts a clean VM snapshot, Windows restores golden VM storage, macOS clones from a baseline Tart VM, iOS clones a simulator, and Android resets through ADB-backed preparation. State reset is part of the environment contract because GUI agents routinely modify files, accounts, settings, and caches.

There is also a controlled set of service-backed applications for workflows involving account, cart, budget, calendar, message, and other persistent state, which is what lets them test durable final-state changes rather than one-shot GUI actions. These apps are built specifically for the benchmark, so the evaluators know the ground-truth state of every record and can check it after execution. That is a deliberate trade: controlled apps make final-state evaluation reliable and reproducible, but they also mean the agent is being tested against software the authors designed to be evaluable, not against arbitrary real-world applications with idiosyncratic UIs and hidden state. The task annotation pipeline is described in the appendix, with manual verification reserved for ambiguous final states, which matters because the entire score hinges on whether the evaluator correctly classified the terminal state as success or failure.

One implementation detail worth calling out for anyone trying to reproduce the harness: the observation space and action space are both specified per platform in the environment section, and the agent loop, action parsing, and episode execution are documented in a dedicated appendix. There is also a set-of-marks implementation, the standard technique of overlaying numbered boxes on interactive elements, which they analyze separately to measure how much it actually helps. That ablation is useful because set-of-marks is one of the few things that reliably moves GUI-agent scores, and knowing its marginal contribution on this harder benchmark is exactly the kind of number you want before deciding whether to ship it.

Now the numbers, and they are the interesting part. A human study shows that OS-Omni tasks require an average of 67.54 interaction steps and 200.97 seconds to complete, compared with OSWorld reference tasks at 15.0 steps and 111.94 seconds. So this is not just broader platform coverage; it is genuinely longer, more involved workflows. They evaluate nine models on v1: GPT-6-Astra, Claude Opus 5.5, Gemini 4 Argon, GLM-5.3-753B, Kimi K3, Qwen 3.8 Max, Qwen 3.8 27B, Qwen 3.8 9B, and DeepSeek V4.1 Flash. The strongest, Claude Opus 5.5, reaches 68.5 percent average success, which trails the 77.3 percent human reference by 8.8 points.

But the gap is wildly uneven across platforms, and that is the more useful finding. All three frontier models, GPT-6-Astra, Claude Opus 5.5, and Gemini 4, exceed the human success rate on Linux. Yet the best iOS and macOS results are 41.7 and 54.2 percent, which are 33.5 and 25.6 points below humans respectively. And the smaller Qwen 3.8 27B and 9B models solve almost no tasks. The authors read this as evidence that current agents have not learned platform-robust, long-horizon computer use: they can solve many visually explicit tasks, but fail when success requires sustained state tracking, platform-specific control, and durable final-state changes.

Where I would push back. First, n is small. Forty-eight tasks per platform, twelve cross-platform workflows. Platform-level numbers from forty-eight tasks have wide confidence intervals, so a 33-point iOS gap is directionally convincing but not precise. If I were adopting this, I would want the per-task trajectories before treating any single platform number as a hard fact. Second, the human reference of 77.3 percent is itself a single study with an unspecified participant pool, and the claim that frontier models beat humans on Linux rests on that reference. Third, the whole benchmark runs on controlled service-backed applications and mock apps, not the messy real software a user actually has. That is the right call for reproducibility, but it means the benchmark measures robustness to their particular app suite, which is a different claim than robustness to the open desktop. And the agent interface, a unified desktop-plus-phone surface, is one specific harness; a different action interface could shift the absolute numbers even if the relative ordering holds.

What I would trust: the central structural finding, that platform and horizon compound, and that final-state scoring exposes failures visual progress hides. The step-count comparison to OSWorld is a clean, defensible demonstration that this is a harder horizon. What I would re-verify: every platform-specific percentage, the human reference methodology, and whether the nine models were all run under identical harness configuration, which the appendix reports but I would want to spot-check before citing.

The bottom line: OS-Omni is a solid, well-engineered step toward cross-platform, long-horizon agent evaluation, and its final-state scoring protocol is the part worth copying. Its numbers are too coarse to rank platforms precisely, but they point in a consistent direction: today's agents still break down when a goal has to survive across machines and leave the system in a verifiably correct state.
