Lost in Recovery, Demystifying Recovery Behavior of Computer-Use Agents via Goal-Oriented Action Replay, from KAIST, with Youngwan Lee at ETRI and Sung Ju Hwang's group, and the third affiliation is DeepAuto.ai. The first three authors are Byeonghun Bang, Sangwoo Park, and Jinheon Baek, the first two as equal contributors. This is a diagnostic paper, the kind that does not build a bigger model but instead isolates one capability, tests whether agents have it, and finds they do not use it. The capability is recovery: restoring the environment to a previously intact state after an agent has made a mistake, and then resuming the task from that restored state.

The motivation is the fragility of computer-use agents on long-horizon tasks. These agents drive a desktop through fine-grained keyboard and mouse operations, and on long tasks early mistakes accumulate and propagate. Worse, an executed action can leave side effects that should not have happened. The paper's example is an agent organizing a directory that completes the task but silently overwrites files the user wanted to keep. So the ability to revert the environment to a clean prior state is not a nice-to-have, it is a reliability requirement. The prior art falls into two families, and the paper walks through why neither is sufficient. The first is inducing self-reflective behavior: textual feedback or reward-signal updates that refine the agent's forward actions. That helps the agent do better next time, but it does nothing about the state the agent has already corrupted. The second is explicit test-time rollback: a full environment reset followed by re-executing all prior actions, or API-based undo operations like a browser back button. Environment resets are often infeasible on production operating systems and websites, action replay inherits that requirement and gets costly over long horizons, and API rollback is largely confined to web environments. What is missing is autonomous model-level recovery, the agent itself restoring a prior state without any of those ad hoc mechanisms, and nobody had systematically studied whether current agents even have that capability. There are three strategies the literature has tried. Reflection continues forward from the erroneous state, which risks compounding the side effects. Rollback is a full environment reset followed by re-executing all prior actions, which is often infeasible on production operating systems and websites and becomes expensive over long horizons. Recovery is what this paper studies: restore a prior intact state and resume, without a full reset.

The formal definition is the technical core. They formalize Transition-Consistent Recovery, borrowed from predictive state representation theory. A recovered state matches its target if, from both states, executing identical downstream actions yields identical outcomes. That is behavioral equivalence, not visual similarity, and it is what makes the evaluation meaningful. A screenshot that looks the same can still have hidden state that diverges, and this criterion catches that. The operational tool is goal-oriented action replay. They take on-policy trajectories, replay each one multiple times, and keep only the trajectories whose outcome is consistently successful across replays, filtering out environment stochasticity. From those deterministic trajectories they sample intermediate states as recovery targets, perturb them into erroneous states, and ask whether the original task outcome can be reproduced by replaying the remaining actions from the recovered state. That is a clean, reproducible way to measure recovery that prior heuristic approaches, like browser back buttons, never subjected to systematic study.

The framework is called ReTRACE, and they run it on two real desktop environments, OSWorld for Linux and WindowsAgentArena for Windows, across both closed and open-source computer-use agents. The construction pipeline has a filtering stage that deserves attention, because it is what makes the whole measurement trustworthy. They replay each on-policy trajectory and retain only the ones that achieve a successful oracle evaluation in three consecutive replays, a process they call Transition-Consistent Filtering, which empirically guarantees deterministic transition dynamics in the evaluation set. That filtering retains sixty-four point four percent of the recovery trajectories, so it is selective without being prohibitive. For the OSWorld short-horizon evaluation with GPT-5.4-CUA, they randomly sample six hundred samples for perturbation after filtering to keep the API cost manageable. The resulting results answer their three research questions. First, is recovery necessary to unlock latent capability? Yes. Ideal recovery, where the agent is returned to an oracle prior state, boosts performance over naive environment resets, which establishes recovery as the lever for reaching capabilities the model already has but cannot reach from a corrupted state. Second, do current agents actually recover on their own? Almost never. Under implicit recovery, where nothing prompts the agent to fix its mistake, the average recovery rate is below one percent. The agents lack both the capability and the behavioral tendency to restore state under failure. Their own rationales show little similarity to recovery prompts, meaning they rarely even attempt it. Third, is the capability absent or latent? Latent. When you give the agent explicit model-based recovery, recovery success climbs by an average margin of seventeen point eight six percent across the Linux and Windows environments, an order of magnitude over the implicit baseline. The underlying capability is there, it is just not elicited during normal forward task execution.

The end-to-end result is more modest and more honest. Equipping the agents with explicit recovery and recovery target contextualization gives an average gain of about two point one two percent in end-to-end task success on Qwen3.5-9B, and it improves over the no-recovery baseline under every recovery setting, even though the recovery success rates themselves are suboptimal. That is a small number, and it is the right number: the recovery rates in this setup are still imperfect, so the end-to-end gain is a lower bound on what reliable recovery would buy. So even imperfect recovery starts to unlock latent capability, and the paper's argument is that more reliable recovery mechanisms hold substantial promise. There is also a negative result worth noting: in some configurations, adding the recovery machinery with a weak recovery target can actively derail the trajectory, so recovery quality matters, not just recovery presence. The paper validates its own evaluator as well. They measure ReTRACE's win rate against human judgments on a sample of recovery outcomes, and the full pipeline matches human annotators eighty-two percent of the time, against sixty-three percent for the variant without the recovery-target contextualization and fifty-four percent for a GPT-5.4 evaluator running alone. That is a meaningful margin over the model-judge baseline, which matters because the entire diagnostic rests on the evaluator being able to tell a true recovery from a state that merely looks recovered.

If you want to test this yourself, the implementation path is short. Take a computer-use agent, collect its successful on-policy trajectories, filter for transition-consistent ones by triple replay, perturb intermediate states, and measure whether replaying the tail reproduces the outcome. You do not need a new model, you need a harness that can inject errors and replay. The ReTRACE code and dataset are public. The thing to check in your own stack is the gap between latent and elicited recovery: run your agent with and without an explicit recovery prompt after an injected failure and measure the recovery rate. If the gap is large, you have a cheap, model-agnostic win available, because you are not retraining anything, you are just asking the model to do the thing it can do but is not doing. The second thing to check is the evaluator, because the whole measurement rests on it: validate your success detector against human labels on a sample before you trust any recovery number it produces.

The verdict. This is a clean, well-scoped diagnostic that isolates a real capability gap in computer-use agents: recovery is necessary, it is latent, and it is essentially never elicited autonomously, sitting below one percent. The end-to-end gains are small, on the order of two points, because current recovery is unreliable, which is exactly the paper's point and exactly the opportunity it opens.
