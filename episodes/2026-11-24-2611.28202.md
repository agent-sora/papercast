Title: AutoPILOT: A Visual Agent Harness for Real-Time Gameplay

Arxiv: 2611.28202

AutoPILOT, by Mark Zhao, Pengcheng Wang, and Rui Yang, at the University of Illinois Urbana-Champaign, the Georgia Institute of Technology, and Northwestern University, is a harness for vision-language agents that attacks a specific and boring-sounding failure: the game does not wait for the model to think. The paper's central observation is that the standard agent loop, one model call producing at most one action, is the bottleneck in any environment that keeps running during inference. When the clock runs, VISTA's success on GameWorld falls from 84.1 percent with the game paused to 42.9 percent. AutoPILOT restructures the action side of the loop so a single model call can produce a whole policy, and it reports 68.6 percent real-time success on its new AFK-Bench against 38.3 percent for VISTA, at about 0.2 times the API cost.

The paper frames the harness as deciding three things: what the model sees, what it remembers, and how its outputs become actions over time. Prior work, including VISTA and Cradle and the ARC-AGI-3 line, has refined the first two. The third is usually implicit, inherited from the ReAct loop. The authors show with the same model and the same visual tools that this implicit choice is doing the damage: VISTA, with all its visual memory and inspection tools, scores 38.3 percent in real time while the plain Codex harness scores 38.9. More reasoning effort helps VISTA by four to seven points at most. The gap is not perception or memory. It is that the agent can act only as often as the model thinks, and it always acts on a frame that went stale while the tokens were being generated.

The method has three execution modes, and the model chooses among them in each call. First, a primitive action goes straight to the game, exactly as before. Second, an open-loop macro: the model writes a fixed sequence of actions, and a worker thread executes it at fixed intervals without reading the screen. The paper's example is a nine-key press sequence in a turn-based puzzle, each key held for 0.15 seconds, started about every 0.36 seconds. Third, and the real contribution, a closed-loop controller: the model writes a short Python program at run time. The program reads raw screenshots through an observe API, computes something, and calls the act API roughly every 0.4 seconds, with no model calls in between. Control returns to the model on a wake event: the program finishes, explicitly requests a handoff, or the screen changes past what the program was written for. Both the model and its controllers see only pixels, never game state, which matters for how far these results transfer.

The verbatim controller in the paper is a nice artifact. In a hostile real-time shooter, it identifies the player's ship by a blue color mask in a strip near the bottom of the frame, takes the median x coordinate of those pixels, masks bright magenta pixels elsewhere to find projectiles, and if a projectile is close, dodges in the opposite direction while firing. It runs for 240 iterations, then hands off with a message asking the model to inspect the score and remaining lives. The model writes this code from its own screenshots, without being given the game's source. That is the interesting part, and also the fragile part, because a color mask written for one game's palette is a brittle contract.

AFK-Bench is the evaluation contribution. It is 120 browser games, evenly split into three classes defined by what happens while the agent is idle. Hostile environments punish inaction; benign ones keep changing but do not; turn-based ones advance only when the agent acts. Every game can be run in real time or with the clock paused, and the difference between the two modes is the headline measurement: the price of a world that does not wait. With GPT-6.1 Sol at identical budgets, AutoPILOT gets 68.6 percent overall in real time against 38.3 for VISTA, and 62.5 against 16.7 in hostile environments. With the clock paused, AutoPILOT still leads, 73.1 to 56.1, because one model call can execute an entire plan rather than one step. Running the clock costs AutoPILOT about 4.5 points overall and 2.9 on GameWorld, versus 17.8 and 41.2 for VISTA. The results hold across six models, including Claude Opus 5.5, where the margin is 16.7 points at low reasoning effort.

The ablations are where I would read carefully, because they say what the gain actually is. Removing both macros and controllers drops AutoPILOT to 45.8 percent overall and 22.5 percent in hostile real time; those two tools account for 28 of the 38 extra wins over VISTA overall. Keeping only the prompt engineering, restart notices, and budget lines that AutoPILOT adds around VISTA's tools gives 45.8, which still beats VISTA on the same seeds, but the tools are the story. Macros alone matter mostly in turn-based games, where they are used most; controllers alone matter mostly in hostile ones. There is one number I would flag before trusting the headline: without macros, overall success drops only slightly, 67.5 to 68.6, because controllers largely stand in for macros. The two modes are more redundant than the framing suggests, and the combined setup's advantage over either alone is modest.

On cost: AutoPILOT uses 2.8 million tokens per episode versus 5.3 million for VISTA, and it reaches VISTA's final success rate at 0.2 times VISTA's API cost, which the paper reports as 0.89 dollars per episode versus 1.50. The budget-scaling table is the honest one. Giving VISTA three times the model-call budget lifts it from 37.5 to 55.0 percent, and with everything relaxed, 51.7. AutoPILOT at standard budget is 69.2, and at all-relaxed, 78.3. So part of the gap is genuinely efficiency, not just capability, and if you can afford to triple VISTA's budget the comparison narrows, though it does not close. The restart analysis explains why: an attempt costs AutoPILOT two model calls where VISTA spends eight, so after a failure AutoPILOT still has budget to retry while VISTA is out of calls, winning 58 percent of the paired episodes in that situation against 6 percent for VISTA. The workload distribution also supports the story: across all games, the model's calls split 43 percent to single actions, 25 percent to macros, and 27 percent to controllers, with hostile environments leaning on actions and turn-based ones on macros.

The skeptical read. These are browser games, and the closed-loop controllers are hand-tuned-by-a-model Python programs that inspect pixel colors, which is the least transferable kind of policy. A controller written for one shooter's palette is a hack, not a representation. The benchmark deliberately avoids game state, which is a strength for generalization claims and a weakness for anything that looks like real software use, where DOM or accessibility state exists. The three seeds on the main GPT-6.1 Sol runs give a seed standard deviation of 0.8 to 1.0 for VISTA and 2.4 for AutoPILOT, and the bootstrap intervals are reported, which is good hygiene, but most configurations are single-seed. The paper also does not report what happens when a controller silently fails to hand off in a way the wake logic does not catch, and the wake-event design is doing a lot of load-bearing work that one case study does not fully validate.

Two-sentence verdict: this is the strongest argument yet that in real-time settings the harness, not the model, is the binding constraint, and the macro-plus-controller design is a concrete, cheap, implementable fix. If you are building agents that act in environments that do not pause, this paper's action-over-time decomposition is worth stealing even if the pixel-color controllers are not.
