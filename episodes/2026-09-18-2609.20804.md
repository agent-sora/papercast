An Empirical Study of Harness Design for Coding Agents. The first three authors are Run-Ze Fan, Zihao Zhang, and Simin Ma, from UMass Amherst, Emory University, and UNC Charlotte. Two of them did the work during internships at Zoom Video Communications.

The problem is that most coding-agent research evaluates harnesses as monoliths. You pick a whole system, run a benchmark, and get a number, but when one harness beats another you have no idea whether the gain came from the planning scaffold, the tool interface, or the context-management policy. Cross-harness studies make it worse: one the authors cite reports Claude-Opus-4.5 doing best in OpenHands while Claude-Sonnet-4.5 does best in SWE-Agent, which tells you harness preferences vary by model but not which component is responsible. The authors' question is whether individual harness components are generally useful or whether each one's effectiveness depends on model capability, task type, and the context budget.

Their answer comes from building a deliberately lightweight harness from scratch. The execution loop is fixed as a ReAct loop: each turn assembles the model input, runs the emitted tool calls in a container, and appends the observation to history. Three components are varied independently. Planning is a persistent, model-maintained task plan injected each turn and updated through a dedicated tool. The action space is either a predefined set of typed workspace tools, read file, write file, edit file, list files, glob, grep, web fetch, and bash, or a bash-only interface. Context management is the richest axis, with five strategies. T0 does nothing and just terminates when the window overflows. T1 elides stale tool observations. T2 adds external storage with a recall event, making elided content recoverable. T3 uses LLM summarization without elision. T4 stages them: rule-based elision first, then summarization only if the context keeps growing. Everything else, permission handling, post-edit diagnostics, stuck detection, is held constant so the measured effect is the component's.

The experimental matrix is 176 matched settings. Four models: three sizes of Nemotron-3 at 30 billion, 120 billion, and 550 billion parameters as a within-family capability axis, plus Mistral-Medium-3.5 at 128 billion as a cross-family comparison. Two benchmarks: SWE-Bench Verified for repository-level issue resolution and Terminal-Bench 2.1 for end-to-end terminal tasks. The context-management strategies are swept across four window budgets of 32, 64, 96, and 128 thousand tokens, and the planning and action-space ablations run at 128k with T4 context management.

The four findings, in order. First, context management matters most when the window budget is tight, and most of its benefit is simply preventing context-overflow failures. With T0, a meaningful fraction of tasks are lost to overflow at 32k; every managed tier overflows on exactly zero tasks at every budget, so the accuracy gap between managed and unmanaged shrinks as the window grows. Second, the staged T4 policy, elision before summarization, gives the strongest efficiency of the managed strategies while matching their accuracy. The lossless recall mechanism that T2 adds is almost never invoked: even the heaviest user, Nemotron-3 30B on Terminal-Bench at 32k, averages 4.3 recall calls per task and scores 3.4 percent below plain elision. So making elision recoverable adds machinery that models rarely use, with no accuracy gain. Third, planning's role flips with model strength. For the weakest model, Nemotron-3 30B, planning raises success rate by 11.6 percentage points on SWE-Bench and 4.5 on Terminal-Bench, at higher cost. For the 550B model and Mistral, planning barely moves accuracy, down 2.0 and 0.4 points respectively on SWE-Bench, but cuts cost by about 30 and 32 percent, because it removes redundant post-edit verification. Fourth, the action space interacts with bash proficiency: predefined tools help bash-weak models, while bash-capable models do well with a bash-only interface at substantially lower cost, especially on command-line-centric tasks, because they can batch multiple file and shell operations into a single call and skip the per-tool round trips that the predefined interface imposes.

A few implementation details are worth knowing if you plan to reproduce any of this. The T4 staging is threshold-driven: above a soft threshold, bulky middle-region tool outputs are replaced by short stubs and offloaded to an external store that can be recovered by a recall event; above a harder threshold, the oldest middle events are summarized, while the system prompt, the task description, and the recent turns always remain verbatim. That middle-region targeting is what makes the strategy cheap: the model never has to re-read the preamble or lose the working set it is actively using. The predefined-tool interface enforces read-before-write checks, tracks file state in the harness, and triggers automatic post-edit diagnostics, while the bash-only condition strips all of that out. The authors are careful to note that the comparison should therefore be read as the effect of the complete action interface, including state tracking and validation support, rather than the isolated effect of tool count. The environment runs in Docker or E2B containers, and the whole harness is deliberately small enough that the 176-setting sweep was tractable, which is a design goal in itself: the point is that component-level analysis requires a harness whose parts can actually be varied.

The trajectory-level analysis is what makes this more than a table of averages. Context management extends trajectories without substantially changing behavior: the agent runs longer because it stops dying to overflow, but does not do different things. Planning changes where trajectories stop: stronger models stop verifying so much. The action space changes the granularity at which code is written: bash-capable models batch multiple operations per call, which is where their cost advantage comes from.

What would I trust? The design is exactly right for the question: fixed loop, independent components, a within-family capability axis plus one cross-family probe, and an explicit window sweep. The claim that recall_event is nearly unused is the kind of result that is hard to get from any other methodology, and it has a direct engineering implication: if you are building a harness, ship elision and staged summarization, and do not spend time on lossless recall unless a model in your stack actually uses it. The planning result is also useful: it argues against a blanket planning scaffold, because for strong models it is a cost item, not an accuracy item. And the very fact that they report a result in which a component does not help, the lossless recall, is a signal that the study is not curated toward a positive headline, which is rarer than it should be in this literature. The 176-setting matrix also means each number is the product of a deliberate combinatorial design rather than a handful of cherry-picked configurations, so the trends across the window sweep are more defensible than they would be from a single-budget comparison.

Where I would push back. The findings are conditional on four models, two of them from one family, and the authors are explicit that the models are probes, not optimization targets. The harness is their own lightweight implementation, so the magnitudes will not transfer verbatim to OpenHands or SWE-Agent even if the directions do. The planning ablation is only run at 128k, so the planning-by-budget interaction is not characterized. And the web tools are excluded from the predefined set to avoid leaking SWE-Bench answers, a reasonable control for that benchmark but one that means the tool-set comparison is not measuring the full interface you would deploy.

Bottom line: this is a clean component-level decomposition of coding harnesses that turns the usual monolithic benchmarking into something actionable, and its central results, that context management mostly prevents overflow, that lossless recall is dead weight, and that planning is a cost saver for strong models but an accuracy scaffold for weak ones, are the kind of findings you can act on directly in a design review. The caveats are the usual ones for a single-harness, four-model study, but the directions are the part that survives the caveats.
