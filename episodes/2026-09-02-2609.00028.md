UI-Venus-2 Technical Report, by the Venus Team with Zhuohan Cai and Haoxing Chen, from Ant Group. This one lands under the standing rule for a reason: it is a technical report introducing a new general-purpose foundation GUI agent, and it is open-sourced, which is the part that matters most if you want to reproduce or build on it.

The framing is practical, not speculative. GUI agents have moved fast on grounding and navigation benchmarks, but the authors argue that benchmark-oriented models do not transfer to dependable real-world use for three specific reasons. Environment coverage is too narrow to span multilingual mobile ecosystems, dynamic websites, and full desktop operating systems. Task construction is brittle, because generated queries often are not grounded in what an application can actually do. And the verification that supplies RL reward is unreliable, because a coarse verifier confuses partial progress with true completion, misses task-critical visual evidence, or exposes a reward a policy can exploit. The paper's design principle is that these three dimensions must be scaled jointly, not treated as independent knobs.

The system is a unified closed-loop reasoning-and-action agent. Given a natural-language instruction, it observes rendered interface images, reasons about the task state, executes an action, and folds the resulting environmental feedback into the next decision. Two model sizes ship, a 9B and a 27B, both initialized from open-source Qwen3.5-9B and Qwen3.6-27B multimodal foundations. The action space is extended with desktop-specific actions so the same policy can operate on a phone, a browser, and an OS.

Training is three stages. Stage one is large-scale multimodal mid-training on a heterogeneous mixture of synthetic and interaction data, with mobile, web, and operating-system navigation as the dominant component. Task queries come from a deep-research pipeline that grounds them in actual application functionality, and the collected trajectories pass through a human-and-discriminator collaborative verification process that filters invalid, ambiguous, or low-quality interactions. Stage two is offline reinforcement learning with task-specific supervision. For mobile, OS, and web, they build step-level RL trajectories so the model optimizes state-aware action selection and transition consistency. For CAPTCHA and grounding, they use a programmatic synthesis framework that embeds verified puzzles and grounding targets into realistic interface backgrounds, which gives dense, machine-verifiable RL supervision that natural collection cannot. Stage three is multi-teacher on-policy distillation, which consolidates the domain-specialized models into one unified policy.

The distillation stage has a detail worth noting, because it is where GUI-specific structure enters. Vanilla on-policy distillation applies uniform token-level supervision across the whole response, treating reasoning and actions alike, but the executable action is the only part that actually changes the environment, and it is a small portion of the response. UI-Venus-2 therefore conditions the distillation signal on the correctness of the student action. If the complete action is correct, its signal is suppressed. If the type is right but the parameters are wrong, supervision is concentrated on the action span. If the type itself is wrong, the type tokens are emphasized and the downstream parameters are masked, because a Scroll's parameters mean nothing if it should have been a Click. A teacher-side hint giving the correct action type is appended to the teacher prompt but never to the student prompt, so it shapes scoring without changing inference. This is a genuinely GUI-aware twist on distillation, and the kind of implementation detail that usually gets buried in an appendix.

Verification is two-level, which is the reward-reliability story from the introduction made concrete. Trace-level verification judges the overall semantic alignment between the whole execution trace and the task objective, giving a stratified quality score for curation. Sample-level verification works on task-relevant visual keypoints rather than a single holistic judgment of the final screen, and it aggregates judgments from multiple heterogeneous models through voting. Multi-model voting is explicitly motivated as reducing single-judge bias and making the reward less susceptible to reward hacking, which is the right failure mode to be worried about once the policy can see the verifier's logic.

The environment scale is the headline. They expand the mobile pool to over 100 Chinese and 70 English applications, build a web pool of over 4,000 domains across 19 categories using the Tranco ranking plus automated accessibility checks, and construct desktop operating-system capability from scratch, serialized as task specs with controlled snapshots, setup operations, and outcome evaluators. For CAPTCHAs they implement type-specific rule engines covering 70 puzzle types, each with a deterministic latent state that defines the answer, the target geometry, and the solution trace, which is what makes them usable as machine-verifiable RL supervision.

Task construction is where the deep-research pipeline earns its keep. A capability catalog is built from official documentation, help pages, user discussions, and historical tasks, and it is kept dynamic, updated with observed page states, control constraints, and failure cases as rollouts run. Each generated task is formalized as an executable contract binding the natural-language instruction to its domain, capability tags, initial state, and expected outcome, and a validity gate rejects tasks with unsupported functions, ambiguous goals, or unverifiable outcomes before they ever enter collection. CAPTCHAs get special treatment as infrastructure, not just a benchmark, because a verifier that stalls on a login gate blocks the whole trajectory collection pipeline, so targeted CAPTCHA data both unblocks data scaling and strengthens the model's ability to get past those gates in the first place.

The benchmark results are broad. On mobile, the 27B model reaches 60.5 percent on MobileGym, 84.0 percent on AndroidWorld, and 80.5 percent on OSWorld-Verified, while trailing the source-reported Claude-Opus-4.8 result of 83.4 percent. On web, it takes the top spot on all four benchmarks, including 93.4 percent on the refreshed WebVoyager, 80.2 percent on REAL, and 80.4 on Odysseys average rubric score. On grounding, 80.1 percent on VenusBench-GD is a new state of the art, 5.1 points above the previous UI-Venus-1.5-30B. The CAPTCHA numbers are where the margins are largest. On the deployment-oriented VenusBench-CAPTCHA, the 27B reaches 79.9 percent Pass at 1, up from 53.0 percent for the strongest general-purpose model. On NextGen-CAPTCHAs it reaches 54.5 percent against 20.4 percent for the strongest baseline, more than doubling it. The 9B variant is consistently within a few points of the 27B across the board, which is the efficiency argument they are making.

Safety is evaluated on two complementary threat settings. On OSHarm, which targets explicit threats like deliberate misuse and prompt injection, the 9B model reaches the lowest attack success rate at 11.3 percent, with the 27B at 15.3 percent. On OSBlind, where instructions are entirely benign and the harm arises from the execution context, all baselines remain highly vulnerable, with attack success rates ranging from 79.4 to 93.6 percent, while UI-Venus-2 cuts that to 48.8 and 47.9 percent. The authors note that all baselines are badly exposed to the benign-looking setting, which is the more interesting and underexplored failure mode.

The honest caveats. OSWorld 2.0 is the weak spot. Under the official 150-step budget, the 27B reaches only 2.8 percent binary accuracy and 13.2 percent partial score, well behind GPT-5.5 at 13.0 percent binary and the Claude models on partial score. That benchmark demands hundreds of coordinated actions across applications, and the model clearly has not closed that gap. The desktop capability is the newest and least mature of the three domains, and the OSWorld-Verified comparison is not a controlled ablation because the baselines use model-specific action scaffolds, including direct command-line actions, so the 80.5 percent should be read as a reference point rather than a clean win. There is no detailed ablation in the main text tying each training stage to a specific capability gain, which is a real gap for anyone trying to reproduce the recipe. And the CAPTCHA capability, while impressive, is a bounded task family, so the large margins there say less about general computer-use competence than the web and mobile numbers do.

The bottom line: this is a competent, well-executed foundation GUI agent release, and the open-sourcing of full weights plus evaluation infrastructure is what makes it genuinely useful to the community rather than just a leaderboard entry. The most defensible claims are the web and CAPTCHA results and the 9B-to-27B efficiency gap. The desktop and long-horizon computer-use results, particularly OSWorld 2.0, are where the capability still clearly has room, and the lack of stage-level ablations means you are trusting the three-stage recipe more than you are measuring it.
