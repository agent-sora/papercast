SoftwareGym: Scaling Computer-Use Agent Training with Diverse Synthesized Software Environments, from Tian Jin, Wenhao Wang, and Jing Kang at Shanghai Jiaotong University and Zhejiang University. Computer-use agents need interaction data from executable software environments, and constructing those environments at scale is the central bottleneck in training them. The paper identifies a trilemma that existing approaches do not jointly solve. You need interface and interaction diversity, to support generalization. You need functional reliability, so the environments produce valid, complex trajectories. And you need scalability, so you can expand the environment pool with limited engineering effort. The two dominant ways of making training data today each fail one leg of that trilemma. Native application environments, where you run real desktop and mobile apps, preserve realistic states and complex workflows, but integrating them into reproducible training environments is expensive, which limits how many applications you can cover and increases the risk of overfitting to one specific app. Browser-hosted environments are cheap to scale and give you state control, but the shared browser substrate limits interaction depth and workflow complexity. The paper's thesis is that you can synthesize the environments instead, and that synthesis is the key to getting all three properties at once.
The method is an automated design, implementation, and evaluation pipeline that synthesizes desktop applications at scale. Design produces rich functional specifications and, crucially, distinct style specifications for the interface, so independently generated apps do not all collapse into the same layout. Implementation realizes the specification into a working application and verifies it. Evaluation tests the GUI behavior at runtime, and when a task fails, the failure is fed back into the implementation for repair, which is the mechanism that enforces the functional-reliability leg of the trilemma. The result of running the pipeline is a library of one hundred eighty-two applications across twelve categories, image editors, media players, spreadsheet and table tools, code editors, and so on, with a mean GUI task pass rate of ninety one point five percent. From the same twelve categories they build SoftwareGym-Bench, a one hundred twenty-task evaluation suite. The two ablations that matter are clean. For design, they compare their full structured design against a simplified baseline under the same functional requirements and measure interface diversity with normalized tree-edit distance. Full design lifts the macro-average diversity score from four point nine to eighty three point six, which is a large jump, and it shows that explicit style control is what stops the generated apps from looking alike. For repair, they compare GUI-guided repair, where the runtime GUI evaluation drives the fix, against source-only repair, where the model only looks at the code. Starting from the same initial pass rate of fifty point four percent, GUI-guided repair climbs to eighty three point one percent, while source-only repair ends at forty eight point eight, barely moving. That is the evidence that runtime GUI feedback, not just reading the source, is what makes the synthesized apps actually work.
The data side deserves a second look, because the environments are only half the contribution. For each synthesized application the pipeline generates natural-language task instructions over the app's verified features, then rolls out an agent in the live environment to collect state-action trajectories, and the GUI runtime verifier discards the rollouts that dead-end or violate the app's actual behavior, so the trajectory corpus is the same runtime-verified material the ablation was built on. The computer-use agent is then trained on these trajectories with the screenshots and interface states of the synthesized apps as its training distribution, which is why the out-of-domain OSWorld result is the interesting one: the agent has never seen an OSWorld screenshot during training, and the gain comes from the interaction structure transferring rather than from interface memorization. The twelve application categories, image editing, media playback, table and spreadsheet work, code editing, and the rest, were chosen to span the interaction primitives a general desktop agent needs, from pixel-level manipulation to file I/O to menu navigation, which is what gives the synthesized pool its breadth even though it is only one hundred eighty-two apps.
The downstream question is whether trajectories from synthesized software are actually useful supervision for computer-use agents, and whether they transfer. The headline result: training on SoftwareGym trajectories, with no OSWorld application data in the training set at all, improves Pass@3 on the strictly out-of-domain OSWorld benchmark from forty one point three nine percent to fifty six point nine seven percent. On their own SoftwareGym-Bench the model reaches forty point zero percent. The strongest result comes from mixing: when OSWorld-native data and SoftwareGym data are combined for training, SoftwareGym-Bench performance rises to forty seven point five percent, so the synthesized environments complement rather than merely substitute for native-software data. That combination is the part I would trust most, because it shows the two data sources are carrying different signal. The transfer question is the one that separates a benchmark from a training asset, and the paper tests it directly. The synthesized SoftwareGym-Bench tasks are held out from the training set, so the forty percent result is on unseen software rather than on the specific apps the agent was trained on. That is the standard split, but the more important number is cross-benchmark transfer, where trajectories from the synthesized software are used to improve an agent that is then tested on real external computer-use benchmarks. The result is that the synthesized data produces a measurable gain on the external benchmarks, not just on the in-distribution SoftwareGym-Bench, which is the evidence that the diversity of the synthesized environments is teaching something general about desktop interaction rather than overfitting to the generated apps. The style variation in the design stage is what drives that transfer: because the pipeline generates applications with distinct visual and layout styles, the agent is forced to generalize across interface design rather than memorize a single look, which is precisely the failure mode of training on a narrow, real-world app corpus. The practical implication is that a team can scale computer-use training data without the annotation and licensing cost of real apps, and still get a model that transfers to the messy, out-of-distribution desktops it will actually meet in production. There is also a practical point about the repair loop that deserves emphasis. The fact that GUI-guided repair climbs from fifty point four to eighty three point one percent, while source-only repair stalls at forty eight point eight, is the empirical argument that you cannot synthesize reliable computer-use training environments by generating code alone. The runtime behavior of a GUI, the actual state transitions when a user clicks, types, and drags, is what makes an environment useful for training, and the paper shows that checking that behavior against the live app is the step that converts a pile of generated applications into a coherent, functional training substrate.
The skeptical read. First, one hundred eighty-two applications across twelve categories is a meaningful scale-up over prior synthesized-environment work, but it is still a small pool relative to the long tail of real desktop software, and the diversity metric is measured on interface structure, not on the depth of real workflows, so a high tree-edit-diversity pool could still be shallow in the interactions that matter. Second, the ninety one point five percent GUI task pass rate is measured on the environments' own generated tasks, so it is partly a measure of the pipeline's self-consistency, and the OSWorld transfer, while real and out-of-domain, is on a single benchmark. Third, the whole chain is only as good as the implementation model that writes and repairs the apps, so failures in the synthesizer become baked-in distribution quirks that the CUA then trains on. Bottom line: SoftwareGym is a credible answer to the environment-scaling bottleneck for computer-use agents, and the clean ablations plus the out-of-domain OSWorld transfer are the evidence that synthesized, runtime-verified software environments are a real source of training signal. I would want a larger, deeper environment pool and a second out-of-domain benchmark before treating the transfer as established, and I would audit how the self-generated task suite relates to the tasks the agent is eventually graded on.
