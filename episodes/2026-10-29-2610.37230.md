Title: TAO: Tool-Aware Joint Scheduling for LLM-Based Agentic Serving
Authors: Shuhuai Li, Shengdong Ye, Dongdong Ge
Labs: Shanghai Jiao Tong University; Stanford University
Arxiv: 2610.37230

TAO, from Shuhuai Li, Shengdong Ye, and Dongdong Ge, all at Shanghai Jiao Tong University, with Yinyu Ye at Stanford, is a systems paper about a problem that has only just started to matter, scheduling LLM inference in agentic workloads, where the model alternates between generating tokens on a GPU cluster and calling external tools that run on a completely separate pool of CPUs. The paper is the first to treat the tool-return time as a first-class scheduling signal, and the results are large enough to be hard to ignore for anyone running agent infrastructure.

The scenario they call CGDC, clustered GPUs with distributed CPUs, is becoming the actual deployment shape of agentic systems. The model inference lives on a cluster of GPUs, but the tools the agent calls, a search API, a database query, a code interpreter, a file system, run on a distributed set of CPU machines that are not co-located with the GPUs. When the model emits a tool call, the GPU session is effectively blocked, not by the compute, but by the tool, and the tool's return time depends on which CPU node it lands on, how loaded that node is, and what the tool actually does. The paper's framing is that in this regime the session's demand for GPU computation becomes interruptible, which is a clean way to say that the bottleneck has moved, it is no longer the prefill or the decode, it is the wait for the tool, and the scheduler that is optimized for the old bottleneck is now scheduling around empty GPUs. Existing serving systems handle this with heuristics, admit a session, place it, and hope, and they do not know when the tool will come back, so they either keep the session's KV cache hot and waste GPU memory, or evict it and pay a recompute penalty when the tool returns.

TAO's contribution is a value interface that scores each waiting session on three things, packaged as a triplet. The first coordinate is a node-specific KV-cache credit with time-aware decay, which captures how much of the session's prompt prefix is already resident on a given node and therefore reusable, and how fast that credit is evaporating as the cache ages. The second is a binary tool-return readiness signal, derived from historical tool-call durations on the distributed CPUs, which tells the scheduler whether this session's tool has almost certainly returned and the session can make progress right now. The third is the token footprint of the session, its demand on GPU memory. Given those triplets, a dynamic program jointly selects which waiting sessions to admit and where to place them, under the per-node GPU memory and CPU capacity constraints, and it does so by maximizing the additive triplets directly, with the coordinates evolving over time as the cache ages and the tools progress, rather than collapsing the three signals into one weighted score. That last detail is deliberate, a weighted sum would force the developer to pick the weights, and the DP formulation lets the three signals compete without a human choosing the trade-off. The whole thing runs in an evaluate-then-decide loop, the session evaluation component builds the triplets from tool observations and cache observations, the decision component solves the DP, and then an executor validates the plan against live state before applying it, because the state moved while the optimizer was thinking.

The results are reported across twelve settings, varying the model, the workload, and the concurrency. Against the best state-of-the-art baseline evaluated for each metric, TAO reduces latency by up to twenty six point eight percent, reduces mean time to first token by up to thirty six point three percent, and increases decode throughput by up to twenty nine point five percent. These are up-to figures, and the per-setting variation is in the paper's tables, but the direction is consistent across the twelve, which matters more than the magnitude for a scheduling contribution, because it means the tool-readiness signal is doing work in every configuration tested, not just in the ones where a tool happens to dominate the timeline. The time to first token number is the one that should register, because TTFT is the user-facing number in an agent, the user is waiting for the next model response, and the model cannot start that response until the tool has returned, so a scheduler that knows which sessions have their tools back and prioritizes them is going to cut the perceived wait directly. Twenty nine percent more decode throughput is the number that matters for the operator, because it means the same cluster serves more concurrent agents.

The positioning against prior work is where the paper is most specific, because there is a whole literature of scheduling signals that touch this problem from adjacent angles, and none of them put the tool-return time in the value function. Cache-aware schedulers like SGLang and Preble exploit the KV prefix structure to reuse earlier turns and balance load, and workflow-aware schedulers try to anticipate future calls in the agent's plan, and latency-aware schedulers prioritize by latency or remaining-work estimates. The closest neighbors are the systems that already knew tool timing was a signal, one predicts tool duration to choose how long to hold the KV cache, and another discounts the token footprint of a session as its tool runs, but in both cases the timing enters as a surrogate for some other quantity, and it goes through fixed scoring rules with manually chosen thresholds. TAO's claim is that the tool timing is not a surrogate, it is the signal, and that it should be modeled jointly with the cache credit and the footprint in one optimization, which is the difference between a feature added to a heuristic and a first-class input to the decision. The paper also notes the framework generalizes, to multi-agent orchestration, to looped agents that alternate inference and tools indefinitely, and back to plain chatbot serving where the tool-readiness coordinate simply does not activate.

The honest limitations are the generality ones. The dynamic program assumes the tool-return time distribution is estimable from history, which is true for the common tools but breaks for a novel tool with no history, and the value function's cache credit term is tuned to a particular KV cache eviction policy, so porting TAO to a different memory management scheme means re-deriving that term. The twelve settings are a good spread, but they are still twelve, and the gap between up-to numbers and typical numbers is not reported in the abstract, so the up-to figures are the ceiling, not the floor. The readiness signal is binary, which is a simplification of a continuous return-time distribution, and the binary works well when the tool durations are tight but will under-represent a tool with a long tail. The paper is a systems paper, the contribution is the formulation and the scheduler, not a model, and that is fine, because the serving layer is where agentic workloads are actually bottlenecked right now.

What I would trust is the problem framing, because tool-awareness as a scheduling signal is the correct abstraction and I expect it to appear in more serving stacks within a year, and the dynamic program formulation is the right level of generality, specific enough to solve, general enough to extend. What I would re-verify before deploying is the tail behavior, because the up-to numbers come from favorable settings, and in a production agent workload the tool-return distribution is heavy-tailed and the dynamic program's assumptions about estimating it are the first thing that will break under a novel tool. The engineering takeaway is the value interface itself, even if you do not adopt the full dynamic program, scoring waiting sessions by tool-readiness probability plus cache credit is a cheap heuristic you can drop into an existing scheduler and the TTFT improvement should show up, because the sessions whose tools are back are the ones that can make progress right now, and prioritizing them is the single highest-leverage change in agentic serving.
