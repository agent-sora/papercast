AutoSaddler: Automatic Harness Optimization with Durable Updates from Agent Execution Traces, by Sungho Park of POSTECH, Wonjoong Kim of KAIST, and Rongyuan Tan of Southern University of Science and Technology, with colleagues at Microsoft where the first author interned. The premise: language-model agents stay unreliable on long-horizon tasks partly because the scaffolding around the model — prompts, tool definitions, control flow — is hand-tuned folklore. AutoSaddler treats that harness as the thing to train: an offline optimization loop that runs the agent on mini-batches of tasks, diagnoses failed traces against the harness source code, generates targeted patches, keeps what validates, and remembers everything in a search graph. Across three agent benchmarks it lifts pass-at-one by nine to ten percentage points over well-regarded manual harnesses.

The formal setup is borrowed straight from machine learning and worth stating because every design choice falls out of it. Executing an agent under harness parameters theta defines a distribution over traces and outputs; the objective is expected task metric over a task distribution, estimated empirically because each evaluation costs a rollout. Training splits into train, development, and test sets drawn from disjoint task groups — on the software benchmark, training uses one repository entirely, validation two others, testing three more — so measured gains reflect generalization rather than memorized repairs. Each iteration evaluates the current harness on a mini-batch, enters a diagnosis-and-patch session, verifies improvement on that batch, optionally checks the development set, then reflects and plans the next candidate. The authors call this backpropagation under textual gradients: unlike numerical gradients, textual error signals are not automatically correct, so every update needs explicit hypothesis generation and empirical verification before it sticks.

Three agents do the work, all implemented on the Claude Agent SDK, all running Claude Opus 4.6 as the underlying model. The Diagnosis-Patch Agent receives failed traces plus the harness codebase and instrumented retrieval guidance for long trajectories; diagnosis and patch generation are deliberately not separated so the patch is written by whoever understands the evidence. Patches are constrained to a taxonomy across three layers. Prompt patches add or modify behavioral rules. Tool patches span four subtypes: adding a missing tool, changing arguments, fixing implementations, rewriting descriptions. Middleware patches cover just-in-time reminders hooked before specific tool calls, infrastructure changes to configuration or budgets, and agent-loop logic changes. These divide into Capability patches, which modify executable code or orchestration, and Steering patches, which only edit text. Optimization runs capability patches first and steering later, analogous to learning-rate scheduling.

The Reflection Agent compares pre- and post-patch traces, sorts outcomes into fixed, regressed, still-failing, and still-passing, and writes lessons into EvoDAG — a directed acyclic graph where nodes are explored harnesses annotated with results and edges are the diffs between them. The Evolution Agent then proposes the next harness not merely by extending the current one but by recombining any subset of ancestors, an evolutionary escape from local optima. EvoDAG deserves a paragraph of its own because it is the piece most teams will skip first and miss most. Standard practice in prompt optimization keeps only the incumbent candidate and a score curve, discarding negative results precisely when they are informative. Here every explored harness remains addressable with its attached lessons, category outcomes, and metric deltas, so the evolution agent composes the next candidate from arbitrary ancestors rather than from the current tip alone. The accepted-patch census shows what lands in practice: hooks injecting reminders before error-prone tool calls, budget-aware agent-loop changes, argument fixes exposing filtering that existed but was undiscoverable, and description rewrites that block plausible-looking misuse. Nothing in that list resembles a hero edit; it reads like disciplined maintenance performed at machine speed. After the rollout budget is spent, the best development-set candidate is evaluated once on test and never touched again.

Results first, then the ablations, which are the real contribution. On GAIA2, a simulated-smartphone assistant benchmark, AutoSaddler reaches sixty-two point zero percent average pass-at-one against fifty-three for the default manual agent — nine points. On SWE-Bench Pro enterprise repositories it takes SWE-agent from thirty-seven point three to forty-six point nine. On Terminal-Bench 2.0 it lifts Terminus 2 from forty to fifty percent on the forty-task test split, also beating the hand-tuned Terminus KIRA harness by two and a half points. Against the strongest automated competitor per benchmark, margins are seven point four, four point four, and six point seven. One honesty note for implementers: the prose section misstates two of these deltas — eight point four and six point two — contradicting the paper's own tables and abstract; the arithmetic supports nine point six and four point four, which is sloppy copyediting but not fudging, since the underlying per-repository numbers are printed beside the errors.

Efficiency numbers matter because rollout budgets dominate this kind of work. On GAIA2 development, AutoSaddler hits seventy-two point three percent accuracy within roughly one thousand task executions while GEPA saturates at sixty-four point six and Meta-Harness at sixty-one point five despite about twenty-eight hundred executions. Counting only traces actually leveraged for learning, it peaks after one hundred forty-seven rollouts — ten times fewer than Meta-Harness's fourteen hundred. Which is to say: the expensive resource being conserved here is the task agent's own executions. A cost-focused configuration reaches sixty-seven point seven percent with three hundred ninety-one rollouts, though optimizer-side monetary cost per patch runs moderately higher than baselines.

The ablations dismantle the framework into its three claimed ingredients, each costing real points when removed. Replacing deep debugging with a single-shot reflection call — the standard prompt-optimization pattern — drops GAIA2 from sixty-two point zero to fifty-seven point eight; instrumentation shows the full session makes six point two extra tool calls and five point eight extra file accesses per step and accepts thirteen patches by iteration twenty-five versus five without. Removing the patch taxonomy forces unconstrained editing, and behavior collapses onto textual tweaks: ninety-one point five percent of generated patches become Steering edits, the high-value categories like new tools collapse to four percent of activity, and GAIA2 falls to fifty-six point nine. Acceptance rates justify the taxonomy — new tools are accepted eighty-three percent of the time, loop changes seventy-one, infrastructure changes sixty-seven — and capability patches match steering patches on fix rate while causing roughly half the regressions, eight versus seventeen percent. Removing generalization-aware selection — dropping both reflection and validation filtering — is the most damaging cut, down to fifty point six. Dev-set tracking shows why: fix rates stay similar either way, but regression rates trend upward without selection and downward with it, and the paper tells a clean cautionary tale where an unconstrained optimizer installs a new messaging tool and forcibly redirects a heavily used notification hook toward it, breaking unrelated scenarios en masse; AutoSaddler produced the identical bad idea at iteration four and reflection blocked it.

What transfers to your own stack: treat the harness as versioned code, split evaluation by task group so validation means something, prefer structural interventions over prompt incantations when acceptance data supports them, and keep a persistent graph of what was tried with machine-readable lessons attached. What to verify before trusting the headline: gains rest on Claude Opus 4.6 end-to-end — including the optimizer judging its own patches, a self-evaluation circularity worth probing — sample sizes on Terminal-Bench are small enough that plus-minus zero looks suspiciously tidy, and a cross-model transfer experiment swapping in Haiku 4.5 retains five and a half points of gain, which is encouraging but single-benchmark. The one missing control is optimizer ablation — running this loop with weaker diagnosis models would show how much of the gain belongs to the meta-layer's own capability, and forty tasks per terminal-suite split give coarse resolution at best, so treat single-digit deltas as provisional. Bottom line: this is the most convincing demonstration yet that harness tuning can be automated with proper training discipline — diagnosis depth, patch structure, and validation filtering each earn their keep — and the regression-rate framing alone is worth stealing for any agent pipeline you operate.
