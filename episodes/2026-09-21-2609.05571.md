Grounded Skill Synthesis from Code at Scale for Agentic Intelligence. The first three authors are Yongqi Tong, Pan Wang, and Hang Wang, all from Ant International, with the remaining authors Jianshe Li, Xin Zhang, Jiang-Ming Yang, and Wei Wu also at the same institution.

The paper tackles skill synthesis for agentic systems, meaning the process of turning reusable procedural knowledge into records that an agent can retrieve at inference time and execute. The motivation is that most agents today rediscover the same procedures from scratch, task by task: how to structure a stateful CLI tool, how to handle a retry with backoff, how to validate a configuration before loading it. If those procedures were captured once, verified, and indexed, a new agent could start from them instead of from zero. Two existing routes have known weaknesses. Trajectory-based synthesis distills skills from the agent's own execution traces, which couples every skill to the specific model, tools, and task distribution that produced the trace, and caps skill quality at the generating agent's competence. Document-based synthesis pulls skills from human-written text, which avoids the trajectory coupling but has no executable evidence against which a synthesized procedure can be grounded or verified. The proposal here is a third substrate: source code itself. Code requires no prior agent experience, and it comes with executable evidence. The pipeline is called Code2Skill, and the resulting skill bank, CodeSkillBank, contains just over 1 million accepted records, 1,006,822 to be exact, built from 19,769 popular, actively maintained GitHub repositories.

The pipeline has four stages. First, selection. The source pool is every GitHub repository available as of April 14, 2026 with more than 500 stars. Within each repository, the pipeline parses functions, methods, command-line entry points, and file-level components, and an LLM tagger selects the units that show reusable intent, operational structure, and visible execution constraints, rejecting trivial, project-local, and unsupported traces. Second, record generation. Each selected unit is lifted into a typed skill record of one of three kinds: an atomic operation, a composite workflow, or a recurring pattern. A good record, by the paper's own definition, must say when the procedure applies, which steps are essential, what invariants must hold, which failure cases change the execution path, and which generalizations fall outside its scope, so the record carries applicability conditions, steps, invariants, failure handling, anti-goals, and supporting evidence spans.

Third is the verification step, and this is the part that makes the bank "grounded." A language model reconstructs the original implementation using only the synthesized skill, with the source body hidden. A second, source-aware judge then compares the reconstruction against the actual code and filters out records that are unsupported or incomplete. Accepted records are deduplicated and stored in a provenance-rich evidence archive, with feature-tagged and purpose-indexed views so downstream agents can retrieve the right record for the task at hand. The authors are explicit that this reconstruction check is a scalable repository-level filter for assessing whether a skill is supported by its source; it is not a substitute for test-based verification, and the pipeline does not assume tests or formal properties exist.

One detail on the selection stage: candidate units are ranked with a reuse-potential score that weighs extracted features against penalties for project-locality and support, and only the top-ranked units per repository proceed to record generation. The accepted records then get an operational card: a compact description of when to use the skill, the execution steps, and the constraints, which is what actually gets retrieved and shown to the downstream agent. The record types are not interchangeable in practice: atomic operations cover single-function behaviors, composite workflows chain several of them, and recurring patterns capture idioms like retry logic or resource cleanup that appear across many repositories.

The downstream evaluation is the largest part of the paper. It is also the part where the evaluation design is doing real work: the 72 comparisons are protocol-matched, meaning each skill source, Code2Skill, Trace2Skill, ExpeL, and SkillRL-Bank, is evaluated with the same retrieval budget and the same downstream prompt format, so the comparison isolates the skill content rather than the harness. Across 72 protocol-matched evaluations spanning nine model settings and eight benchmarks, covering software engineering, mathematical and scientific reasoning, and system interaction, models augmented with retrieved CodeSkillBank skills improve their macro-average from 42.90 without skills to 47.90 with them, an 11.7 percent relative gain, winning 57 of the 72 runs. On SWE-bench Verified, all nine model comparisons improve. Under a unified downstream interface, Code2Skill beats the trajectory-derived skill banks on all seven shared benchmarks: 49.5 average for Code2Skill, against 31.0 for Trace2Skill, 27.9 for ExpeL, and 32.8 for SkillRL-Bank, with individual benchmark margins of 6.6 to 13.3 points over the strongest trajectory-derived baseline.

Two secondary findings are worth flagging. First, the skills help most when used to guide planning or to critique concrete candidate solutions, and even compact summaries of skills retain most of the benefit at much lower context cost, which matters because the full skill records carry applicability conditions, invariants, and failure cases that are expensive to include wholesale. Second, skills synthesized from tested AI-generated code achieve a 93.50 percent pass rate in the reconstruction filter, versus 93.00 percent for human-written code, which the authors take as initial evidence that the same pipeline can keep expanding the bank as AI-written code becomes more prevalent. A third point the paper makes explicitly is that the bank is a substrate, not a system: the records are designed to be retrieved and injected into whatever downstream agent is running, so the quality of the surrounding agent's planning is still what determines how well the skills are used.

The skeptical read. The core idea, that a million verified procedural records can act as an external, versionable memory for agents, is plausible and the evaluation scale is genuinely larger than most skill-library papers. But the reconstruction-based verification is where I would push hardest before trusting the bank. The filter asks whether an LLM can regenerate the original code from the skill text. A skill that is vague but generic can pass that check in a shallow sense, because many correct implementations exist, and the judge is comparing to one reference implementation, not to a specification. The paper concedes this is not test-based verification, which means a record can be grounded in the sense of "consistent with one implementation" while still being wrong about the invariants that matter in your stack. The 11.7 percent average gain also deserves scrutiny: it is a macro average across eight benchmarks and nine model settings, and the per-run distribution is 57 wins out of 72, meaning 15 runs where skills did not help and possibly hurt. For a production harness, the right question is the worst-case delta on the tasks you actually run, not the macro average. There is also a retrieval problem the paper glosses over: 1 million records is a large index, and the gains depend on the feature-tagged, purpose-indexed retrieval views surfacing the right record at the right time; a misretrieved skill that contradicts the agent's plan is worse than no skill. Finally, the source pool is 500-star GitHub repositories, so the bank encodes the conventions, idioms, and failure modes of popular open-source code, which is a reasonable prior for software-engineering agents and a weak one for anything else.

Bottom line: this is the most complete treatment of code-derived skill synthesis I have seen, with a bank size and evaluation breadth that other skill papers do not match. Treat the reconstruction filter as a necessary but not sufficient quality gate, and if you adopt it, re-validate the records you actually retrieve against real tests for your target workloads. The most practical near-term use is as a training and evaluation resource: the bank's provenance metadata lets you audit where each skill came from, which is exactly what you want when a retrieved skill misbehaves in your harness.
