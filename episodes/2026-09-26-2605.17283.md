OProver: A Unified Framework for Agentic Formal Theorem Proving, by David
Ma, Kaijing Ma, Shawn Guo, and a long co-author list, from the M-A-P group,
which does not print institutional affiliations on the paper but releases the
model and code under its Hugging Face organization, a pattern that has become
common for formal-mathematics work coming out of applied AI labs.

The setting is the current state of Lean-based theorem proving, and the
specific gap the paper targets is a real one. Recent systems have gotten good
at generating proofs in a single pass, or by sampling many attempts and
keeping the one that type-checks, and they have gotten good at using
retrieval and compiler feedback, but those two capabilities have usually
lived at different times of the system's life. Retrieval and compiler
feedback appear at inference time, as a test-time heuristic you bolt on,
while the model's training treats proving as a single-shot generation problem
and never learns to use the feedback loop as part of its own policy. The
paper's claim is that if you are going to run a multi-round, retrieval-
grounded, feedback-conditioned proving process at inference, then you should
train the model on that exact process, so the training-time interface matches
the proving-time interaction rather than diverging from it. The training
mixture is worth describing because it is unusually specific for a
formal-mathematics paper. The one-time continued pretraining uses a
sixty-five-billion-token mixture, roughly thirty percent Lean formal data
drawn from OProofs, twenty percent code data, forty percent mathematical
data, and ten percent long-chain-of-thought data, so the base model is
exposed to the formal structure, the surrounding code, the underlying
mathematics, and the long reasoning traces, before the iterative post-
training begins. The reinforcement learning stage is the part that makes the
agentic loop a trained capability rather than an inference-time trick. For
each theorem, the system samples multiple multi-round rollouts, each with up
to a fixed number of refinement rounds, and assigns a per-round reward that
is a small format bonus plus the main reward, which is one if the compiler
verifies the proof and zero otherwise, with group-relative advantage
normalization so the reward is relative to the other rollouts for the same
theorem rather than an absolute value, which stabilizes the optimization
when most rollouts for a hard theorem fail. The retrieval memory is the
component that distinguishes this from a pure iterative-refinement system.
It is a growing index of proofs the compiler has verified, and at inference
time, before the first attempt on a new theorem, the planner queries it for
the most relevant verified proofs, which are injected as context, so the
model starts each new theorem with a set of worked examples drawn from
domains it has already proven. This is the same design pattern as
retrieval-augmented generation, but the retrieved units are verified
theorems with their full proof structure rather than prose passages, which
is a meaningfully different retrieval target, because a verified theorem
carries not just a natural-language statement but a Lean 4 proof that
type-checks, and the model can use both the statement and the proof as
evidence for the new theorem. The memory grows as the prover runs, so a
system that has proven many theorems in a particular area has a richer
retrieval corpus for theorems in that area, which means the retrieval
quality is domain-dependent and improves with the system's own experience,
which is a self-reinforcing property that is hard to replicate with a
static retrieval index.

The framework, OProver, has three interacting components, the proving
policy, the retrieval memory just described, and the Lean four compiler as
the verification environment. At each round, the policy conditions on the
target statement, the retrieved proof context, the most recent proof
attempt, and the most recent compiler feedback, and produces a new attempt.
A notable modeling choice is that the policy conditions only on the most
recent attempt and its feedback, not on the full interaction history, which
keeps the state fixed-size and makes the training interface identical to the
inference interface.

The training data is the other major contribution, a corpus called OProofs,
built from public Lean resources, large-scale proof synthesis, and agentic
proving traces. The headline sizes are one point seven seven million Lean
statements and six point eight six million compiler-verified proofs, plus
serialized proving trajectories that record the retrieved context, the
failed attempts, the compiler feedback, and the subsequent repairs. The
last part is what makes it different from prior Lean corpora, which store
the end products of proving, the statement and the final verified proof,
but not the process. OProofs stores the process, which is exactly the
supervision you need to teach a model to do iterative, feedback-conditioned
proving. The corpus is built from three sources, and the mix matters. The
first is public Lean resources, existing theorems and proofs from open Lean
projects, which provide the verified ground truth. The second is large-scale
proof synthesis, where the system generates proofs at scale and keeps only
the ones the compiler verifies, which produces a large but easy-tilted set.
The third is the agentic proving traces, where the system runs its own
multi-round proving on the hard cases and records every failed attempt, every
compiler diagnostic, and every subsequent repair, and this third source is
what the other two do not provide, because it is the only source that
captures the repair trajectory, which is the unit of supervision for teaching
a model to use feedback. The serialized trajectories record the retrieved
context, the failed attempts, the compiler feedback, and the repairs in
order, so a training example is a full proving episode rather than a single
proof, which is the structural difference between OProofs and a conventional
Lean statement-proof dataset. The training itself is a one-time continued pretraining on a
mixture that is roughly thirty percent Lean formal data, followed by
iterative post-training, where each iteration runs agentic proving
rollouts, indexes the newly verified proofs into the retrieval memory, uses
the repair trajectories as supervised fine-tuning data, and uses the
unresolved hard cases for reinforcement learning, so the corpus grows as the
prover improves.

The results are across five benchmarks. OProver at thirty-two billion
parameters attains the best pass-at-thirty-two on MiniF2F at ninety-three
point three percent, on ProverBench at fifty-eight point two percent, and on
PutnamBench at eleven point three percent, and ranks second on MathOlympiad
at twenty-two point eight percent and on ProofNet at thirty-three point two
percent, which the authors describe as more top placements than any prior
open-weight whole-proof prover. The honest read of those numbers is that the
easy benchmarks are near saturation, with MiniF2F at ninety-three point
three, while the hard ones remain low, with PutnamBench at eleven point
three, and that is the same pattern the field has had for a while, the gap
between the competition-level and the research-level difficulty is where the
real work is.

Now the skeptical read. The first question is the iterative post-training
loop, which is the paper's central idea, and the honest version of that
question is whether the self-improvement, where the prover indexes its own
newly verified proofs and trains on its own repair trajectories, actually
moves the needle or mostly just re-weights what it already knows. The second
question is the scale of the corpus relative to the claim, the corpus is
large in absolute terms, but the reinforcement learning stage uses only the
unresolved hard cases, which are a small fraction, and the question is how
much of the reported gain comes from the pretraining corpus and how much
from the agentic loop. The third question is the benchmark composition, the
three best placements are on the more competition-flavored benchmarks, and
the second placements are on the harder ones, so the "more top placements"
framing is true but it is doing some work, and a reader should check whether
the comparison is against the same set of prior provers on the same
difficulty split. And the practical question is the inference cost, because
a multi-round retrieval-and-repair loop is substantially more expensive per
theorem than a single pass, and the pass-at-thirty-two metric rewards
sampling many attempts, so the framework's advantage partly comes from
spending more compute per problem, which is a real but different claim than
being more sample-efficient.

Bottom line: this is a well-posed contribution that closes a specific gap in
the Lean proving literature, training the model on the same iterative,
retrieval-grounded, feedback-conditioned process it runs at inference, with
a process-rich corpus and competitive benchmark results. The open question is
how much of the gain is genuinely from the agentic training loop versus the
scale of the pretraining corpus, and whether the advantage survives a
sample-efficiency accounting rather than a pass-at-thirty-two one.
