Memory Tax, by Xuan He, Sining Zhou, and Ruozhen Yang, from the University of Illinois Urbana Champaign, Tsinghua University, and Renmin University of China, among others, is one of the most-upvoted papers on Hugging Face this week, and it takes aim at a question the agent-memory community has been avoiding. When you build a memory system for a long-horizon agent, a graph store, a lifecycle, a trained policy, does it actually beat just retrieving straight from the raw history? The short answer they arrive at is no, not in many cases. They define the net value of memory relative to naive RAG and split it into two terms, memory benefit and memory tax, and then spend the paper explaining why the tax keeps winning.

The setup is a large-scale evaluation. They test on three personal-agent memory benchmarks, LongMemEval-s, PersonaMem-v2, and MINT-Eval, and because of cost they evaluate twenty percent of PersonaMem-v2 and ten percent of MINT-Eval, both with stratified sampling over question types. They take representative systems from each of four families. The flat stores, A-MEM, SimpleMem, and MemOS. The hierarchical or lifecycle systems, MemoryOS, LightMem, and OpenViking. The graph-based systems, HippoRAG2, PlugMem, and MAGMA. And the trained-policy systems, MemT and Memory-R2. They run every one of these on three backbones, Qwen 3.5 at four billion, Qwen 3.6 at twenty seven billion, and GPT 5.6 Luna in its low setting, with a shared Qwen 3 Embedding model at 0.6 billion parameters for retrieval and a Qwen 3 Reranker for reranking. Answers are scored by an LLM-as-Judge backed by the twenty seven billion model.

The numbers are the point, so here they are. First the reference points. With no context at all, the four billion backbone scores nine point zero on LongMemEval-s, and even stuffing the entire raw history into the context, full context, only reaches fifty eight point six, which tells you how much a long personal history exceeds a context window and why retrieval is on the table at all. Gold context, the oracle where you hand the model exactly the turns that answer the query, reaches seventy three point four to ninety two point eight on LongMemEval-s depending on backbone, so that is the ceiling the retrieval methods are trying to approach. Naive RAG, one round, scores seventy point two on LongMemEval-s with the four billion backbone, rising to seventy seven point six with the twenty seven billion and eighty two with Luna. Two-round RAG pushes that to seventy two point two, eighty one point four, and ninety point zero. Two rounds is only a modest gain, which is consistent with their observation that the benchmarks, especially LongMemEval-s, are retrieval-friendly, the relevant turns are usually findable in a single pass, and there is limited headroom left for any memory system to add. Now look at the memory systems against that bar. A-MEM comes in at seventy point four, which is already below one-round RAG by one point eight, and drops further on the bigger backbones. SimpleMem is at sixty point two, twelve point zero below RAG. MemOS is at sixty two point zero, down ten point two. And OpenViking, the most aggressive of the lifecycle systems, is at thirty one point eight, a gap of forty point four below two-round RAG. That is not a close contest. On the harder benchmarks the story is the same and the margins are worse. PersonaMem-v2 sees RAG at thirty seven to forty six, and most memory systems hovering around it or below. MINT-Eval is the weakest field of all, with RAG in the mid twenties and memory systems scattered from eighteen to thirty eight, several of them well under RAG. The headline is that naive RAG over the raw corpus is a strong baseline, and a meaningful fraction of the dedicated memory systems underperform it while costing more in tokens, LLM calls, and storage.

Their contribution is the framing, not the benchmark results. They say memory goes beyond a purely beneficial augmentation. It is a double-edged process that changes how the raw history is organized and accessed, and those changes are deviations from the raw history. Some deviations are intended, reorganizing scattered facts, distilling preferences, and those are the memory benefit. But other deviations remove or obscure evidence, and that is the memory tax. When the tax outweighs the benefit, the system falls below RAG overall, which is exactly what the tables show. So they stop there and dig into where the tax comes from, because the benefit is the expected gain and the tax is the overlooked loss.

They trace the tax through three dimensions. Faithfulness, which is how well the information survives the ingestion process at all, does the fact still exist in the memory after it has been summarized, extracted, or linked. Accessibility, which is whether the preserved information can actually be recalled at query time, and this is where a lot of the tax hides, because the evidence is in the store but the retrieval does not surface it. And robustness, which is how stable a given memory system is when you swap the backbone, because a system tuned to one model can degrade on another. On the system side they identify concrete failure modes. Fragmenting, where one raw turn is split into several memory units and the query needs the whole turn but retrieval only returns a piece. Diluting, where a single fact is spread across many units so its signal is weakened. And rephrasing, where the memory rewrites the source in a way that breaks exact-match or embedding retrieval that would have found the original. Each of these is a mechanism by which the memory tax shows up, and each is something you can actually go fix in your pipeline rather than redesign the whole architecture.

They check that the benefit-tax view is not specific to conversational memory by extending it to experiential memory and world-model memory. On experiential memory, agent task benchmarks with Qwen 3.5 at four billion as the backbone, the memory baselines do not outperform naive RAG in overall performance in many cases, and the token cost per task is substantially higher. That is the same negative net value in a different setting, which supports their claim that the concept generalizes beyond the personal-agent scenario. The world-model memory case is the more striking one, because there the memory is not a store of past turns but a learned model of how the environment behaves, and the same benefit-tax decomposition applies, the intended gain is a compressed, reusable model of the world, and the tax is the distortion that model introduces when it is used to answer a question that the raw observations would have answered more faithfully. The point of the generalization is that the tax is not an artifact of a particular memory implementation. It is a property of any process that transforms raw information before it is accessed, and the benefit-tax split is the way to measure whether that transformation is worth it.

The practical guidance is the part I would take away. They recommend evaluating any memory system against a retrieval baseline over the same raw history with the retrieval budget aligned, and they use a Retrieval Scope metric, the number of tokens in the retrieved memory units, to make the budgets comparable, because a fixed top-k retrieves very different amounts of information across systems with different granularity. They report accuracy alongside token cost, wall clock time, number of LLM calls, and memory storage size, so you can see the cost of the memory, not just the score. And their design implications are deliberately conservative, simple changes to existing memory systems that reduce the tax without new architectures, because the point is that the tax is the thing you should be minimizing, not the benefit, which you already get by design.

What I would trust here is the negative result, that many published memory systems do not beat naive RAG, because it is consistent across three benchmarks, three backbones, and four system families, and the gap is large enough on several systems that it is not a tuning artifact. What I would re-verify before acting on it is the judge, because LLM-as-Judge with a single model can bias the comparison in ways that are hard to see, and the MINT-Eval slice is small. The engineering takeaway is real though. If you are building an agent with memory, the first thing to do is run your raw history through a plain chunk-based retriever and hold that number in your head, because it is likely higher than the memory system you are about to build, and the memory only earns its keep if you can show it clears that bar with the tax, not just the benefit, accounted for. Memory Tax is a good name for the idea, and a useful one.
