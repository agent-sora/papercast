The paper is OpenVLHarness, real-world visual agentic tool-use with multimodal memory, from Yu Zhou, Cheng-Fu Yang, and Rui Sun, at the University of California, Los Angeles, with co-authors at Apple. The starting point is a controlled study on 22 multimodal benchmarks that shows the obvious lever is nearly dry: simply increasing the inference budget of the base model, moving it from its highest standard effort to maximum effort, buys only a small, diminishing gain on the average score. That is the motivation for a different lever, one that does not touch the model weights at all. OpenVLHarness is a reasoning harness, external scaffolding around a frozen multimodal model, organized around two pieces: a capability layer that gives the model consistent access to heterogeneous tools and renders their outputs into observations the model can actually read, and persistent multimodal memory that keeps the images, structured data, and web references the agent has gathered as addressable artifacts for the rest of the query, so the model can inspect and recombine them across reasoning steps.

The paper's own diagnosis of why the base model stalls is worth stating, because it frames every design choice. Many real visual tasks need evidence the model cannot reliably produce from internal reasoning alone. Localizing dozens of tiny objects in a dense scene, retrieving long-tail external knowledge about an entity, or computing a quantity from intermediate measurements all require grounded perception, external lookup, or arithmetic on measured values. Those are exactly the operations a tool can do and a decoder cannot. The harness therefore treats the model as a reasoning engine over an accumulating evidence base, rather than as a self-contained predictor.

The capability layer is the first half. It combines task-level tool interfaces with evidence rendering. The tools are heterogeneous backends, grounding and detection models, visual search, web search, and numeric computation, and the capability layer's job is to normalize them: the model calls a tool through one consistent interface, and the tool's raw output, which might be a list of bounding boxes, a scraped webpage, or a table, gets converted into a model-readable observation. That conversion step, the evidence rendering, is doing more work than it looks. Raw tool outputs are long and noisy, and if you just concatenate them into the context, the model either ignores them or drowns in them. The rendering layer reformats them into compact, structured observations with stable addressing, which is what makes them usable in the next reasoning step.

The second half is the persistent multimodal memory. This is not a summary of what happened, it is the artifacts themselves. The images the agent retrieved, the structured data it extracted, the web references it pulled, all stay in memory as addressable objects with identifiers. A coding interface then runs generated programs over that stored data, which is the key capability: the model can write and execute code that combines results from multiple tools, for example taking the bounding boxes from one grounding pass, joining them against a table from a search result, and computing a count or a ratio that no single tool returned. Without that code step, composing evidence across tools requires the model to hold everything in context and do the arithmetic in its head, which is exactly where the failures live.

The evaluation is the strongest part of the paper, and it is unusually broad. Twenty-two benchmarks spanning four domains, grounding, visual search and deep research, general VQA, and spatial reasoning. Eight backbones, both open and proprietary: the Qwen3-VL family at 8B and 32B, Kimi K3 at maximum effort, and the GPT-6 family, Luna and Astra at medium effort. The headline is that OpenVLHarness improves the average score by 9.7 to 12.6 points over the matched no-tool baseline, with +11.2 using Qwen3-VL-8B, +9.7 with Kimi K3, and +9.9 with GPT-6 Astra. The 32B Qwen goes from 56.52 to 66.09, and the 8B from 45.76 to 56.52. The cost comparison is where the paper earns its keep as an engineering result: with GPT-6 Luna at medium reasoning effort, OpenVLHarness outperforms the base model, Codex, and Visual Sketchpad at maximum effort by 7.7 to 8.5 points while using at most 37 percent of their model-token cost. In other words, it beats a much bigger reasoning budget with a small fraction of the tokens.

The paper also runs a failure diagnosis, which is where the practical content is. They took failure trajectories from the Qwen3-VL-8B configuration and had a strong model, Kimi K3, critique each one, labeling the primary failure cause and proposing a fix. Those labels agree with human annotations on 92 percent of 100 sampled failures, which is high enough to trust the taxonomy. The finding is that failure patterns differ by domain. In grounding, where scenes have more than 25 objects, the dominant failure is incorrect tool output, 75 percent of failures, because missed or merged instances break exhaustive detection. In visual search and deep research, the dominant failure is an omitted tool call, 49 percent, the model simply never called the tool it needed. Spatial and general VQA mix omitted calls with reasoning errors. What is reassuring is that failures from unusable or ignored correct tool outputs are rare, 3 to 8 percent across domains, which suggests the capability layer generally presents evidence in a form the model can use.

From that diagnosis they build two coding-agent workflows for specializing the harness on custom data, without updating any weights. Harness search edits the system prompt, tool descriptions, and evidence-rendering templates, selecting candidates through repeated evaluation. Tool generation implements new task-specific tools by composing existing capabilities. On four datasets with contrasting failure profiles, the right workflow depends on the profile: harness search improves ERQA and RealWorldQA by 4.1 and 3.7 points where text-level changes dominate, while tool generation improves SparBench and FREAK-VQA by 8.2 and 4.5 points where new task-specific tools are needed, and in fact harness search slightly hurts those two, by 0.5 and 1.0 points, because editing prompts does not add the missing composition.

There is also a clean ablation, and it attributes the gain. Starting from the no-tool baseline, raw tool access alone adds 3.8 points at 8B and 4.3 at 32B, with the largest gains in grounded perception. Adding the capability layer, the full tool schemas plus evidence rendering, is where most of the remaining gain lands, and that comparison does not separately isolate the schema from the rendering. A textual-memory variant, structured data bindings and web references but no reusable image handles, adds only 0.7 at 8B and 0.3 at 32B. Completing the persistent multimodal memory with visual attachments and reusable image handles adds a further 3.1 and 4.5, bringing the full harness to 47.1 and 52.5 overall, with the biggest jump in visual search and deep research, 6.2 and 3.5 points. So the decomposition is roughly: tools plus rendering do the heavy lifting, and retained image artifacts add a smaller but real second chunk, concentrated where evidence has to be revisited.

What I would trust: the breadth of the backbone sweep and the cost curve. Showing the same harness lifting eight different models, and beating maximum-effort baselines at a third of the token cost, is exactly the evidence that the gain comes from the scaffold rather than the model. The 92 percent agreement on the failure taxonomy is also well done. What I would re-verify: the benchmarks are a curated set of 22, several of them internal or newly released, so the absolute scores are not directly comparable to prior literature. The cost figure is measured on 1,000 query rollouts, which is reasonable, but it is model-token cost only, and it excludes the compute of the tools themselves, the grounding and search backends, which in a real deployment is not free. A skeptical read: this is a genuinely useful systems contribution with honest, broad evaluation, and the diagnose-then-specialize workflow is a practical recipe. But it is a harness over existing models, and the ceiling it hits is the ceiling of the frozen backbone, so it will not help a task that requires new perception the tools cannot supply.
