CogEvol: Towards Efficient and Reliable Learning Environment Generation, by the CogEvol Team, from CogEvol Inc. and Tsinghua University, with first authors Shangqing Tu, Daniel Zhang-Li, and Yucheng Wang.

This is a new foundation-model family, and that matters for this show. CogEvol is a pair of models, a 4B and a 27B, trained specifically for one narrow job: Learning Environment Generation. Given a course brief, it produces a finished learning artifact in a single pass, either structured-JSON slides or a self-contained interactive HTML page. The claim is efficiency and reliability: across 220,000 production requests, a slide completes in a median of 17 seconds and an interactive page in 59, replacing the minutes-long multi-turn agent scaffolding that was the incumbent approach. The 4B is released openly under Apache 2.0; the 27B has served live production traffic in collaboration with the OpenMAIC team since August 2026.

I will be precise about one thing up front. CogEvol is built entirely through post-training on top of public base models. The 27B starts from Qwen3.8-27B, a hybrid architecture interleaving 48 gated-delta-net linear-attention layers with 16 full-attention layers and a multi-token-prediction head; the 4B starts from the dense Qwen3.5-4B. The authors contribute everything above the base: the data pipelines, hybrid reward and RL recipes, evaluation suites, and serving infrastructure. So this is a capability release, not a new pre-trained base, and I am flagging it as a foundation-model technical report in the sense the standing rule intends, a new named family of production models for a specific task, not because they trained a transformer from scratch.

The task is harder than it sounds because the output is an executable artifact, not free-form text. A schema-valid slide can still clip text or overlap tables; a valid HTML document can still crash on load or expose dead controls. Syntactic validity is necessary but not sufficient, so the whole design is built around execution-aware verification.

The data pipeline is the first real contribution. There are two, one per modality, and both follow three principles: training prompts come from real production usage, teacher outputs are accepted only after execution-aware verification, and the supervision format matches the deployment contract. The slide pipeline is production-seeded synthesis. They start from completed production slide scenes, join them with outlines and image assets, and a specification model converts each seed into a self-contained design brief. Data expansion happens at the specification layer, with each round of variants targeting failure modes the previous checkpoint actually showed: table and footer collisions, English wrapping, chart-label overlap, formula-heavy and code layouts. The final round seeds 500 production scenes with six structural variants each, 3,000 hard layout prompts, and fixed benchmark topics are excluded before generation to prevent train-test contamination. Teacher candidates, Gemini 3.1 Pro and 3.5 Flash, emit the final scene graph directly, and each candidate must pass JSON parsing, schema validation, a canonicalization step, a production render pass, and a multimodal judge. One detail they flag as more important than it sounds: canonicalization in a control experiment recovered 26 of 28 wrongly rejected candidates and lifted schema-valid, renderable slides from 92 to 118 of 120, because format strictness is a poor proxy for visual quality. After deduplication and tripling the 1,989 hardest examples, the slide corpus holds 32,816 rows.

The HTML pipeline is production failure mining, which is a more interesting design choice. They exported 119,122 interactive self-generations from the incumbent model and executed each in an isolated Chromium probe. 117,309 completed, and 25,475, about 21.7 percent, exhibited hard failures: initialization crashes, missing interaction contracts, or fully unresponsive controls. They concentrated supervision exactly there. Gemini 3 Flash regenerated a complete page for each of the 24,937 resolvable failing requests, and every regeneration was re-executed under the same probe, 17,561 passing directly, 72.8 percent. Auditing the rejects exposed a systematic false positive in the original contract check, which only recognized slider-style controls, while valid simulations also use selects, checkboxes, and semantic handlers; a recovery pass re-admitted 4,412 examples. The usable corpus is 21,973, trimmed to 20,871 by a 16,384-token limit, since full pages are long with a median of 8,988 tokens. The final SFT mixture is 53,687 conversations: 32,816 slides plus 20,871 interactive pages, each a triple of system contract, user brief, and verified artifact.

The SFT stage has an important negative result. They find that SFT reliably teaches the two output contracts but cannot raise interactive quality. Under the pre-hardening reward, HTML quality declines monotonically with update count on the 27B: 88.4 at 6,710 updates, 83.7 at 10,711, and about 73.5 at 13,421, sitting below its own bare base of 78.3, having ceded ground precisely where the base was strongest, 7.0 points on code and 17.9 on games. So the HTML ceiling is left to the RL stage, and the base model's capability dominates the SFT ceiling: under an identical recipe, the Qwen3.8-27B base reaches 79.5 on slide standard versus 67.7 for the Qwen3.6-27B, with contract parse rates of 99.2 versus 85.8 percent.

The RL stage is where the central finding lives, and it comes with a cautionary tale worth telling in full. The slide RL stage uses a hybrid reward, 0.6 weight on VLM fidelity scored on rendered pixels plus 0.4 on geometric rules, and it lifts slide standard to 76.8 on the 4B and 84.8 on the 27B. The interactive-HTML RL is where things got interesting. The rebuilt judge first re-based all scores about 25 points downward, and under it the failure-mined data delivered real gains. Then the third run doubled down on the weakest type, games, giving them a third of the training batch, the largest share of any type. Games regressed by 12.1 points, the worst single-type collapse of the campaign, while every weighted non-game type gained. The authors diagnosed it: every component of the reward, visual quality, dual-viewport screenshots, content, judged static renderings. Nothing measured what actually makes a game, responding to input, enforcing rules, closing a feedback loop. A policy optimizing that reward on game prompts converges on exactly what they observed: pages whose opening frame screenshots beautifully and whose interaction is broken.

The fix was run as a clean A/B. They hardened the reward with an always-on interactivity probe plus a hard-fail gate, and retrained from the same checkpoint, same data, same schedule, with the reward as the only variable. Games reversed from minus 12.1 to plus 5.8 points, 3D rose 15.9 points, and overall HTML lifted from 54.2 to 61.7. The smoking gun: the 27B old-reward run, trained before hardening, had looked merely mediocre on games under the old judge, but re-scored under the hardened reward its game score is 18.8, a 36-point collapse that the screenshot judge had masked as only 9.7 points. Its non-game mean matches the hardened run exactly, so the old reward learned everything except playability and quietly unlearned that. The principle that survives is interactivity must be measured, not judged, and the probe is now a permanent component of both the reward and the benchmark gate.

The final numbers. CogEvol-27B, the production model, scores 83.7 on slide quality and 63.7 on the 500-case interactive-HTML benchmark, with games at 57.6, using 26.9 times fewer parameters than the flagship coding models it is benchmarked against, on the same suites under the identical harness. CogEvol-4B, the open Apache 2.0 release, reaches 61.7 on HTML-500, up from 52.8 at SFT, and 75.1 on slide standard, paying a 1.7-point forgetting tax. A systems result: scaffold editing cuts interactive-page generation cost by a further 76 percent, and the stack runs on domestic Ascend accelerators at application-level parity with A800 GPUs.

Now the skeptical read. First, and most important, the foundation-model framing is generous. This is a strong post-training pipeline on top of Qwen bases, and the base-model ablation is the honest core: under an identical recipe, base capability sets the ceiling, so a large share of the 27B's slide score is inherited from Qwen3.8-27B rather than created by CogEvol's training. If you are evaluating this as a capability you can reproduce, the transferable assets are the execution-aware data pipelines, the hybrid rule-plus-VLM reward, and the interactivity probe, not the 27B weights. Second, the headline 63.7 on interactive HTML is still a modest absolute number, and the reward-hacking episode is a warning that the metric is fragile: a screenshot-based judge masked a 36-point collapse in playability as a 9.7-point dip. The hardened probe fixes the known failure mode, but the same class of error, rewarding what renders well over what behaves well, can recur in a new modality. Third, the data is production-biased by construction: the HTML corpus is 69.8 percent simulations, 2.4 percent code, and contains no 3D examples, so the model is strongest where the incumbent already operated. Fourth, the 26.9-times-fewer-parameters claim is a cost comparison under an identical harness the authors control; I would want the harness and the flagships' exact configurations before treating the gap as robust. Fifth, the forgetting tax is small, 1.1 to 1.7 points, but nonzero, and it is paid in the modality not currently being trained, the standard cost of sequential multi-task RL.

If you implement this: the 4B weights and editing harness are open, and the recipe is a standard SFT-then-GRPO stack, so the barrier is the verification infrastructure, not the training code. Replicate the execution-aware data pipeline first, because it is what makes the supervision trustworthy, and the interactivity probe plus hard-fail gate second, because the central result is that a screenshot judge will happily reward broken games. I would also re-run the reward-hacking A/B on my own task, changing only the reward, before trusting any visual-quality judge on interactive output.

Bottom line: CogEvol is a credible, production-validated capability release for learning-environment generation, and its most transferable lesson is a methodological one, that for interactive artifacts you must probe behavior, not judge screenshots, or your reward will reward broken output that looks right. Treat the foundation-model framing as a post-training capability on Qwen bases, weight the reward-hacking episode as a caution about your own metrics, and evaluate the open 4B against your own briefs before assuming the production numbers transfer.
