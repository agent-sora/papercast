nanoMuse is from Guangyi Liu, Yong Liu, and Jiangning Zhang, all at Zhejiang University, with Jiangning Zhang as the corresponding author. This is a report rather than an empirical paper, and it is worth covering for what it positions rather than what it benchmarks. The claim is that a personal agent, an agent that acts for one person across that person's own accounts and devices over weeks, with memory, proactive follow-up, and an accountable log of what it did, is a real category of software, and until now the only implementations of it were closed, vendor-hosted products. The authors present nanoMuse as the open-source counterpart, released under GPL-3, with the agent running on every device the person owns rather than in a vendor's cloud.

The context they set up is a specific historical argument. Assistants like Siri answered and waited. ChatGPT agents did a task and stopped. And the screen-operating agents that came after, computer-use, GUI agents driving a phone or desktop through screenshots or an accessibility tree, all act for a task, none of them belongs to a person. The vendors then moved the agent into their own clouds: hosted browsers the user watches, a cloud computer per task. The report's point is that every one of these acts on behalf of a task, but none of them is a resident of a person's life, with persistent memory, the ability to speak first when it is worth it, and accountability for what it did. Meta's Muse, released in September 2026, is the first product to assemble those pieces for one person and to say so in its first sentence, and within three weeks other vendors shipped their own versions. The report reads how Muse is built from Meta's public record and a copy of its production prompt, marking each statement with its source, and then presents the open version.

The design of nanoMuse is organized around five questions and three horizons, which is their way of defining what a personal agent should be before they describe how to build one. The concrete architecture has a few distinctive pieces. There is one agent on every device a person owns, with hands on the phone's screen and the computer's, and these devices share one conversation over a relay that anyone can run, open source and optional, because a single device alone does not need a relay. Every action goes through a Sentinel, which is the accountability layer, the component that checks and logs what the agent does. Memory is files the person can read, rather than an opaque vector store, and the model is the person's choice rather than something the vendor picks for you. The screens are treated as drawings the agent renders, not screenshots it passively observes, which is a meaningful difference for how the agent reasons about what it is doing. The iPhone case is interesting because iOS lets no app operate another, so the phone gets everything but the hands, and it delegates actions to the other devices.

The three horizons are the other organizing axis, and they describe the kind of proactivity the agent is allowed to have. The first horizon is reactive, the agent answers when spoken to. The second is proactive, the agent speaks first when something is worth raising, a follow-up, a reminder, a change it noticed, and the report is careful to say this is the horizon where the accountability matters most, because an agent that initiates contact without being asked is the one most likely to do something the person did not intend. The third horizon is the one where the agent holds a standing responsibility, a task it is accountable for across days, and the ledger, the log of what it did and why, is what makes that horizon safe, because a person can audit a standing responsibility in a way they cannot audit a cloud that does a task and discards the trace.

There is a deliberate contrast throughout between the open version and the closed one it is modeled on, and it is worth spelling out because it is the report's implicit argument for why open matters here. A closed personal agent, hosted in the vendor's cloud, is accountable in the same way a cloud function is accountable, by the vendor's logs and the vendor's goodwill, and the person has no independent way to check what the agent did with their accounts or memory. The open version's accountability is structural, the memory is files the person can open, the ledger is on the person's own devices, and the relay anyone can run, so the audit does not depend on the vendor choosing to show you the trace. The report also gives rough size and cost figures for the model and the device footprint, which it flags as estimates, and its roadmap is explicit about what is not done yet: an open model for the hands, an evaluation suite for the hands, and open memory with provenance. That last one, provenance, is the piece I would track most, because a memory that can say where a fact came from is what separates an auditable personal agent from one that is just confidently persistent. The relay is also worth a second thought, because the report is right that a single device does not need one, but the moment a person has two devices, the relay becomes the coordination substrate, and a relay anyone can run means the person's entire cross-device conversation and action log transits a component whose correctness and availability the person has to stand up and maintain themselves, which is a real operational burden that the report, being a design document, does not price out.

A skeptical read. This is a design report and a roadmap, and it should be evaluated on the strength of the specification, not on numbers, because there are essentially no experimental results in it, the size and cost figures are given as estimates, and the authors are explicit that there is work still open, including an evaluation suite for the hands and an open model for them, that is not yet done. That honesty is a point in its favor, but it also means the core claims, that you can build a genuinely personal, accountable, cross-device agent in the open, are not yet demonstrated. The thing I would want to see before taking this seriously is the Sentinel, because accountability is the whole difference between a personal agent and an unattended auto-pilot, and a Sentinel that is just a log is not the same as a Sentinel that actually constrains or rolls back actions, and the report does not give enough detail to tell which it is. The second thing I would re-verify is the memory-as-files claim, because readable memory is a great accountability story, but the question is whether the agent can actually use that memory to act coherently over weeks, and a file store with no retrieval structure is easy to read and hard to reason over at scale. The third: this is a three-author effort from a single lab describing a system that spans phones, desktops, a relay, and a Sentinel, which is a lot of surface area, and I would want to see the parts actually shipped and working, not the architecture diagram, before concluding the open version matches the closed one it is modeled on.

Bottom line: nanoMuse is best read as a clear, sourced specification of what an open personal agent should be, and as a credible roadmap, rather than as a demonstrated system, because the evaluation, the hands model, and the Sentinel's actual enforcement are all still on the roadmap. If you are tracking the personal-agent category, the value here is the five-questions-and-three-horizons framing and the memory-as-files, Sentinel-gated design, and the value you should withhold is trust that the open build already delivers it.
