The paper is OpenGCUA: Toward a Fully Open Stack for Generalist Computer Use, from Hanzhang Zhou, Long Li, and Quyu Kong, out of Alibaba's Token Hub team. It is not a model release. It is a definition, a harness, and a set of experiments that argue the field should stop describing computer-use agents by the parts they contain and start describing them by the decisions their model makes at each step. The authors call such a system a generalist computer-use agent, or GCUA, and the central claim is that a GCUA makes three decisions at every step, and that almost every agent family we have built so far is just a GCUA with some of those decisions fixed in advance by the developer.

Those three decisions are what to observe, how to act, and how to organize. What to observe means the model chooses which view of the computer it needs at this step, which might be a screenshot, an accessibility tree, the output of a command, the response of an API, or simply nothing new at all. How to act means the model chooses which of four interfaces fits the step, the graphical interface where it clicks and drags at a screen coordinate, the accessibility tree where it operates on a named element without ever touching the user's pointer, the command line where it runs a shell command, or an external API. How to organize means the model keeps its own plan, tracks what has been done, and decides which past observations stay in context, instead of following a harness rule like keep the last three screenshots. The formalization is clean: at each step a policy jointly emits the set of views it wants, a program whose statements draw on all four interfaces and may use loops, branches, and variables, and an updated working state. The next observation is then the program's printed output plus whatever views it asked for.

The nice part of this definition is that it swallows everything we already have. A pure GUI agent fixes all three decisions, it always looks at a screenshot, takes one graphical action per step, and follows a harness rule for context. A command-line agent fixes what it observes to just command output and restricts how it acts to the shell. A multi-agent hybrid fixes the interface for each subagent in advance and lets an orchestrator pick per subtask. Even the authors' own earlier GUI-plus-CLI agent, which emits a batch of mixed graphical and shell actions per call, is a restricted GCUA where the view is always a screenshot and the context follows a fixed rule. GCUA lifts each of those constraints and lets one model make all three decisions at every step. That is a genuinely tidy unification, and it does the job that the five-layer brain-eyes-body-hands-feet taxonomy from the agent evaluation literature could not, because a model can have all five layers and still be bad at choosing between them.

The reason this matters right now, and the authors make the case, is that the frontier is visibly shifting from clicking toward programming, and it shows up in vendor documentation. With the release of GPT-6 Astra, OpenAI's computer-use guide started recommending that models write and run short programs with PyAutoGUI or Playwright instead of leaning on the mouse-and-keyboard tool, and the code-execution examples use the new model while the computer tool still targets the older one. The authors contrast code execution with batched actions, which is the stepping stone our earlier GUI-plus-CLI work introduced. A batch is a program without control flow, because every action was fixed when the call was generated, so the model has to commit to every click before it sees the result of the first. A program, by contrast, decides its control flow while it runs, and that unlocks a conditional, a loop, and a verification all inside a single model call. A task that took a dozen round trips becomes one.

The harness, called OpenGCUA, gives existing models two things. The first is code execution over the GUI and the command line, implemented as a Python runtime where a PyAutoGUI call and a bash function are just two kinds of statements in the same program, so intermediate results can decide the next operation without another model call and the model can bring its existing programming skill directly to computer interaction. The second is what they call harness-to-model decision transfer, where workflow decisions that a harness normally fixes by rule, like taking a screenshot after every step, are delegated to the model. In the current implementation the model decides when to request screenshots and how to track task state, and it states each program's purpose before executing it.

The evaluation is on the offline set of OSWorld-v2, and they run eight frontier models including GPT-6 Astra and Claude Opus 5. They measure efficiency as a first-class metric, with four numbers per task: steps, which counts model calls, output tokens, reasoning tokens reported separately, and dollar cost at each model's published prices including cache discounts. The headline result is that the full GCUA design raises the mean partial score by 19.6 points and cuts steps per task by 53 percent compared to a batched GUI-only baseline, and all eight models improve, and the score gap between the strongest and weakest models narrows by more than half. They decompose the gain. Code execution on top of the GUI-plus-CLI baseline adds 6.1 points and cuts steps per task by another 14.8 percent. On-demand observation alone, letting the model decide when to look, raises prompt-cache hit rates by 10.5 and 14.4 percentage points for two models without lowering task scores. On the real-device harness, which they release only in preliminary form and which has to share the machine with its human user and act on background windows, they hold the harness fixed and find that Qwen3.8-Max uses 19.4 times as many reasoning tokens as GPT-6 Astra on four macOS tasks, and 5.7 times as many output tokens in total, and they trace that gap to model behavior rather than the harness, heavy reasoning for simple operations, difficulty adapting to real-device conditions, and a gap in code-execution capability.

What I would trust here is the framing and the direction. The three-decision definition is the right lens, it unifies the existing families without hand-waving, and the empirical evidence that code execution and on-demand observation both help, for every model they tested, is the kind of result you can build on. Releasing the prompts, the harness, and the full evaluation trajectories for eight frontier models makes this reproducible in a way that most systems papers are not, and the real-device case studies are honest about where the remaining gap is.

What I would re-verify before treating the numbers as settled. The main gain is measured in mean partial score on a curated offline benchmark, and partial score can flatter a method that makes progress on tasks it does not fully finish, so I would want the per-model success-rate breakdown. The 19.4 times token ratio is striking but comes from a single run per model on four tasks, which is far too little to attribute that gap to the model with confidence. And the real-device harness is explicitly preliminary, with the actual GCUA model still planned for a later release, so this is a foundation and a set of measurements, not the finished product it is named for.

Two-sentence verdict: OpenGCUA gives computer-use agents a clean, decision-based definition and shows, across eight frontier models, that letting the model write programs and choose what to look at is worth real gains in score and efficiency, which is strong evidence that code execution is becoming the primary interface to the computer. It is a harness and an evaluation, not a model, so read it as a well-motivated blueprint with reproducible artifacts rather than a complete system.
