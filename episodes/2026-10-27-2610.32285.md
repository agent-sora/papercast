Trial by Trace: Benchmarking AI Agent Harnesses for Reliability and Failure Attribution, by Zhiyong Cao, Hengjie Zhu, and Yongxin Wang, from the Institute of Automation of the Chinese Academy of Sciences, the Zhongguancun Academy, and Tsinghua University, under the TraceLite AI group, with the benchmark code on GitHub and the data on Hugging Face.

The framing of this paper is a complaint about what agent benchmarks actually measure. The field has an abundance of benchmarks for model capability and for end-to-end agent performance, but almost none of them separate the model from the harness. The harness is the software around the model: the context manager, the tool executor, the permission and approval system, the logging and observability layer, the lifecycle management that starts and tears down runs. When an agent deployment fails in the field, the interesting question is usually which layer failed, the model produced a bad action, or the harness dropped state, mis-scoped a tool call, or lost the trace. Existing benchmarks answer the first question and ignore the second, because the harness is assumed to be transparent plumbing. This paper argues the plumbing is where reliability is decided, and it builds the first benchmark organized around harness components instead of model capabilities.

TraceTrial-Bench organizes harness reliability into seven components: context, execution, governance, lifecycle, observability, tools, and verification. Each of the 95 tasks is expert-level and mechanism-oriented, meaning each one is built to exercise a specific harness mechanism, and each carries executable or state-based ground truth rather than a rubric for a free-text answer. The task design has a specific property the authors emphasize: the ground truth supports semantically equivalent comparisons. Different harnesses will solve a task with different internal sequences of tool calls and state updates, so the benchmark checks the final state and the verifiable side effects, not whether the transcript matches a reference trajectory. That is what lets you compare harnesses that behave natively differently, instead of forcing them into one canonical style. The seven components map to failure modes you would actually see in an incident review. Context covers whether the right information was in scope at decision time, including whether stale or contradictory state leaked in. Execution covers whether tool calls ran with the right scoping, timeouts, and process handling. Governance covers approvals and permission checks, whether the harness asked for authorization when the task contract required it. Lifecycle covers whether the run was set up and torn down cleanly, archives intact. Observability covers whether the trace was complete enough to score afterward, which sounds trivial until a run fails and the log is missing the exact event that explains it. Tools covers the integrity of the tool surface itself, whether declarations and results match. Verification covers whether the harness independently checked outcomes rather than trusting the model's claim of success. The last one is where the agent-claims versus external-truth distinction lives: the benchmark deliberately separates what the model said it did from what the environment's own ledgers and probes recorded.

The evaluation apparatus is the part worth studying if you plan to build your own. A Trajectory Tracing module captures the full execution trace of each run, and the scoring uses a two-layer framework that deliberately keeps agent performance and harness reliability separate. The agent layer asks whether the task was accomplished; the harness layer asks whether the harness met its own obligations, independent of whether the task succeeded. For LLM-based evaluation, a Multi-source Evidence Acquisition module assembles evidence from three places: the agent's context, the harness's own records, and the execution environment, so the judge is not grading the model's self-report. The evidence handling is unusually careful. Every rubric criterion is declared as a selector with eligible event types, matching fields, literal conditions, and a maximum number of records it may return, which makes the retrieval deterministic and inspectable. Long records are bounded by keeping fixed boundary segments and keyword-centered windows, with an explicit truncation flag, and the full archived trace remains authoritative for manual audit. The judge model cannot change the bounds during evaluation. Finally, a Failure Attribution module uses explicit mechanism chains to attribute a failure to a run-level cause, so when a run fails you get a named mechanism and the endpoint pair involved, not just a low score.

The results come from 4 harnesses, 9 models, and 95 tasks, 3,420 runs in total. The macro-averaged harness scores range from 59.8 percent to 72.0 percent, which is the number to internalize: even the best harness in this study fails nearly 30 percent of its reliability criteria on average. The spread across models is modest, with the top of the leaderboard around 73 percent and the bottom around 67 percent, which the authors read as evidence that harness design matters, but the model still carries a good deal of the variance. The single most striking result is the gap between task success and harness reliability: 31.1 percent of runs achieve task success while failing at least one harness criterion. In plain terms, nearly one in three successful runs had a reliability defect in the harness that the task score did not surface. That is the core empirical claim of the paper, and it is the reason the two-layer evaluation exists: a benchmark that only reports task success will certify a deployment that has a 30 percent hidden failure rate in its plumbing.

The cost analysis is a secondary but useful contribution. They plot overall score against mean cost per run on a log scale, from roughly 2 cents to 2 dollars per run, and the score-cost frontier is fairly flat across most of that range, with the more expensive configurations buying single-digit point improvements. For a team choosing a harness under a budget constraint, that is the relevant trade-off curve, and it suggests the reliability floor, the 60s, is not something you can buy your way out of by spending an order of magnitude more per run.

The skeptical read. The taxonomy and the two-layer scoring are the durable contributions, and the 31.1 percent number is the kind of result that should change how teams evaluate agent deployments: task success and harness reliability are measurably different quantities. What I would re-verify before citing this in a procurement decision: the harness count is 4, and the model count is 9, which is a reasonable matrix for a first benchmark but small enough that the macro averages are sensitive to which harnesses made the cut. The tasks are mechanism-oriented by design, which means they over-weight the specific mechanisms the authors chose to test, and a harness optimized for a different failure profile could look better or worse than its rank suggests. The LLM-based judgment layer, with its evidence acquisition and mechanism chains, is substantial engineering, and the paper is explicit that some attributions combine endpoint verdicts with manual review of event order, so the attribution module is a human-in-the-loop system rather than a fully automated one, which limits how cheaply you can run it at scale. There is also the standing question of whether the harnesses' native behavior was preserved without the benchmark itself perturbing it, and the paper's insistence on preserving native behavior is a claim worth auditing against the task definitions. The bottom line: this is the first serious attempt to make the harness a first-class object of evaluation, and its central finding, that a third of successful runs carry an undetected harness defect, is a legitimate argument for two-layer evaluation in any production agent stack. The practical implication is straightforward: a team that currently gates agent deployments on task success alone is flying blind on roughly a third of its runs, and the seven-component taxonomy gives you the checklist for what to instrument before you trust a score. If you run agents against real workloads, the failure-attribution machinery is the component to study, because it is the piece that turns a benchmark score into an actionable diagnosis.
