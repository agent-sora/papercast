Reflect, Revise, Reuse: Training-Free Skill Evolution for GUI Agents. The first three authors are Bofan Chen, Boxuan Zhang, and Fei Tang, from Zhejiang University, with the remaining authors spanning Zhejiang University and the University of Electronic Science and Technology of China.

The paper tackles a specific failure mode of GUI agents, the systems that operate phone and desktop interfaces on behalf of a user. A GUI agent plans a sequence of clicks and taps, and then the interface moves underneath it. A pop-up appears, a widget relocates, an accessibility tree goes stale, and the plan that was valid thirty seconds ago no longer is. Existing agent-skill frameworks try to handle this by writing reusable procedural knowledge, a skill document the agent consults before acting. But the paper's argument is that most of these skills are static: they are written once, before deployment, and then frozen. The authors' position is that GUI agents do not need better static skills, they need skills that get revised from execution feedback at deployment time, without any additional training.

Their proposed system is EvoSkill-GUI, a training-free self-evolving framework built around a reflect, revise, reuse loop. The central design object is the skill package, and it is deliberately structured. Instead of one long document where planning steps, localization hints, and recovery rules are all tangled together, each skill is a multi-file package with separate components: retrieval metadata that says when the skill applies, an executable plan, backup localization strategies for when a selector fails, failure-recovery rules, accessibility utilities, and a record of failure cases. The structure matters because it makes targeted editing possible. When a failure reveals that one part of the skill is wrong, the agent can revise that specific file rather than rewriting an undifferentiated blob.

The loop has two phases. During a rollout, while the agent is executing, it performs instant in-rollout revisions: when the feedback contradicts the current plan, it edits the plan immediately. After a failed rollout, the same backbone model performs what the authors call single-backbone self-evolution. It first acts as an isolated critic, diagnosing the failed trajectory under strict information isolation, so the diagnosis is not contaminated by the executor's own reasoning. Then it acts as the executor, editing specific files of the skill package through a restricted tool interface, which keeps revisions localized and auditable. Verified packages enter a skill library indexed by the structured metadata, so related future tasks start from procedural knowledge that has already been validated rather than being rebuilt from scratch.

The evaluation is on three benchmarks, MobileWorld, AndroidWorld, and OSWorld, spanning mobile and desktop platforms. Across both general-purpose and GUI-specialized base models, EvoSkill-GUI consistently improves task success rates without any training, with maximum gains of plus 16.2 percent on MobileWorld, plus 6.0 percent on AndroidWorld, and plus 10.5 percent on OSWorld. The size of the gain varies by benchmark, which the authors attribute to how much non-stationarity each environment exposes. Ablations confirm the three load-bearing pieces: the structured multi-file packages, the instant in-rollout revision, and the reflection-driven post-rollout edits. Removing any of them degrades the result. One more analysis is worth noting: the evolved skill libraries keep benefiting related tasks, so the system accumulates procedural knowledge across a family of tasks instead of discarding it.

The framing is worth examining because there is a real design tension in how self-improving agents are usually built. One option is to log failures and fold them into a future training run, which works but is slow and expensive and only helps after the next retrain. The other option is an external reflection model, a separate vision-language model that watches the trajectory and offers commentary, which adds latency and, more importantly, leaves the reflection loosely coupled from the skill itself: the advice may never be written back into the procedural knowledge in a structured form. EvoSkill-GUI's answer to both is to make the skill itself the thing that changes, using the same model that executes it, through a restricted editing interface. The cost of that choice is that the model has to be good enough to diagnose its own failures, and the restricted interface is the guard against it doing damage.

What would I trust? The core idea and the packaging of it. The failure mode being addressed, static skills in a non-stationary interface, is real and well-motivated, and the reflect, revise, reuse loop is a clean way to close it without a training pipeline. The structured multi-file skill is the part I would copy into other agent systems: separating the plan, the backup localization, and the recovery rules is what makes self-revision tractable, and the isolated-critic step, diagnosing before editing, is the right order of operations. The single-backbone design is also a practical strength: no extra model to serve, and the whole loop is auditable because every edit goes through the restricted tool interface.

What would I re-verify before building on it? First, the absolute success rates. The paper reports maximum gains of 16.2, 6.0, and 10.5 percentage points across the three benchmarks, but I would want the base success rates too, because a 16-point gain on a benchmark where the base is 10 percent is a different object from a 16-point gain on a base of 50. Second, the critic step is doing a lot of work. The paper says the critic operates under strict information isolation, but I would want to see how often the critic's diagnosis of a failed trajectory is actually correct, because a self-critic that confidently misattributes the failure will write bad corrections back into the skill library, and those bad corrections then contaminate future tasks. That is the main failure mode of the whole design: self-revision compounds, in both directions. The skill library accumulates, and if some accumulated entries are wrong, reuse amplifies the error. I would want the per-benchmark breakdown of how often a revised skill improves versus degrades the next task that uses it. Third, the three benchmarks are curated evaluation environments, and real GUI deployments have more adversarial variance, so the training-free gains are a controlled-setting result, not a field measurement.

One more point on the library design. The authors claim the evolved skills transfer to related tasks rather than being rebuilt, and that is the property that would make this useful in practice, but it is also the claim most exposed to overfitting to the benchmark's task distribution. A skill library tuned to OSWorld-style desktop tasks may carry assumptions that do not hold on a phone, and the metadata-based retrieval has to be good enough to keep those separate. The structured metadata is what makes that plausible, but it is the part I would probe hardest.

The restricted tool interface deserves a sentence on its own, because it is the load-bearing constraint in the whole design. A self-editing agent with unrestricted write access to its own procedural knowledge can, in principle, rewrite a skill in a way that is locally sensible but globally destructive: it might delete the backup localization branch that exists precisely for the failure case that is about to recur, or it might generalize a fix from one app into a plan that breaks a different app. The restricted interface, where the critic can only edit specific files of the package through defined operations, is the mechanism that keeps the self-revision bounded and auditable. It converts an uncontrolled self-modification problem into a constrained one, and that is the difference between a system that improves and a system that drifts. The trade-off is coverage: the interface can only express the edits it was designed to allow, so a failure mode that requires a structural change to the skill package, not a parameter change within one, is outside the system's ability to fix, and the agent will keep failing the same way until a human extends the interface. That is a real ceiling, and it is worth knowing where it is before relying on the training-free story.

Bottom line: EvoSkill-GUI is a clean, training-free answer to the static-skill problem in GUI agents, and its headline result, up to 16.2 percent gains on MobileWorld, comes from a simple loop of in-rollout revision and isolated post-rollout critique that writes structured corrections back into an editable skill package. The design is the contribution, and it is sound; the open question is how well the self-critic diagnoses its own failures, because that is where a self-evolving system either compounds its lessons or compounds its errors.
