The paper is called "Flide: Accelerating Decision Inference with Exact State Forking." The first three authors are Bobo Li, Jiajia Song, and Hao Fei, working at the National University of Singapore, with Hao Fei at the University of Oxford.

The context for this paper is a workload that standard inference engines handle badly. Decision models, of which Jev is the example the paper uses throughout, are small models built for categorical reasoning: given a state, they score a set of options or answer a batch of yes-no and scoring questions in one pass. They sit in agent systems as the fast, reliable System One component, making rapid decisions while a larger model handles the slow reasoning. The problem is that the request structure is a tree. A single decision request fans out over many options, and the natural way to serve it is to share the computed prefix across the branches, but existing generation-oriented engines like vLLM and SGLang were built for linear sequences, not for tree-structured requests over shared prefixes. The result is either severe prefix recomputation, where each branch pays for the whole prefix again, or multi-item scoring tricks that batch the branches together but distort the output probabilities, because the attention pattern of a flattened batch is not the attention pattern of the tree.

Flide's core move is to decouple the logical structure of the request from its physical execution. The whole tree is flattened into a single token stream, and the branching is encoded as GPU-resident metadata. That metadata is what they call ForkAttention: indices that tell the attention computation, for each query token, which prefix and which branch siblings it can see, so that the flattened execution is exactly equivalent to running each branch as an isolated forward pass. The paper is careful to emphasize that this is exact in arithmetic, not an approximation: every query branch evaluates identically to the standalone pass it is standing in for. That is a stronger claim than the usual batching paper makes, and it is the reason the comparison to multi-item scoring is framed in terms of distance to a float32 reference rather than just speed.

The second architectural point is that Flide handles hybrid models, which is where the interesting engineering lives. The decision models it targets mix standard attention with recurrent layers, specifically Gated DeltaNet layers, which maintain a running state instead of a full key-value cache. Forking a tree over a recurrent state is genuinely harder than forking over attention, because attention is stateless with respect to the past, just a matter of which tokens are visible, while a recurrent state is a single vector that each branch has diverged into. Flide solves this with exact state forking: the recurrent state at each fork point is saved as a checkpoint, and branches resume from the saved state, so the physical execution never recomputes the trunk of the tree. The state checkpoints also give you a second capability for free: as an agent's history grows across turns, new requests can resume from checkpoints saved in earlier passes rather than reprocessing the entire history.

It is worth pausing on why the tree structure is the crux, because it explains where the speedup comes from. In a generation engine, a shared prefix is usually handled by a prefix cache keyed on the token sequence, which works for linear requests where one continuation follows another. A decision tree is not linear: the branches diverge, and a flattened batch of branch sequences either recomputes the trunk for each branch because the cache key stops matching, or it packs the branches into one sequence and changes the attention each query can see, which is what distorts the probabilities in multi-item scoring. Flide's flat stream plus fork metadata sidesteps both failure modes: the trunk is computed once in the stream, the metadata routes attention so each branch query sees exactly the tokens its isolated pass would see, and the recurrent checkpoint saves the state at the fork point so the recurrent layers never reprocess the trunk either. That is why the per-round cost is one flat-graph replay regardless of how many branches are in the tree, and it is the mechanism behind the headline throughput numbers.

The evaluation is against vLLM and SGLang through their standard endpoints, against SGLang's multi-item scoring mode, and against a purpose-built engine for these models, vllm-jev, including its RadixFlow scheduler. The workloads are public hybrid and decision models, and the request structure is realistic for the use case: at most 26 options per choice question, 10 levels per scoring question, and up to 64 questions per request.

The headline result is throughput: Flide answers queries up to 9.5 times faster than vLLM and SGLang on these workloads. On the dedicated engine comparison, it completes 4.4 to 7.2 times the steps per second of the strongest baseline, and on the smallest model the gain is up to 3.2 times over the best vllm-jev configuration. The gain comes from one flat-graph replay per decision round, instead of the per-branch recomputation the alternatives pay. The latency curves show Flide serving more requests at lower median latency across 1, 8, 32, and 64 closed-loop clients.

The accuracy side of the story is what I would weight heavily. Flide's outputs stay closest to the float32 reference in total variation distance across the workloads, and its accuracy stays within 1.2 points of vLLM's on the task metrics. That combination is the actual selling point: it is the fast engine that is also the one that matches the reference best, while the multi-item scoring baselines trade probability fidelity for speed. On workloads where a state carries many questions, which is exactly the decision-model regime, Flide leads most strongly, which is the regime its design targets.

Now the skeptical read. The first caveat is scope: the evaluation is on public hybrid and decision models, and the request structure, while realistic for the stated use case, is bounded at 26 options and 64 questions per request. Decision-model serving at larger fan-out, where the tree gets wide enough that the metadata and state checkpoints themselves become memory pressure, is not covered, and forking recurrent state at scale is where the engineering cost would actually show up. The paper reports latency and throughput but the memory profile of the saved state checkpoints across a deep agent history is the number I would want before adopting this in production.

Second, the exactness claim is arithmetic exactness relative to the same model's own forward pass, and that is the right claim, but the float32 reference comparison cuts both ways: all of these engines are running the same approximate model, and the total variation distance to float32 measures how faithfully the engine preserves the model, not how good the model's decisions are. The within-1.2-points result says the speed is not bought with accuracy, which is the important thing, but the decision quality itself is out of scope for this paper.

Third, the ecosystem here is young. The decision-model paradigm, the Jev line of models, and the vllm-jev engine are all recent, and a 9.5 times speedup over today's baselines may look smaller or larger depending on how fast the generation engines add native tree support. The durable contribution is the pattern: flatten the logical tree, encode the topology as GPU metadata, fork the recurrent state exactly, and you get exact execution without prefix recomputation. That pattern generalizes beyond decision models to any serving regime where requests share prefixes and the model carries recurrent state, which is a widening class as hybrid architectures become common.

The bottom line: Flide is a tight systems paper that solves a real and currently underserved workload, giving tree-structured decision requests exact, checkpoint-resumable execution on hybrid models with up to a 9.5 times throughput gain over the general-purpose engines while staying closest to the float32 reference. The honest limits are the bounded request structure in the evaluation, the missing memory accounting for deep state histories, and the fact that the baseline engines are early. If you are building agent systems with fast categorical decision models in the loop, this is the paper to read, and the state-forking pattern is the idea worth stealing even if you never use the engine itself.
