CodeMidas: Scaling Agentic Coding RL Environments from Code Itself. The first three authors are Bowen Ye, Lei Li, and Shicheng Li, from Xiaomi's LLM Core team, with the remaining authors spread across Peking University, the University of Hong Kong, and Renmin University of China.

Reinforcement learning for coding agents has two requirements that are easy to state and hard to satisfy: diverse tasks, so the policy generalizes, and reliable reward signals, so the reinforced work is actually correct. Most existing pipelines build RL environments from development artifacts, issues, pull requests, commits, existing tests, or documentation. That works, but it ties the supply of tasks to the coverage of recorded changes, tests, and docs, which caps how far the environment can scale. The proposal here is to use the source code itself as the only task-specific input. Implemented functionality is both the basis of a task and a candidate solution: its public interfaces define what an agent should implement, executing the original code gives you the expected behavior for building tests, and the surrounding codebase becomes a realistic development starting point. The pipeline, CodeMidas, turns that idea into 5,545 training tasks from 3,185 open-source codebases, spanning 23 programming languages and 15 technical domains. Python, TypeScript, and Go are the most represented languages at 21.4, 18.3, and 16.2 percent respectively, and systems software, web technologies, and developer tools are the largest domains. The reference patches are nontrivial: the median solution is 142 lines of added or removed source, with an interquartile range of 66 to 305.

The pipeline allocates agentic compute to every construction stage. Agents explore the implemented functionality to formulate a behavioral specification: what the feature does, stated as requirements, while leaving internal implementation choices open. That matters, because a task statement that pins down the implementation invites the trivial solution of copying it. Then agents construct tests grounded in execution of the original code, checking that the generated tests enforce the stated requirements, reject incorrect solutions, and still accept alternative correct implementations. Finally, candidate tasks are validated and filtered through execution checks and repeated solution rollouts. The filtering stage has three mechanisms: adversarial rollouts that probe for exploitable leakage, solution reviews that assess whether the verifier's accept-or-reject decisions match the stated requirements, and rollout success rates that guide which tasks survive.

The training experiments use MiMo-V2.5, trained on these tasks with GRPO, with binary execution rewards, a batch size of 32, and 32 rollouts per task. The evaluation uses each benchmark's official task set, with identical settings for the initial policy and the RL checkpoints, and the paper reports absolute improvements in percentage points. The five external benchmarks all improve. SWE-bench Pro rises from 50.3 to 54.4, a gain of 4.1 points. DeepSWE pass rate rises from 10.0 percent to 21.7 percent, a gain of 11.7 points on issue repair. ProgramBench, which measures whole-program construction, sees its Almost Solved score jump from 4.5 to 21.5, a gain of 17 points, the largest absolute improvement in the table. RepoZero C2Rust, a code translation benchmark from C to Rust, rises from 40.5 to 51.8, a gain of 11.3 points. Terminal-Bench version 2.1 pass rate rises from 63.7 percent for the initial policy to 72.2 percent after RL, an 8.5 point gain on terminal work. The paper verifies that the training set is disjoint from all five external benchmark task sets and from its own 200-task validation split, CodeMidas Val, on which pass rate climbs from 35.0 to 44.7 during training.

Two ablations carry the paper's scaling argument. First, task count and quality: increasing the high-quality task set from 1,000 to 3,000 to the full 5,545 yields progressively higher scores on SWE-bench Pro, DeepSWE, and the CodeMidas validation set, with the full dataset leading at later checkpoints. The striking comparison is that the 3,000-task filtered subset beats an 8,000-task baseline constructed without the cleaning and filtering on all three, so quality of the environment matters more than raw volume. The vanilla 8,000 sample is a meaningful control: it is a real sample of tasks with statements, environments, and verifiers, just one that skipped the environment scrubbing, the execution-consistency checks, and the three post-rollout filters, which isolates the contribution of the filtering machinery rather than the contribution of having tasks at all. Second, behavior: trajectory analysis shows that as RL progresses, the agent explores the codebase more before writing code and performs more varied self-verification, and the agent-written checks are associated with higher success rates. The authors note these behavioral changes also appear on external tasks, which they read as behavioral evidence of generalization that complements the benchmark numbers.

The skeptical read. The construction detail is where this paper is worth reading line by line, and it explains why the gains are credible. The environment preparation stage removes anything that could leak the answer: compiled outputs, cached copies, files left behind by the construction agents, and the original tests for the target functionality, all scrubbed from a fresh base container. Then each task is execution-checked in six fresh containers, two with the starting codebase and four with the reference solution, and both starting runs must fail while all four reference runs must pass, which screens out unstable or already-solved tasks. On top of that sit the three post-rollout filters, and the leakage filter in particular is the right paranoia: an adversarial agent is pointed at the solver-visible environment, including installed copies of the project, and any task where leaked material can bypass the intended implementation work gets rejected. That is the difference between an RL environment that measures capability and one that measures the agent's ability to find the answer in a build artifact. The dataset statistics are also honest: the median reference patch is 142 lines, touching at least two files in 66 percent of tasks, and the top three languages, Python at 21.4 percent, TypeScript at 18.3, and Go at 16.2, cover most of the set.

The caveats. First, the whole pipeline is agentic at every stage, which means construction quality is bounded by the same frontier models doing the specifying, test-writing, and reviewing, and the paper does not report how often the behavioral specifications themselves were wrong, only that the filters remove downstream symptoms like verifier disagreement. Second, the 3,000-versus-8,000 comparison is the load-bearing result for the "quality over quantity" claim, but it is also the result most sensitive to how the vanilla 8k sample was drawn, and the filtered pipeline's advantage could shrink if the unfiltered sample were cleaned by even a fraction of the same machinery. Third, the benchmark gains are real but modest in absolute terms, with SWE-bench Pro moving 4.1 points and Terminal-Bench moving 8.5, so this is an environment-contribution paper more than a capability breakthrough, and the interesting claim is that source code is a nearly unlimited supply of such tasks, not that this recipe alone closes the gap. Fourth, training MiMo-V2.5 with 32 rollouts per task across 5,545 tasks is a serious compute budget, and the paper's ablations measure score deltas, not the cost of reaching them.

Bottom line: this is one of the most carefully engineered RL environment pipelines I have seen, and the six-container fail-to-pass check plus adversarial leakage filtering are patterns worth copying into any execution-based RL setup. The honest read is that it validates source code as a scalable substrate for coding RL tasks, with moderate but consistent gains across five benchmarks, and the biggest open question is how much of the quality advantage comes from the filters versus the specific frontier models running them. If you replicate it, the first experiment worth running is swapping one construction stage, the spec writer or the test generator, to a smaller model, to find out where the quality actually lives.
