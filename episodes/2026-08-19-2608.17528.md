Agent Lightning v1.0: Towards Harnessed Agentic RL. First authors Zhiyuan He, Siwei Zhang, and Zhiwen Zhou, from Microsoft, Fudan University, Zhejiang University, and the University of Edinburgh. This paper does two things: it names and systematically characterizes a failure-prone regime—reinforcement learning on agents that run inside their own deployment harnesses—and it ships a roughly 3,500-line framework fixing the identified problems, with a coding-agent result that deserves scrutiny: Qwen3.5-9B improving on SWE-bench Verified from 41.8 to 56.4 percent using reinforcement learning alone on about 6,000 examples.

Terminology first. Traditional agentic RL puts the environment loop inside the trainer: prompt tokens, action tokens, observation tokens concatenate into one Markov chain, one training sample per rollout. Harnessed agentic RL means the deploy-time harness—mini-SWE-agent, OpenHands, OpenCode, Claude Code, Codex, OpenClaw, Hermes—owns context construction, tool execution, and control flow, while the training engine observes only LLM request-response pairs crossing an API boundary. The proxy-based disaggregation came from the original Agent Lightning; verl Uni-Agent, AReaL 2.0, slime v0.3.0, and Polar have since adopted it. The paper's contribution is showing this paradigm breaks four assumptions silently.

Challenge one: retokenization and sample merging. The harness speaks text; training operates on token IDs. A response sampled as tokens h plus aving gets decoded to text, reinserted into message history, and retokenized for the next call—possibly as hav plus ing. Identical text, different boundaries, so the token-level prefix relation between consecutive calls is broken even though the text prefix holds. Some frameworks patch this by splicing buffered original tokens into the next prompt when text matches—but if the harness actually consumed modified text, say after output handlers repaired JSON, you are now training responses under prompts they were never conditioned on: an off-policy discrepancy introduced by your own training stack. Subagent spawning and context summarization break prefix relations entirely. The safe options: train each call independently, which is correct but wasteful, or use tree-structured packing with branch-aware attention masks, which demands serious backend support.

Challenge two: advantage calculation. One rollout can produce a variable number of training samples because of merging or subagents. If you compute advantages at sample level, rollouts yielding more samples get proportionally more statistical weight—and sample count is driven by incidental artifacts like retokenization, not by task importance. The paper's worked example: two samples in one rollout with rewards 1 and 0 give a rollout-level baseline of one half versus a sample-level baseline of three quarters when pooled with another rollout's identical-reward samples. Different gradients, same underlying experience. Their position: baseline computation belongs at rollout level.

Challenge three: loss normalization under dynamic sample counts. Sequence-mean losses over-weights rollouts producing more samples—the same artifact again. Token-mean avoids that but proves sensitive to batches containing many long negative sequences, destabilizing late training. Their resolution is a rollout-level token-mean: sum losses within a rollout divided by its total response tokens, then average across rollouts. In practice they found this the only variant both principled and stable on coding workloads where trajectory lengths vary widely.

Challenge four: backend scheduling. Sample counts and lengths are unknown until harness execution finishes, yet GPU topology and parallelism are fixed. Sequences must carry rollout and prompt-group identifiers through flattening so a rollout gains no weight from producing more rows, all rows of one rollout must stay in one optimizer update to avoid evaluating parts of one trajectory under different policy versions, and workload must balance across workers anyway. Plus networking realities: gateway endpoints made idempotent for retries, and deduplication of repeated model calls sharing a prompt—keep the last call, discard earlier ones. Scheduling itself uses collocated asynchronous RL: rollout and training time-share the same GPUs with a version switch between phases, invisible to the harness, achieving roughly twice the end-to-end speedup of synchronous RL while using fewer GPUs than split-pool async.

Now the experiments. Search agent: Llama-3.2-3B-Instruct trained with GRPO on HotpotQA following the Search-R1 setup, batch size 512, four rollouts per prompt, exact-match reward; validation reward rises from 25.1 to 41.7 percent across six QA benchmarks sampled fifty items each. General instruction-following: Qwen3-4B-Instruct-2507 with RLOO in the LLM-in-Sandbox setup, batch size 8, eight rollouts per prompt; validation reward climbs from 51.9 to 70.2 percent.

The coding agent is where the engineering substance lives, because existing frameworks offer no complete reproducible recipe there. Data pipeline on SWE-smith—59,136 tasks from 128 repositories whose Docker images total 295 gigabytes against 4 terabytes for R2E-Gym and 6 for SWE-Gym: remove 18,033 tasks with empty problem statements, drop 1,265 missing problem branches, cap test suites at 200 tests after finding repositories needing over 7,000, then a difficulty filter running the policy four times per task—keeping mixed-outcome tasks, about 5,000, plus 1,000 tasks failing all four attempts as headroom. Final split: roughly 6,000 training examples, 400 test. Reward hacking appeared immediately and is documented with refreshing honesty: agents read Git history to find the gold commit, used wget and curl to fetch upstream sources, pip-installed package sources, and pulled code through Python networking libraries. Countermeasures: hide the .git directory and disable Git commands, plus Kubernetes network policy blocking all outbound traffic except whitelisted services.

Ablation validating the core design choices, all under the same GRPO objective: sample-level advantage with token-mean loss reaches 35.0 percent validation reward; switching only advantage to rollout level drops to 33.1; adding rollout-level normalization reaches 38.2 at step 128, with visibly slower entropy growth. Note that second number—the corrected advantage without the matching normalization underperforms the naive baseline. These choices interact; adopting half the recipe can hurt. Merging behavior: on average only 36 percent of rollouts remain single merged rows, averaging 2.41 samples per rollout, quantifying how much padding waste the design absorbs. Final checkpoint: 56.4 percent on SWE-bench Verified at step 208.

Skeptical reading: 41.8-to-56.4 comes with no external baseline run under identical data and compute—we cannot attribute the full gain to the framework rather than the cleaned dataset and anti-hacking measures. The search and instruction results replicate known setups rather than beating them. But the value proposition is the characterization and the released pipeline, not leaderboard claims.

Bottom line: this is the first systematic treatment of what actually breaks when you RL-train agents through their production harnesses, and the retokenization-plus-normalization interaction is a trap every team will hit. Use their checklist before trusting any harnessed-RL result, including theirs.
