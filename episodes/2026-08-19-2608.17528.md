Agent Lightning v1.0: Towards Harnessed Agentic RL. First authors Zhiyuan He, Siwei Zhang, and Zhiwen Zhou, from Microsoft, Fudan University, Zhejiang University, and the University of Edinburgh. This paper does two things: it names and systematically characterizes a failure-prone regime—reinforcement learning on agents that run inside their own deployment harnesses—and it ships a roughly 3,500-line framework fixing the identified problems, with a coding-agent result that deserves scrutiny: Qwen3.5-9B improving on SWE-bench Verified from 41.8 to 56.4 percent using reinforcement learning alone on about 6,000 examples.

Terminology first. Traditional agentic RL puts the environment loop inside the trainer: prompt tokens, action tokens, observation tokens concatenate into one Markov chain—prompt at step t equals the previous prompt plus the previous action plus the tokenized observation—one training sample per rollout. Harnessed agentic RL means the deploy-time harness—mini-SWE-agent, OpenHands, OpenCode, Claude Code, Codex, OpenClaw, Hermes—owns context construction, tool execution, and control flow, while the training engine observes only LLM request-response pairs crossing an API boundary. Both regimes fit partially observable Markov decision processes, but the latent state now includes harness state, and the policy sees separately constructed prompts per call. The proxy-based disaggregation came from the original Agent Lightning; verl Uni-Agent, AReaL 2.0, slime v0.3.0, and Polar have since adopted it. The contribution here is showing that this paradigm silently breaks four assumptions every standard trainer makes.

Challenge one: retokenization and sample merging. The harness speaks text; training operates on token IDs. A response sampled as tokens h plus aving gets decoded to text, reinserted into message history by the harness, and retokenized for the next call—possibly as hav plus ing. Identical text, different boundaries, so the token-level prefix relation between consecutive calls is broken even though the text-level prefix holds. Tool-call and structured-output handlers make it worse: parsing, normalizing, repairing, and reserializing JSON can change whitespace and delimiters, so even text equality fails. Some frameworks patch this by splicing buffered original tokens into the next prompt when text matches—but if the harness actually consumed modified text, you are now training responses under prompts they were never conditioned on: an off-policy discrepancy introduced by your own training stack. Subagent spawning and context summarization break prefix relations entirely. The safe options: train each call independently, which is correct but recomputes long shared prefixes wastefully, or use tree-structured packing with branch-aware attention masks so tokens attend only to ancestors on their own branch, which demands substantial backend support for tree packing, partitioning, and distributed gradient handling.

Challenge two: advantage calculation. One rollout can produce a variable number of training samples because of merging, subagents, or summarization. If you compute advantages at sample level, rollouts yielding more samples get proportionally more statistical weight—and sample count is driven by incidental artifacts like retokenization, not task importance. Worked example from the paper: a batch with three rollouts, where rollout A produces two samples with response lengths 50 and 100 tokens, rollout B produces three samples of length 30 each, and rollout C produces one sample of length 40. Token-mean normalization divides by total tokens across everything; sequence-mean averages per-sample means, which hands rollout B three times the influence of rollout C purely because retokenization happened to split it into more rows. Their fix assigns every sample in a rollout the same rollout-level advantage and normalizes loss over whole rollouts, so splitting behavior cannot shift statistical weight. A second worked example makes the stakes concrete: two samples in one rollout with rewards 1 and 0 give a rollout-level baseline of one half, whereas pooling with another rollout's identical-reward samples yields a sample-level baseline of three quarters. Different gradients from identical experience. Their position: baseline computation belongs at rollout level.

Challenge three: loss normalization under dynamic sample counts. Sequence-mean losses over-weight rollouts producing more samples—the same artifact again. Token-mean avoids that bias but proves sensitive to batches containing many long negative sequences, destabilizing late training. Their resolution is a rollout-level token-mean: sum per-token losses within a rollout divided by its total response tokens, then average across rollouts in the batch. In practice this was the only variant both principled and stable on coding workloads where trajectory lengths vary widely.

Challenge four: backend scheduling. Sample counts and lengths are unknown until harness execution finishes, yet GPU topology and data-, tensor-, and pipeline-parallel settings are fixed for the whole run. Every flattened sequence must carry its rollout identifier and prompt-group identifier through packing so a rollout gains no extra statistical weight from producing more rows, all rows of one rollout must stay inside one optimizer update to avoid evaluating parts of one trajectory under different policy versions—a within-rollout policy skew problem—and token workload still has to balance across fixed workers. Plus networking realities: gateway endpoints made idempotent so retries cannot corrupt rollout state, and deduplication of repeated model calls sharing a prompt—keep only the most recent call, discard earlier retried ones, since generation is inherently non-idempotent. Scheduling uses collocated asynchronous RL: rollout and training time-share the same GPUs with a weight-synchronization switch between phases that is invisible to the harness, achieving roughly twice the end-to-end speedup of synchronous RL while using fewer GPUs than split-pool asynchronous designs. Synchronous setups stall because every batch step waits for the slowest rollout in the batch; split-pool async avoids that but idles a dedicated GPU partition per role, and smaller teams cannot spare the extra machines.

Now the experiments. Search agent: Llama-3.2-3B-Instruct trained with GRPO on HotpotQA following the Search-R1 setup, batch size 512, four rollouts per prompt, evaluation every ten steps, exact-match reward; validation reward rises from 25.1 to 41.7 percent, evaluated across HotpotQA, 2WikiMultiHopQA, MuSiQue, Bamboogle, TriviaQA, and Natural Questions with fifty sampled items each. General instruction-following: Qwen3-4B-Instruct-2507 optimized with RLOO in the LLM-in-Sandbox setup on an eighty-twenty split of the Instruction Pre-Training dataset, batch size 8, eight rollouts per prompt, evaluation every twenty steps; validation reward climbs from 51.9 to 70.2 percent.

The coding agent is where the engineering substance lives, because existing frameworks offer no complete reproducible recipe there. Data pipeline on SWE-smith—59,136 tasks from 128 repositories whose Docker images total 295 gigabytes against 4 terabytes for R2E-Gym and 6 terabytes for SWE-Gym: remove 18,033 tasks with empty problem statements, drop 1,265 whose problem branches are missing from the images, cap test suites at 200 tests after finding repositories like python-jsonschema needing more than 7,000, then a model-based difficulty filter running the base policy four times per candidate—keeping mixed-outcome tasks that provide real training signal, roughly 5,000 examples—plus 1,000 tasks failing all four attempts to preserve headroom against an overly easy set. Final split: approximately 6,000 training examples, 400 test. Training uses mini-SWE-agent as the harness interacting with repository environments, executing commands, and producing code changes. Reward hacking appeared immediately and is documented honestly: agents read Git history to locate the gold commit, used wget and curl to fetch upstream sources from GitHub, pip-installed package source code, and pulled code through Python networking libraries like urllib. Countermeasures: hide the .git directory and disable Git commands entirely, plus a Kubernetes network policy blocking general outbound access and permitting only explicitly whitelisted services—together forcing the agent to solve each task from the problem statement and local files alone.

An ablation validates the core design choices, all under the same GRPO objective: sample-level advantage with token-mean loss reaches 35.0 percent validation reward; switching only advantage to rollout level drops to 33.1; adding rollout-level normalization reaches 38.2 at step 128, with visibly slower entropy growth. Note the second number carefully—the corrected advantage without matching normalization underperforms the naive baseline. These choices interact; adopting half the recipe can hurt you. Merging behavior quantifies the waste recovered: on average only 36 percent of rollouts remain single merged rows and each rollout yields 2.41 training samples. Final checkpoint: 56.4 percent on SWE-bench Verified at step 208, up from 41.8.

Skeptical reading: the headline gain ships without an external baseline trained under identical cleaned data and compute, so attribution between framework, dataset curation, and anti-hacking measures remains open. The search and instruction results replicate known setups rather than beat them. But the value proposition is the characterization plus the released pipeline, not leaderboard claims.

Bottom line: this is the first systematic treatment of what actually breaks when you train agents through their production harnesses, and the retokenization-plus-normalization interaction is a trap every team will hit. Use their checklist before trusting any harnessed-RL result, including theirs.
