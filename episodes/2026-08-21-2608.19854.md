Repo0: Design-Driven Zero-to-All Code Generation, by Silin Chen and Haoyi Teng as equal first authors, Xiaodong Gu as corresponding author, with Yuling Shi, Jiale Huang, Yongpan Wang, Hongyu Zhang, and Haibing Guan. The affiliations are Shanghai Jiao Tong University and Chongqing University.

The setting is zero-to-all code generation: an agent receives natural-language requirements and must construct an entire software project from nothing while maintaining a modular repository architecture throughout. Most existing systems quietly assume the opposite, that component boundaries, package organization, and dependency graphs are already given, which is why repository-completion work looks so much better than it should. The authors' diagnosis of prior systems, including RPG, the strongest graph-based baseline, is that they treat software design as a static artifact: a perfect architectural blueprint generated in one initial planning stage, then rigidly executed. Anyone who has shipped software knows the blueprint is wrong by the time implementation starts; generated code reveals whether planned components were ever cohesive or whether dependency edges are entangled.

Repo0's answer is continuous structural evolution around an explicit architectural state, instantiated as what they call a Dual-DAG. Two directed acyclic graphs plus an alignment relation. The requirement-level DAG holds high-level requirements decomposed into sub-requirements, and its edges encode functional coordination: two requirements logically used together and needing joint consideration for behavior, inputs, and outputs. The component-level DAG holds components such as modules, parsers, adapters, or service layers, each a bounded implementation responsibility, with edges encoding real implementation dependencies like inheritance, reuse, or containment. The alignment relation maps requirements to components many-to-many and preserves traceability from prompt to code. The split matters because conflating functional coordination with implementation dependencies in one planning graph is exactly how prior planners produce brittle structures.

Construction proceeds in three phases. Phase one builds the initial state. An LLM extracts capability-level candidate requirements under regularization constraints so low-level operations do not become top-level items, then merges redundant items into high-level requirements that serve as decomposition anchors rather than file specifications. Each high-level requirement goes through a three-stage reasoning-then-labeling process inspired by Atom of Thoughts: produce an enriched description covering intended behavior, inputs, outputs, constraints, interface expectations, error cases, and ambiguous scope; identify sub-requirements from that description; then label logical dependency edges between them. For each requirement the LLM proposes bounded components with names, responsibility descriptions, and explicit served sub-requirement lists, creating alignment pairs, then infers must-have implementation dependencies using requirement coordination edges only as soft evidence.

Phase two evolves the component-level graph through four structural actions triggered by modularity metrics. Split fires when a component's cohesion falls below a threshold gamma-split of two thirds while its served sub-requirement count exceeds a per-round cap preventing over-splitting; cohesion is the density of coordination edges among the sub-requirements a component serves, computed over the induced subgraph. Candidate groups come from minimum-cut graph partitioning, and the LLM rewrites the component accordingly. Merge fires when two components' served sub-requirement sets have Jaccard similarity above 0.7 with more than one bridging edge, but an LLM validates candidates first, because some coupling is legitimate layered or adapter architecture. Revise rewrites responsibilities and interface assumptions without moving boundaries. Save marks a component stable for this round. The loop terminates when a full round yields no eligible actions: that is structural convergence, after which a final semantic-alignment pass applies revisions where coverage or interfaces look inconsistent. Thresholds were tuned on Commit0 Lite against two held-out repositories, wcwidth and sphinx, comparing evolved architectures to golden ones manually.

Phase three generates code test-first. The converged component DAG converts into a package plan with file paths, exported symbols, and dependency-aware generation order. Per component, context includes its responsibility description, aligned requirement nodes, and upstream components. Then TDD: generate an importable skeleton fixing the public API, synthesize tests from aligned requirements, implement until tests pass, with import checks, interface checks, and pytest execution triggering localized repair. Validation feedback revealing wrong interface assumptions can trigger revise before the next cycle.

Evaluation uses RepoCraft, six paraphrased real Python repositories to reduce pretraining leakage: scikit-learn as MLKit-Py at roughly 66 thousand lines, pandas as TableKit at 106 thousand, sympy as SymbolicMath at 219 thousand, statsmodels as StatModeler at 83 thousand, requests as HttpEasy at about 2,800, django as PyWebEngine at 109 thousand. Two engineers revised task descriptions to strip structure cues and interface hints while preserving function. Backbones are GPT-5 mini and DeepSeek V3.2, temperature zero, three runs averaged, with cross-model evaluation so DeepSeek grades GPT's output and vice versa. Baselines are mini-SWE-agent, Paper2Code, and RPG, all sharing the identical downstream TDD scaffold once their architecture exists, isolating the design contribution.

Results on requests, statsmodels, and django: Repo0 takes highest Functionality Coverage in every setting, hitting 100 percent on requests under both backbones, 80.68 on statsmodels and 80.50 on django under GPT-5 mini. Against RPG, pass rate improves by up to 29.74 percentage points and coverage by up to 20.08. Under GPT-5 mini on django, Repo0 posts 74.36 pass versus RPG's 47.33, with voting rates above 97 everywhere. Ablations confirm each piece: removing structural evolution costs the most, minus 13.33 pass rate on django; removing dependency-aware component ordering costs 30 points of pass rate on statsmodels, showing order matters as complexity grows; removing requirement context and collapsing the Dual-DAG into one unified graph both hurt consistently. The RQ3 analysis is the sharpest finding: LLM-decided evolution with fixed budgets of one, three, or five rounds all underperform metric-guided convergence, because unconstrained structural actions over-decompose the architecture past the point of coherence. Metrics provide an actual stopping criterion, not just more refinement. Action distributions show split dominant at 307 of 393 actions for GPT-5 mini, save next, merge rare, and DeepSeek V3.2 issuing far fewer revise calls, which controlled experiments attribute to cleaner initial states rather than model differences.

Metrics deserve definition since they are non-obvious. Functionality Coverage counts reference functional categories matched by at least one generated functionality description. Pass Rate is the fraction of benchmark tasks whose adapted ground-truth tests pass on the generated repository, and Voting Rate is the fraction where majority-vote semantic evaluation finds a matched functional interface; both task-level measures are computed with cross-model grading, DeepSeek V3.2 evaluating GPT-5 mini output and vice versa, to mitigate evaluator bias.

One more result worth knowing before adoption: the case study on StatModeler shows the pipeline end to end, from a README specifying regression modeling, generalized linear models, time-series analysis, statistical testing, data backends, and diagnostics, through 39 extracted high-level requirements, sub-requirement decomposition, component architecture, down to concrete package and file realization. Representative refinements include splitting an overloaded experimental namespace manager into registry-lifecycle and access-control components, and merging redundant variance-estimation fragments.

The structural-evolution figure deserves a closer read because it is the paper's core evidence. On StatModeler with GPT-5 mini: no evolution at all yields 75.90 coverage and 81.90 pass; one fixed LLM-decided round reaches 78.74 and 81.10 coverage-pass territory before declining through three rounds to 70.45 coverage and five rounds to 69.32, with novelty rising to 13.37 as fragmentation generates extra functionality. Metric-guided convergence reaches 80.68 coverage, 85.51 pass, 98.65 voting, beating every budgeted variant despite using fewer refinement rounds, which is the cleanest demonstration that an explicit stopping criterion beats more optimization.

Skeptical read. Only three of six repositories appear in the main paper, the rest pushed to supplementary material. Functionality Novelty rising alongside falling coverage in ablations signals drift toward generating extra functionality instead of required behavior. Thresholds were hand-tuned on held-out repos by visual comparison to golden architectures, which is defensible but not automated. And every evaluation runs through LLM-based semantic voting plus rewritten tests, so grader reliability is a shared-mode risk across all arms even with cross-model grading. Bottom line: treating architecture as an evolving state with measurable convergence criteria is the substantive idea here, and the ablation evidence backs it. Re-run the thresholds on your own domain before trusting the specific numbers.
