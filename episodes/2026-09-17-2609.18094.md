Agora: Git as Shared Memory for Collective AutoResearch. The first three authors are Yifan Zhang, Yunheng Zou, and Shaokun Zhang, and the work comes out of NVIDIA. It is a systems paper with an unusual experimental subject, a community of autonomous research agents working without a planner.

The starting point is a known limitation of autonomous research loops. A single coding agent, in the AutoResearch style, can improve a training setup unattended, and that is well established. But if you run several of them in parallel, each one starts from scratch, so adding agents tends to add duplicated search rather than more discovery. More workers means more of the same search being done several times over. Agora is proposed as the shared memory that fixes this. The core idea is almost embarrassingly simple: research is recorded as an append-only directed acyclic graph stored in Git, so that every claim is a commit anyone can check out and rerun. Each result, insight, hypothesis, verification, and report is an immutable commit, and the parent edges of the commit say what it builds on. There is no custom coordination server, no message bus, no central planner. The coordination substrate is a Git repository and the discipline of commits.

The appeal of using Git specifically, rather than a purpose-built coordination store, is worth stating, because it is a design bet. Every claim being a commit means the entire history of the community is versioned, diffable, and reproducible with tools every researcher already knows. A worker can check out any prior claim, rerun the experiment that produced it, and see whether it reproduces, without trusting a summary or a leaderboard entry. The derived index is a read-only projection over that log, so it can be rebuilt from the commits at any time, which means there is no single source of truth that can drift out of sync with the actual work. The diversity-aware selection rule then reads the index and steers new workers toward neglected branches rather than the current leader, which is the mechanism the authors rely on to avoid the community collapsing into a monoculture where every worker just refines the same top idea. The whole design is an argument that the hard part of multi-agent research is not the coordination protocol but the persistence and verifiability of the shared state, and that Git already solves both.

On top of that immutable log, a derived index exposes the state of the community: the frontier, the neglected branches, and the verification status of each claim. A diversity-aware selection rule is the mechanism that keeps the community from collapsing onto one leader, the anti-monoculture device. The paper describes the system and then reports its first sustained use, which is the interesting part. It is a run of nearly 12 days in which 13 language-model workers, with no assigned tasks and no central planner, worked on a weight-transfer problem. The setup: 141 pretrained donor models and a frozen 119.6 million parameter attention and SSM hybrid whose dimensions match no donor, and the workers had to initialize the target without training data or gradient updates. They published 1,703 contributions and drove the evaluator from 3.39 to 1.899 bits per byte, closing 62 percent of the gap to a trained GPT-2 124M model.

The structure of the improvement is worth noting. The descent is extremely front-loaded: the first eight improvements account for roughly 70 percent of the total descent, and the first 18 scored contributions account for about 98 percent. After that, the community is mostly consolidating and rediscovering. There is heavy parallel rediscovery. Of 696 pairs of different accounts posting identical scores, 63 percent are within a tight score range, meaning a large share of the work is multiple agents independently arriving at the same result. The winning recipe compresses the donors' next-token statistics into the target's embedding and output head, then adds a short-range context signal through sparse edits to the attention, feed-forward, and state-space blocks. Its ancestry spans 145 commits across 15 accounts, and 165 independent reproductions were posted, none of which failed. The paper is candid that the single mid-run human intervention, which pulled the community out of a monoculture, was necessary, and it is explicit about what the trace does and does not establish.

It is worth pausing on why the chosen problem is a good testbed for a shared-memory system, because the choice is doing some of the argument's work. The weight-transfer task has a small, verifiable objective, a single number, bits per byte, that every worker can compute identically from the same held-out evaluation, so there is no ambiguity about whether a contribution improved the state. That shared, cheap, reproducible metric is exactly the condition under which an append-only log is useful, because every claim can be checked by rerunning the same evaluation rather than by trusting a narrative. The target's mismatched dimensions relative to every donor also matter, because it rules out the trivial solution of copying a donor's weights, forcing the workers to actually reason about how to map statistics across architectures. So the problem is not just hard, it is hard in a way that is checkable, which is the property a shared-memory system needs in order to be testable at all. A task with a fuzzy or subjective success criterion would not let the 1,703 contributions be ordered and verified, and the whole point of the Git substrate would be untestable. The problem selection is therefore a design decision, not an accident, and it is the reason the run can be reported as a controlled artifact rather than an anecdote.

A skeptical read, and it is a long one, because the experimental design has a real hole. What I trust is the artifact, the idea that Git is a perfectly adequate shared-memory substrate for a community of research agents, and the reproducibility story, 165 independent reproductions with zero failures, is strong evidence that the log is actually checkable and not a narrative. The 62 percent gap closure on a genuinely hard weight-transfer problem, with a target whose dimensions match no donor, is a real result and not a toy. And the front-loaded descent plus the 63 percent parallel-rediscovery rate are honest, useful observations about what parallel agents actually do, which is mostly redo each other's work.

What I would re-verify before believing the headline. The paper itself says it, and this is the crux: the 12-day run is a single sustained use, and it does not establish that shared research state improves discovery per unit of compute. That is the controlled comparison the authors explicitly defer, the run you would have to do to know whether the community beat what 13 independent agents would have produced on the same budget. Without that control, the 62 percent result could be entirely a property of the weight-transfer problem being easy to crack once the right idea lands, with the shared memory doing nothing more than filing the parallel waste more neatly. The 13 workers with no tasks and no planner is also a very specific regime, and the one human intervention that broke the monoculture is a reminder that the diversity rule is not yet reliable enough to run unsupervised. There is also a compute accounting question the trace does not fully answer, because 13 agents running in parallel for 12 days is a large aggregate budget, and the relevant comparison is not against one agent but against the same total compute spent by a set of independent agents with no shared log, which is precisely the control the authors flag as missing. The bottom line is that this is a clean, honest systems paper whose central artifact, Git as agent shared memory, I would take seriously and reuse, but whose central empirical claim, that shared state improves discovery, is still an open question the authors themselves flag as unresolved.
