CrossSWE, Benchmarking Cross-Repository Joint Development for Coding Agents, from Shanghai Jiao Tong University, Xidian University, and Singapore Management University. The first three authors are Silin Chen, Yuling Shi, and Heng Lian. This is a benchmark paper that pushes coding-agent evaluation past the single-repository boundary, and the motivation is a real one. Every major SWE benchmark, from SWE-bench through SWE-bench Pro and ProMax, expands complexity within a single repository: bigger codebases, longer horizons, more files changed. But the context an agent needs to understand and the scope of changes it needs to consider are still bounded by one repository, and that caps how hard these tasks can get. Real development is different. A change to an API, a library, or a protocol in one repository propagates to dependent repositories, and the fix requires modifying several of them together, consistently, in one shot.

CrossSWE introduces cross-repository software-engineering tasks: a single issue whose correct resolution requires coordinated changes across multiple interdependent repositories. That is distinct from the multi-repository settings that already exist, where the other repositories serve only as context, the agent reads them to understand an API or a dependency, but the patch it writes and the tests that check it stay inside one repository. Here the solution itself spans the boundary. The paper verifies joint necessity explicitly: each task is tested to confirm that partial modifications, changing only some of the required repositories, are insufficient to achieve the intended behavior. That is the methodological contribution, because it rules out tasks where the agent could ignore the second repository and still pass, and it is the reason the benchmark's headline number is a lower bound on the difficulty of cross-repo work rather than an estimate of it.

The construction methodology deserves a second look, because it is what separates this from a data-engineering exercise. The suite spans one hundred sixty-five repositories, twenty technical domains, and thirteen programming languages. They start from real-world multi-repository instances and verify joint necessity by construction: for each candidate task, they test that partial repository modifications, changing only a subset of the involved repositories, fail the tests. A task that survives this filter genuinely requires coordinated changes across the boundary. The evaluation harness runs each model as a coding agent against the full repository set, with the joint test suite as the oracle, and reports pass-at-one as the primary metric. The reference patches are deliberately large, which is part of the point: these are not one-line fixes. Fifty-six point one percent of instances modify more than ten files, and sixty-six point seven percent touch more than two hundred lines, well above the SWE-bench Pro distribution where the corresponding top bucket is around twenty-five percent. The paper's running example is a session-refresh bug: split cookies are lost because one repository joins multiple cookies into a single string while a dependent repository assumes a single string and its type assertion fails. The fix requires changing both repositories' handling of the cookie list simultaneously, and the figure walks through why patching only one side fails.

The results, evaluating five frontier models with pass-at-one as the primary metric. The strongest, GPT-6.1 Sol, achieves only fifty-eight point four eight percent pass-at-one, substantially below its reported seventy-five point two on DeepSWE version one point one. That gap is the paper's central finding: cross-repository joint development is a genuinely harder regime, not a harder instance of the same problem. DeepSeek V4.1 Flash follows at fifty-two point six three, Claude Sonnet 5.5 at fifty point two nine, Qwen3.8-Flash-Next at forty-five point zero three, and GLM-5.3 Flash at forty-three point eight six. Performance also splits by language setting: GPT-6.1 Sol scores sixty point three four on single-language tasks against fifty-four point five five on multi-language ones, and the same pattern holds for the other models, with multi-language cross-repo work consistently harder. The dominant failure mode, identified in their analysis, is cross-repository inconsistency, at forty-four point two percent of failures: the agent produces changes in each repository that are individually plausible but mutually incompatible, which is exactly the capability the benchmark was built to measure. The paper notes this failure mode appears across all five models, so it is a property of the task structure rather than of one model's weakness.

The evaluation protocol is deliberately fixed so the comparison isolates model capability. They use SWE-agent, a lightweight repository-level coding-agent framework that inspects, modifies, and tests codebases through iterative shell-based interactions, and they keep the agent configuration identical across all models, at high reasoning effort, with each run limited to at most three hundred interaction steps and a ten dollar cost cap. That matters because the headline is not about harness engineering; it is about what the models bring to the same scaffold. Pass-at-one counts an instance as resolved only when the final repository state satisfies the complete evaluation suite, so a patch that fixes one side of a two-repository change does not get credit. They also derive three hundred thirty single-side modification tasks from all one hundred sixty-five of the two-repository instances, keeping both repositories in the environment but requiring edits to only one, which lets them separate the cost of cross-repository coordination from the cost of per-repository competence.

The resource numbers are a second, quieter finding, and they cut against the intuitive picture. The closed-source models solve tasks with about one to one point three million input tokens and roughly twenty-nine to thirty-three steps, while the open-source models burn between nine point seven and seventeen point five million input tokens and one hundred forty to one hundred eighty-two steps. So the open models are spending an order of magnitude more context and steps and still landing lower. Whatever they are doing with that budget, it is not converting to cross-repository consistency. This also suggests a structural explanation: cross-repository tasks may be the regime where long-horizon context helps less, because the failure is not in recalling the remote API but in keeping the two edits aligned, and more context does not buy alignment.

The task distribution is worth a word before the skeptical read. The twenty technical domains and thirteen languages are broad enough that the headline number is not an artifact of one stack, but the paper does not publish the per-domain breakdown in the main body, so the effective difficulty may concentrate in a subset, and a model tuned on one domain's conventions could look much worse than its true cross-repo ability suggests. The joint-necessity filter is the part that survives contact with that concern: it is a construction-time property, not an evaluation-time one, so it does not depend on which model you point at the benchmark.

The skeptical read. As a benchmark, the construction bar is the thing to scrutinize: joint necessity verification sounds clean, but it depends on the test suites being able to detect incompatibility across repository boundaries, and a task is only as hard as its tests. The five-model evaluation is a snapshot, and the benchmark will age the way all SWE benchmarks do, as models adapt. The honest framing is that CrossSWE measures a real, currently-unsolved gap, and fifty-eight percent for the best model means there is headroom, not a ceiling being hit.

What to take away. If you are evaluating coding agents, this is the dimension your current single-repo suite is blind to, and the cross-repository inconsistency failure mode is worth measuring in your own pipelines: it will tell you whether your agent treats a multi-repo change as one problem or as several independent ones. If you are building agents, the finding that consistency, not per-repo competence, is the bottleneck points at a concrete training target: joint-edit planning across repository boundaries, with compatibility checking as a first-class step rather than an afterthought.

The verdict. CrossSWE is a well-motivated benchmark that closes a real blind spot in coding-agent evaluation, with verified joint necessity and a clean headline: the best frontier model reaches only fifty-eight point four eight percent pass-at-one, and the top failure mode is the agent failing to keep its own cross-repository changes consistent. It measures a genuine open capability rather than re-ranking models on a harder version of a closed one.
