Omni-IO Skills: Harnessing Your Agent Omni-Native. The first three authors are Yanlin Li, Mingyang Hao, and Shengqiong Wu, from the National University of Singapore and the University of Oxford, with project lead Hao Fei.

The paper's argument starts from a scaling tension. Omni foundation models have brought perception, reasoning, and generation into a shared context, but every new modality added to a shared backbone means reconciling representations, objectives, and fidelity requirements, usually with new data, codecs, decoders, and alignment stages. Meanwhile, specialized models and media engines keep improving outside the shared backbone. Omni-IO Skills takes the complementary route: instead of widening one model, it wraps an existing general-purpose agent in a harness that gives it omni-native behavior, without changing the host agent's reasoning core. The motivating example is producing an online course, which begins with lecture recordings and reference documents, continues through content analysis and visual design, and ends with slides, illustrations, narration, and an explainer video. The artifacts share facts, style, timing, and production constraints, so the system must receive and produce interleaved combinations of text, images, audio, video, documents, 3D assets, and code while preserving semantic and asset continuity across the whole workflow.

The harness has two layers worth separating. The upper layer is the Skills, which are hierarchical. There are 19 Atomic Skills, which are capability primitives; 2 Expert Skills, which are production procedures for concrete deliverables; and 6 Scenario Skills, which are application-level tasks with multiple related outputs. Together, 27 Skills cover 38 representative tasks across four capability families, understanding, generation, reasoning, and retrieval, and seven artifact modalities. The lower layer is a four-layer runtime: a Skill Entry layer, an MCP Tool Service layer, a Provider and Configuration layer, and a persistent Asset Registry layer. These separate task knowledge, tool interfaces, service implementations, and persistent outputs, so the host agent can plan multimodal tasks without coupling a workflow to a particular provider or file path.

The central data structure is the Declare Execution Graph. Multi-asset workflows are represented as graphs whose nodes are operations and whose edges are dependencies. Independent operations are scheduled concurrently, and successful outputs are registered in the Asset Registry for downstream and cross-turn reuse. The registry is what makes the harness stateful across turns: an asset generated in one turn is addressable in the next, and the graph can be re-executed with a replaceable backend, meaning you can swap the provider that renders a video without rewriting the workflow. The MCP tool service is the integration point to external tools, and the whole design is deliberately backend-agnostic, which is the engineering property that makes it plug-and-play across hosts.

The layering has a specific purpose: task knowledge lives in the Skills, tool access in the MCP service, provider binding in the configuration layer, and artifact state in the registry, so that a workflow can outlive any one provider or model version. The paper positions this against two routes to omni capability. The first route, extending the foundation model itself to more modalities, ties capability growth to costly model updates, and the scaling pressure is explicit: as more modalities enter a shared model, their representations, objectives, and fidelity requirements must be reconciled, often with new data, codecs, decoders, and alignment stages. The second route, assembling specialist models and tools, leaves unresolved how procedures, dependencies, intermediate assets, and cross-turn revisions should be coordinated. Omni-IO Skills is a bet that the coordination layer, not the model, is the binding constraint for most production omni workflows, and that it can be built as a plug-and-play harness around whatever agent and tools you already run.

The evaluation is on UniM-90, a controlled 90-instance subset of the UniM benchmark, using two distinct host agents: GPT-5.6 Sol and Claude Sonnet 5. The headline metric is input support rate, the fraction of instances the host can actually attempt, and the harness raises it from 40.00 percent and 38.89 percent to 100 percent for the two hosts. The quality metric is the Semantic-Quality Coupled Score, or SQCS, which couples semantic correctness to quality. The relative SQCS increases from 26.99 to 74.94 for GPT-5.6 Sol and from 27.82 to 77.78 for Claude Sonnet 5, gains of 47.95 and 49.96 percentage points. The Strict Structure Score, which checks whether the response satisfies the task's required structure, reaches 100.00 and 99.78, and both hosts attain a Lenient Structure Score of 100.00. The paper also reports that the absolute SQCS after loading the harness, 74.94 and 77.78 across all instances, exceeds the base agents' 67.49 and 71.53, which were measured only on their narrower supported subsets. So the harness does not just widen coverage; it delivers stronger responses on the full set than the base agents managed on the subset they could handle.

The runtime workflow is worth tracing through a concrete example. A user requests a product promotion, and the Skill Entry layer selects the relevant Skills, which expand through Expert Skills into five Atomic Skills, each a single tool call or a single generation step. The dependencies among these atomic operations form a Declare Execution Graph, which is validated before execution and then scheduled in successive waves. Each ready node in a wave follows the same execution loop: tool routing through the MCP Tool Service, provider resolution from the configuration layer, asset injection from the Asset Registry for any inputs that were generated in a prior turn or a prior wave, and execution. Successful outputs are registered back in the Asset Registry for downstream nodes in the same wave and for cross-turn reuse. The figure in the paper illustrating this workflow shows the asset flow and the control flow as two separate streams: control flow goes from Skill selection through DEG construction, validation, scheduling, and final state, while asset flow goes from user-provided and historical assets through generation and registration.

The fact that the same harness produces large, similar gains on two very different host agents is the paper's strongest internal evidence. If the improvement came from a specific model's quirks, it would not transfer across hosts. The consistency across GPT-5.6 Sol and Claude Sonnet 5 suggests the gains are in the orchestration and asset-management layer, not the reasoning model.

Here is the skeptical read. The single most important caveat is the benchmark: UniM-90 is a 90-instance controlled subset, and the base agents' reference numbers were measured on their narrower supported subsets, not the full 90, so the comparison is not perfectly apples-to-apples, even though the paper discloses this. The input support rate jumping to 100 percent is partly a function of the harness covering the modality gaps that made instances unsupported, which is the intended behavior but means the metric is measuring coverage more than reasoning. The SQCS gains of roughly 48 to 50 points are large enough to warrant scrutiny: a harness that adds tool calls and asset registration can inflate quality scores if the scoring rewards structure and completeness, which the Strict Structure Score of essentially 100 percent hints at. The paper is also a technical report with a code repository rather than a peer-reviewed system paper, and the 27 Skills are a curated set; the harness's behavior outside the 38 covered tasks is not characterized.

What would I trust, and what would I re-verify? I would trust the architecture: separating Skills from a backend-agnostic runtime, and the Declare Execution Graph with a persistent Asset Registry, is a sound decomposition for multi-asset workflows, and the MCP-based tool layer means it slots into existing agent stacks. The cross-host consistency is the number to trust most. Before adopting, I would re-verify the SQCS on the full UniM set with the exact host versions, inspect a handful of the 90 instances to confirm the quality gains are real content improvement and not structural completeness, and measure the added latency and cost from the concurrent graph execution and asset registration, because a 100 percent support rate that doubles wall time is a different tradeoff than the abstract implies. The gotcha is the Asset Registry's cross-turn state: persistent assets across turns is where bugs hide, and the graph re-execution with a replaced backend is the part that needs its own integration tests.

Omni-IO Skills is a practical, well-structured answer to the omni-scaling problem: compose specialized tools and persistent asset state around an existing agent instead of widening one model, and the cross-host consistency is genuinely encouraging. Treat the benchmark numbers as promising but subset-bound, and verify the quality gains against your own task distribution before betting a production pipeline on the coverage metrics.
