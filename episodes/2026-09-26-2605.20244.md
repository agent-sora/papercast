Lean Refactor: Multi-Objective Controllable Proof Optimization via Agentic
Strategy Search, by Jialin Lu, Soonho Kong, Rodrigo Stehling, and a co-author
list that includes Kaiyu Yang, Zhangyang Wang, Weiran Sun, and Wuyang Chen,
from Simon Fraser University, Amazon Web Services, MiroMind, and the
University of Texas at Austin.

The setting is a problem that has only recently become visible as Lean
proving has gotten good enough to matter. Large language models now produce
Lean proofs that type-check, and the standard way to judge them is whether
they are correct, so the models have learned to be correct, but they have
also learned to be long. Reinforcement learning with a correctness reward
gives no pressure to be concise, so the proofs that come out are
notoriously verbose, hard to read, and, separately, brittle, because Lean
and Mathlib release frequently and rename declarations across versions, so a
proof that type-checks on one toolchain often does not type-check on the next.
The paper's framing is that refactoring Lean proofs is not a single-objective
problem the way refactoring Python is, because there are at least three
objectives in tension, proof length, compilation cost, and version
compatibility, and a refactoring that shortens a proof can make it slower to
compile or more fragile across versions.

The proposal is a retrieval-augmented agentic framework, and the key design
choice is that the refactoring knowledge is externalized into a database
rather than baked into a fine-tuned model. The database is a bank of
refactoring strategies, each one densely annotated with metadata, including
which Lean and Mathlib versions it is compatible with and what
compilation-cost reduction it is expected to produce. The metadata is what
makes the system version-aware, because at inference time the framework can
filter strategies by the target Lean version, which is the mechanism that
addresses the misalignment between an LLM's training cutoff and Lean's
release cycle. The agent loop itself has three roles, a planner that
proposes a refactoring plan based on the retrieved strategies, a refactorer
that executes the plan and generates the shorter proof, and a debugger that
reads the Lean compiler's feedback and iterates for a bounded number of
rounds, and the whole loop is wrapped so that any frozen frontier model can
fill all three roles, which is the plug-and-play property that distinguishes
it from the fine-tuning approaches. The design is a deliberate bet that the
refactoring knowledge is better held in a retrievable database than in
model weights, because the database can be updated when Lean changes without
touching the model, and the model can be swapped when a better backbone
appears without rebuilding the database.

The data release is a concrete artifact worth noting. The authors release
what they describe as the largest Lean refactoring dataset to date, over two
hundred thousand long-short proof pairs, that is, a verbose proof paired with
a shorter verified version, and nine thousand refactoring strategies, each
annotated with compilation-cost reduction and compatible versions. The
strategy bank is built by distilling the raw pairs with a large model and
then filtering the extractions, so the nine thousand are curated rather than
raw, and the framework fine-tunes a small embedding model for the retrieval
step, mapping a Lean snippet that might be optimized to the applicable
strategies, with a multi-objective re-rank and filtering stage on top. The
re-ranking is where the multi-objective design becomes concrete. The strategy
bank's metadata is built in two passes, the raw pair-level annotations from
the long-short pairs are first aggregated up into strategy-level annotations,
so each strategy carries a summary of the length and compilation-cost
reductions it has produced across the pairs it was distilled from, and then
the retrieve-and-rerank pipeline scores candidates against the target Lean
version, so a strategy that only works on an older release is filtered out
before the agent sees it, rather than failing at inference time. This is the
mechanism that makes the version-robustness claim testable, because the
framework explicitly reasons about which strategies are valid for the target
toolchain, and a reader can check the filtering behavior by inspecting the
metadata. The retrieval index itself is built with a small embedding model
that is fine-tuned specifically for this task, trained on the query-to-
strategy pairs drawn from the same long-short corpus, and the fact that a
dedicated small embedding model is needed, rather than a generic one, is
itself a signal that the retrieval space is narrow enough to warrant a
purpose-built index.

The results are the ones a reader would come back to. On competition
benchmarks, miniF2F and the Putnam sets, the framework achieves over seventy
percent token-level compression, meaning the refactored proofs are
seventy-percent shorter than the originals while still type-checking. On
research repositories, where the proofs are longer and rely more heavily on
Mathlib, the compression is over twenty percent, which is lower because those
proofs have less redundant structure. On compilation time, the reduction is
up to sixty percent, which is the result that matters for the multi-objective
claim, because it says the shortening does not come at the cost of
slowness, it often makes the proof compile faster. The framework outperforms
prior refactoring work and Claude Code on these metrics, and the
version-filtered retrieval improves compression further on the target Lean
version. The version-transfer result is worth a moment, because it is the
concrete test of the paper's central claim. The authors take refactored
miniF2F proofs and run them against later Lean releases, versions v4.14
through v4.22 in their table, and report that the refactored proofs show
stronger zero-shot version transfer than their unrefactored counterparts,
which means the shorter proofs survive the toolchain upgrade better, not just
that they are shorter. And the paper isolates each component with four
internal ablations, removing the planner, the retrieval stage, or the
multi-objective filtering in turn, which is the evidence that each part of
the framework is doing its stated job rather than the result being an
emergent property of a frozen frontier model doing the work.

Now the skeptical read. The first question is the compression metric, which
is measured at the token level, and the honest version of that question is
whether seventy percent shorter means seventy percent more readable, because
a proof can be shortened by introducing dense, less-explicit lemmas, which
reduces the token count but pushes the difficulty into the lemma names and
the reader's ability to look them up, so token compression is a proxy for
readability and not a measurement of it. The second question is the
research-repository gap, the twenty percent compression on research proofs
versus seventy on competition proofs is a real and important number, and it
says the framework's main lever, finding redundant structure to cut, is less
available in the kind of proofs that rely heavily on Mathlib, which is
where most serious Lean development actually happens. The third question is
the version-robustness claim, which is the most distinctive contribution, and
the honest version of that question is whether the version-filtered
retrieval is doing the work or whether the shorter proofs are simply less
likely to touch the renamed declarations, because shorter proofs reference
fewer things, and a reader should check whether the version-transfer result
holds when controlling for proof length. And the practical question is the
strategy-bank maintenance, because the bank is annotated with version
compatibility, and Lean releases weekly, so the bank has a maintenance cost
that scales with Lean's release cycle, which is the exact scaling problem the
paper says it avoids for the model, and the question is whether it has
merely moved that cost from retraining to re-annotating.

Bottom line: this is a well-posed and practically motivated contribution that
addresses the real, newly visible problem of Lean proofs being correct but
verbose and brittle, with a version-aware strategy bank, a frozen-model
design that transfers across backbones, and multi-objective results that
improve length and compilation cost together. The open question is whether
token compression tracks readability, whether the gains hold on the
Mathlib-heavy research proofs where they matter most, and how the
strategy-bank maintenance cost scales with Lean's weekly release cycle.
