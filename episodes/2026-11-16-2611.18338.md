The paper is MEM-SQL: Memory-Empowered Text-to-SQL, by Xiaoqi Wang, Wenqi Pei, Shizheng Hou, and colleagues at NICE Lab at the University of Hong Kong, the National University of Singapore, and the University of Science and Technology of China in Guangzhou, the Hong Kong campus. This paper has two deliverables: a benchmark, HARE, that measures something no existing text-to-SQL benchmark measures, which is the value of a user's query history, and a memory architecture that exploits it. If your text-to-SQL system serves the same database repeatedly, both are directly relevant.

The gap. Spider, BIRD, and Spider 2.0 all evaluate questions independently. Each question is a cold start: the system sees a question and a schema and has to reconstruct everything from scratch. But real usage is not like that. A user queries the same database over and over, and a verified query from an earlier request often already contains the join, the subquery, or the column mapping that a new question needs. Existing benchmarks ignore that overlap entirely, which means they systematically overstate the cost of answering follow-up questions and make it impossible to tell whether a system is actually learning from history or just regenerating from the schema every time.

The benchmark. HARE, which stands for History-Aware Text-to-SQL Benchmark, contains 1,600 requests derived from a fixed pool of 823 verified queries, drawn from Spider, BIRD, Spider 2.0, and BEAVER. The source mix is 755 from BIRD, 365 from BEAVER, 268 from Spider 2.0, and 212 from Spider, which puts a heavy weight on the enterprise-grade schemas where schema linking is most expensive, and that is deliberate, because that is where history reuse saves the most. Of the 1,600 requests, 1,300 belong to a single reuse category and 300 combine two of them, 50 per composite. The requests are organized into six primitive reuse categories that specify exactly what carries over from history and what must be edited. Rephrase changes only the wording. Parametric changes alter literal values while keeping the full query structure. Component parametric changes alter values inside a reused intermediate computation. Structural changes keep an intermediate computation and drop it into a new query structure. Shared joins preserve a historical join path while changing filters or grouping. Shared concepts reuse column mappings and metric definitions. The annotations are what make the benchmark useful: every request records which components it preserves and which edits it requires, so you can distinguish whole-query adaptation from partial reuse. Validation checks both the answer and the intended relationship to history, so a query that executes but does not use the history in the annotated way does not qualify. That is a stricter and better validation rule than most text-to-SQL benchmarks use.

The method. MEM-SQL stores three layers of memory, inspired by hierarchical agent memory. The top layer holds whole-query templates. The middle layer holds reusable SQL blocks, essentially subqueries and select fragments. The bottom layer holds mappings from domain concepts to schema elements. Each layer has searchable descriptions that connect new wording to the stored SQL structures and column mappings, so a question that says, in the user's vocabulary, "monthly revenue by region" can be tied to a stored join and a stored metric definition without the model having to re-derive either. Retrieval is where the design is careful: it checks coverage separately for each requirement of the new question, and a layer only contributes if every requirement assigned to it has a match above that layer's threshold. A strong match on one requirement cannot hide an uncovered one. That coverage-gated routing is the core mechanism, and it is the difference between this and a naive retrieve-the-most-similar-query approach. On top of that sits On-demand Schema Linking, or OSL: the system consults the schema only when no memory layer qualifies, or when the generator judges the retrieved evidence insufficient, rather than relying on the model's self-reported uncertainty.

The results, across six language models on HARE. Mean execution accuracy rises from 37.1 percent for direct generation without history to 50.0 percent for MEM-SQL. That is a 12.9-point absolute gain, which is large in this field. On the cost side, MEM-SQL uses 76.6 percent fewer input tokens and achieves 68.8 percent lower latency on average, because it is generating from stored structure instead of re-deriving from the full schema. The ablations separate the memory layers' roles: whole-query templates contribute the most to accuracy, while the reusable SQL blocks matter specifically for composition, that is, requests that assemble pieces from more than one historical query. And here is the honest negative result: requests that reuse several verified queries remain a bottleneck for every method, with accuracy falling from 56.7 percent to 29.7 percent. The drop is sharpest when reused components must be placed in a new query structure or combined with a shared join. So composition from multiple historical sources is the unsolved case.

They also test OSL's transferability. Applying on-demand schema linking to three other memory designs from the literature consistently reduces generation cost in every comparison, but the accuracy benefit depends on the memory design's ability to retrieve complete evidence. That separation is a useful finding: the deferral of schema consultation is a broadly transferable efficiency gain, while the accuracy question is really a retrieval-completeness question. The composition analysis is worth unpacking, because it is where the paper's diagnostics are sharpest. The requests where several verified queries must be combined are exactly the ones where a single strong retrieval match is most likely to mislead: the system retrieves one good-looking historical query, the coverage gate passes because most requirements are met, and the missing piece, often a second join or a structural rearrangement, is never retrieved because the system never asks for it. That is a structural limit of retrieve-then-generate, and it is the reason the authors' coverage-gated routing helps so much on single-source requests but still caps out at 29.7 percent on multi-source ones.

The skeptical assessment. First, 50 percent execution accuracy on HARE is a modest absolute number, and the benchmark is deliberately harder than standard text-to-SQL because it requires the history relationship to hold, not just the answer. That is a feature, not a bug, but it means the numbers are not comparable to BIRD scores floating around. Second, the memory layers require the history to be verified before storage; the paper does not fully treat what happens when the historical query was itself wrong, which is the realistic failure mode in production. Third, the composition bottleneck, 29.7 percent, is where the practical value of the whole approach is capped, and the paper is right to flag it but does not solve it. Fourth, the token and latency savings are measured against direct generation on the same six models, which is the right baseline, but they do not include a retrieval-cost model for the memory store itself.

What I would trust: HARE, because the annotation scheme is clean and the validation rule is stricter than the norm, and it should become a useful evaluation target for any system that serves repeated queries. What I would trust: the coverage-gated retrieval, because the mechanism is explicit and its failure mode is understood. What I would re-verify: the behavior when stored history contains errors, and the composition case, before wiring this into a production data product.

Two-sentence verdict: MEM-SQL shows that verified query history makes text-to-SQL both more accurate and cheaper, with a 12.9-point accuracy gain and a 76.6 percent token reduction, and its HARE benchmark is a genuinely useful tool for measuring history reuse, one that any team running a persistent data product should adopt. The open problem it cleanly identifies, composing evidence from multiple historical queries at 29.7 percent accuracy, is where the next work needs to go, and it is a well-defined problem that the benchmark makes measurable.
