Title: Rules to Tools: Executable Checks for LLM Agents in Scientific Computing
Authors: Jingjie Ning, Guojiang Zhao, Chen Xu
Labs: Carnegie Mellon University
Arxiv: 2610.00313
Day: 2026-10-03
Upvotes: 5
Link: https://arxiv.org/abs/2610.00313
---Rules to Tools is from Jingjie Ning, Guojiang Zhao, and Chen Xu at Carnegie Mellon University, a small matched experiment on how you should hand a coding agent the requirements for a scientific computation.

This is a small paper with a clean, specific claim about how you should hand a coding agent the requirements for a scientific computation. The setting is scientific coding, where an agent receives an equation, boundary conditions, and output requirements, and has to write, run, and revise a program that satisfies them. The paper's observation is that the way the requirements are delivered matters, and it is currently delivered as prose. The requirements arrive as written text, and the agent has to translate that text into checks on its own, build a test, run it, read the output, and decide whether the program is right. The paper's argument is that the same requirements can be delivered as a prepared, callable check, a tool the agent invokes that returns a structured measurement of whether the current artifact violates the public requirement. The two are matched, same written criteria, same starting program, same model, same budget, and the only difference is the interface between the requirement and the agent.

The design is worth being precise about because the whole contribution is in the interface. Public scientific requirements support two verification workflows that share the same underlying criteria. The text group receives the criteria as written specifications, and constructs its own checks through ordinary code execution, it writes the test, runs it, and inspects the output. The tool group receives a callable implementation of those same criteria, and calls the check, which returns a structured measurement of whether the current artifact violates the requirement, so the agent reads a measurement rather than interpreting raw output. In both groups the checks are defined before execution, the measurements arise from running the checks on the current artifact, and both groups revise their program based on what they observe. A concrete example from the paper is a boundary-condition task, where the public rule is that the outer slope is less than zero and that conservation holds, and the text agent has to build a residual check to verify it while the tool agent calls the check and reads whether the residual violates the bound. The point is that the tool turns a requirement the agent has to operationalize into a measurement the agent can read, and the question the paper asks is whether that is worth anything.

The results are a matched repair comparison on a held-out and a development SciCode set, drawn from scientific coding tasks across molecular workflows and scientific repositories. The comparison is structured as a repair task, and the control is the thing that makes it a fair test. Every repair group shares the written checks, the starting program, the model, and the budget, so the only variable is the verification interface, the text group builds its own checks from the written criteria through ordinary code execution, while the tool group is handed a callable implementation of those same criteria and reads the structured measurements it returns. The tasks come from a shared-definition SciCode pool, and the cohorts are split so that some tasks are held out and some are development tasks that the agent has seen alternate starting programs for. The headline numbers, and the honest ones, are mixed. On the two task-id cohorts, complete repair is 26 out of 30 with text and 29 out of 30 with the prepared checks. Breaking that down, three task ids favor the tool, one favors text, and eleven tie. On the eight-id held-out cohort it is 13 out of 16 with text versus 15 out of 16 with checks, and the task-cluster bootstrap 95 percent interval for the difference runs from minus 12.5 to 43.75 percentage points, which is wide enough that the difference is not statistically resolved. On the larger shared-definition cohort the two groups tie at 13 out of 24 each. On the five development tasks with alternate starting programs it is 3 out of 10 with text versus 7 out of 10 with checks, the one cohort where the tool group clearly does better. On a matched partial-differential-equation comparison, detailed text scores 23 out of 24 and checks score 24 out of 24, with 31.2 percent lower reported model output for the check group. So the cleanest finding is not that the tool wins on repair, it is that it is a wash on repair overall, with a real advantage on the development cohort, while cutting the agent-side output substantially, and the public CPU use actually rises in both task-id cohorts because the checks themselves have to run. The paper is careful to frame this as measuring task-dependent repair outcomes and agent-side costs, not a claim that executable checks are a universal upgrade.

The task-level breakdown is where the nuance lives, and it is the part a summary that only carries the aggregate numbers misses. The tool group favors tasks 17, 77, and 11, and the initial checks flag task 17 as a violation while reporting no violation for tasks 77 and 11, which is a useful data point, the check is catching a real defect on at least one of the tasks where the tool wins, which suggests the measurement is doing diagnostic work rather than just saving tokens. Task 37 favors text and has no initial reported violation, so on that task the tool gave the agent a clean bill of health and the text agent, doing its own checking, still repaired better, which is the counterexample to the naive story. A fresh source-through-Python arm, where the checks are reconstructed from the source rather than handed over as a ready-made command, also reaches 15 out of 16, matching the dedicated command's aggregate, which is the finding that the benefit is in having the check at all, in some executable form, rather than in any particular delivery mechanism.

The caveats are the story here. The repair gains, where they exist, are small and sit inside a bootstrap interval that includes zero, so the honest read is that the interface change does not reliably make the agent more correct, it makes it cheaper in output tokens on some cohorts. The checks are prepared by someone who knows the requirement, which is a non-trivial assumption, in the wild the requirement is often only as well-specified as the person who wrote the prompt, and building a correct executable check is itself a task the tool group gets for free. And the CPU cost going up is a real tradeoff, you are trading agent output tokens for check-computation cycles, and which side of that trade favors you depends on the task. The fresh source-through-Python arm, where the checks are reconstructed from source rather than handed over, also reaches 15 out of 16, matching the dedicated command, which suggests the benefit is in having the check at all, in either form, rather than in any particular delivery mechanism.

To sum up, this is an interface paper for scientific coding agents, and its contribution is honest to the point of being a caution, turning written requirements into prepared executable checks does not reliably improve repair correctness, the difference is within noise, but it does cut agent-side output meaningfully on some cohorts at the cost of more public CPU. The practical takeaway is that if your scientific agent is burning output tokens re-deriving checks from prose, an executable check is a legitimate token-saver, but do not expect it to make the agent more correct, and weigh the added computation against the token savings for your specific tasks. The deeper point is that the verification interface is a real design variable in agent systems, and this is one of the few matched experiments that isolates it, so the null result is worth as much as a positive one, it tells you that the interface is not a free correctness gain, only a cost one, and that the correctness you actually need to come from the model and the check's diagnostic content, not from the fact that the check is callable.
