Verus-SpecGym: An Agentic Environment for Evaluating Specification
Autoformalization, by Anmol Agarwal, Natalie Neamtu, Pranjal Aggarwal, and a
longer co-author list including Seungone Kim, Jannis Limperg, Cédric Flamant,
Kanna Shimizu, Bryan Parno, and Sean Welleck, from Carnegie Mellon University
and Amazon.

The setting is one that has become central to the question of whether formal
verification can be used in real software engineering rather than in isolated
benchmark exercises. AI coding agents are now writing real software, and the
obvious answer to the question of whether that software is correct is formal
verification: the agent does not just produce code, it produces the code
together with a machine-checked proof that the code satisfies a formal
specification. That framing has a hidden dependency, and the paper identifies
it precisely. The proof is only as strong as the specification it proves
against. If the specification is wrong, too weak, missing an assumption, or
accepts outputs it should reject, then the machine-checked proof certifies
the wrong property, and a verified program that does the wrong thing is worse
than an unverified one in a specific sense, because it comes with a
certificate of correctness that the team will trust. The specification is
where the verification guarantee is won or lost, and the question the paper
asks is whether language models can write faithful specifications, and
specifically whether we can evaluate that ability in a way that is itself
reliable.

The benchmark is the first contribution, Verus-SpecBench, a collection of
five hundred and eighty-one specification-writing tasks. The tasks are derived
from Codeforces problems, which is a deliberate choice, because Codeforces
problems come with adversarial test cases generated by competitors specifically
to break incorrect solutions, and those test cases are exactly the kind of
evidence that distinguishes a faithful specification from an incorrect one.
The choice also means each task has a natural ground-truth notion of correct
behavior, the program must pass the hidden adversarial tests, which gives the
evaluator an objective signal for whether a specification is faithful rather
than relying on a reference specification that might itself be imperfect. The
target is Verus, a verifier for Rust, so the specification language is a
real industrial verifier's specification language, with preconditions,
postconditions, and invariants, rather than a toy logic designed for the
benchmark. The second contribution, Verus-SpecGym, is the agentic
environment in which models interact with Verus, bash, and the filesystem to
develop these specifications, which means the evaluation is not a single-shot
prompt-and-answer but a multi-turn process in which the model writes a
specification, runs the verifier, reads the errors, and iterates, the same
loop that a developer would actually use.

The headline results are the ones a reader should come back to. On
Verus-SpecBench, the strongest frontier model, which the paper names as
Gemini 3.1 Pro, solves seventy-seven point eight percent of the tasks. Other
frontier models solve between fifty-one point one and fifty-seven point eight
percent. And open-source models reach only between twenty-one point five and
twenty-five point five percent. That gap between the frontier and the
open-source tier is the single most important number in the paper, because it
says that specification autoformalization is not a capability that the current
open models have, it is a capability concentrated in the strongest systems,
and the gap is large enough that a team choosing between a frontier model and
an open model for this task is making a difference of more than fifty
percentage points in solved tasks. The gap is not a marginal difference that a better
prompt could close, it is a structural difference in what the two tiers of
models can do with formal specification languages, and the paper's own
framing of the state of the field is that specification autoformalization is
within reach of frontier models but far from solved, and the numbers support
that framing.

The failure-mode analysis is the second important contribution, and it is
where the benchmark earns its place beyond the leaderboard. The paper finds
that model-generated specifications fail in specific ways: they omit
important input assumptions, they accept incorrect outputs that the test
cases expose, and they reject valid outputs that the specification should
allow. Those are three distinct failure classes, and the distinction matters
because each one has a different implication. A missing assumption means the
specification is weaker than it should be, so the proof certifies a weaker
property than the program actually needs. Accepting an incorrect output means
the specification is unsound, which is the most dangerous failure, because the
program can do the wrong thing and still pass verification. Rejecting a valid
output means the specification is too strong, which is a liveness problem,
the program is correct but the specification says it is not. The third
finding is the one that affects how the field evaluates this work in general:
LLM-as-a-judge evaluation misses twenty-six percent of the failures that the
paper's own evaluator catches. That is a direct and consequential result for
the benchmarking practice itself, because it says that if a team uses a
language model to judge whether a specification is correct, they will miss
roughly a quarter of the real failures, and the verifier-based evaluation is
the one that should be used. The evaluator itself is worth describing because
it is the piece that makes the failure classes measurable. Each specification
is checked in four buckets, pre-completeness, pre-soundness, post-completeness,
and post-soundness: pre-completeness confirms that every valid input the tests
know is acceptable is accepted by the pre-specification, pre-soundness confirms
that invalid inputs are rejected, and the two post-buckets do the same for the
output specification, so a specification that is too weak fails a
completeness bucket and one that is too strong fails a soundness bucket, and
the unsound case, accepting an incorrect output, is the one that corresponds
to a proof certifying the wrong property.

Now the skeptical read. The first question is the Codeforces provenance of the
tasks, and I say this as a question about generality rather than a criticism.
Competitive programming problems are real and adversarially tested, which is
the strength, but they are a specific distribution of specification
difficulty, and the question for a team deploying this is whether the
seventy-seven point eight percent transfers to the specifications they would
actually write, which involve state, concurrency, and domain invariants that
competitive programming rarely touches. The second question is the agentic
setting, and the honest version of that question is how much of the
seventy-seven point eight percent comes from the model's ability to write
specifications and how much comes from its ability to iterate against the
verifier, because the SpecGym environment gives the model the verifier's
feedback, and a model that is bad at writing specifications but good at
reading error messages will still do well in the environment, which means the
benchmark is measuring a combination of specification skill and
debugging skill rather than specification skill alone. The third question is
the LLM-as-a-judge result, which is the most methodologically important
number, and the honest version of that question is whether the twenty-six
percent miss rate is uniform across failure classes or concentrated in the
ones the judge is least likely to catch, which would mean the judge is
useful for some failures and unreliable for others, and a team using it as a
triage tool needs to know which. And the scale question is the adoption
question, because five hundred and eighty-one tasks is a solid benchmark but
a single distribution, and the field needs to know whether the frontier
models' seventy-seven point eight percent holds on a second benchmark with a
different specification style before it is safe to treat the capability as
established.

Bottom line: this is a well-constructed and methodologically important
contribution, a real benchmark of specification autoformalization with
adversarially tested tasks, an agentic environment that matches real
developer workflow, and a direct demonstration that LLM-as-a-judge evaluation
is unreliable for this task at the rate that a deployment would care about.
The open question is whether the frontier performance transfers beyond the
competitive-programming distribution, and how much of the agentic gain comes
from specification ability versus iteration against the verifier.
