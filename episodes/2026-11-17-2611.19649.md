Today's paper is LoopFill: Pipelined Multi-Token Speculative Decoding for Looped Transformers, from Siqi Zhu, Suozhi Huang, and Yi Zhao, at the University of Illinois Urbana-Champaign and Princeton University. The subject is a specific and growing architecture class — looped transformers, where the same set of layers is applied repeatedly — and the specific problem that comes with it: decoding is slow, because every token requires T sequential passes through the shared block before it is done. LoopFill is a training-free speculative decoding algorithm for these models, and it beats the strongest prior baseline, LoopAhead, by 40 percent speedup on one test model and 25 percent on the other.

Start with the architecture, because the loop topology is what the method exploits. A looped transformer has three parts: a prelude, a weight-shared block that is applied T times, and a coda. The block is applied T times to refine the hidden state without emitting tokens, which favors the kind of latent reasoning that the looped reasoning models are built for — the paper cites evidence that one looped model improves as its test-time recurrence grows, and that small looped models match larger standard transformers. The price is decoding latency. In a standard transformer, each token is one forward pass. In a looped model, each token is T passes through the shared block, and at small batch sizes those passes are sequential, so the per-token latency scales with T. That is the gap speculative decoding should fill, and prior pipelined self-speculative methods do fill some of it: they use shallow-loop predictions, so a token that is only a few loops in can start being processed while others finish more loops, all in one batch.

The bottleneck LoopFill targets is in that pipelining. In the prior scheme, each token must reach the drafting depth before the next token can enter the pipeline. The pipeline has an admission constraint: a token is admitted once its draft is deep enough to be useful, and while one token is waiting to reach that depth, the pipeline slot sits partly idle. LoopFill's fix is to merge two sources of draft tokens into a single draft tree, so that several future tokens can enter the pipeline together.

The two drafters. First, suffix drafts from two suffix trees — the standard n-gram machinery used in other speculative decoders. The local tree indexes the current request's prompt and everything it has generated so far; the global tree indexes the outputs of completed requests. For a prefix, the system looks up every suffix up to 64 tokens long in both trees. If the phrase would like appeared before followed by to, then to becomes a candidate next token. For each matching suffix, the system builds a small tree from the tokens that followed it, adding the highest-scoring extensions up to a cap, where the score of an extension is the product of the next-token frequencies along its path — so the score of join Lean is the fraction of matches followed by join, times the fraction of those followed by Lean. Across all suffix lengths and both trees, it selects the candidate subtree with the largest sum of node scores and merges it into the draft.

Second, shallow-loop predictions. When a node in the draft tree reaches a designated shallow depth d, which is less than the full T, the model applies the language-model head to its hidden state and proposes its top-k tokens as children of that node. This is the self-speculative part: the model itself is drafting, at a fraction of its full depth.

The unification is the contribution. Both drafters feed one tree, so a suffix lookup can immediately extend a shallow prediction — the model says the next token is probably to, and the suffix tree says that after to the common continuations are a and the, and both sets of candidates compete in the same tree, with each node scored by combining the model probability and the suffix frequency. The top-N candidates are kept, and a shared batched block computes the highest-scoring draft candidates at different loop depths in one forward batch. Full-depth verification then preserves the model's autoregressive output distribution exactly — the verification step is just the model running to its full depth T on the draft tokens in one batched call, and the standard speculative-decoding acceptance rule applies.

Results. Across seven benchmarks, the average speedup over greedy autoregressive decoding is 5.85 times on the Ouro 2.6 billion model and 5.13 times on the Huginn 3.5 billion model. Against LoopAhead, the strongest baseline, the speedups are 40 percent higher on Ouro and 25 percent higher on Huginn. Because the method is training-free and the verification is full-depth, the output distribution is identical to greedy decoding of the same model — the speedup is a strict implementation win, not a quality trade.

The decomposition of the speedup is where the practical value sits, and it is worth spelling out. Speculative decoding speedup is acceptance rate times draft length: if the draft tree proposes four tokens and the verifier accepts three of them, you get three tokens for the cost of one full-depth batched pass plus the draft generation. LoopFill's two drafters push both factors in different directions. The suffix tree produces high-acceptance, short drafts — n-gram continuations are predictable, so they accept well, but they are short. The shallow-loop model drafts are longer and more diverse, because the model's own distribution at partial depth covers continuations the suffix tree has never seen, at the cost of lower per-token acceptance. Merging them into one tree means the verifier sees the union: the high-confidence suffix extensions anchor the early positions of the draft, and the model's deeper proposals fill the later positions where the suffix evidence thins out. That is a reasonable division of labor, and it explains why the method beats both a pure-suffix baseline and a pure-pipelined baseline. The 64-token suffix cap is where the workload sensitivity lives: on code, where the local tree is dense with repeated patterns, the suffix drafter can carry most of the load; on open-ended reasoning text, the global tree is sparse and the shallow-loop drafter does more of the work, which is why the Huginn margin over LoopAhead is the smaller of the two numbers.

Skeptical assessment. First, the scope is narrow by design: this is for looped transformers specifically, which is a small but rising fraction of the reasoning-model landscape, and the method does not generalize to standard transformers, where suffix-tree and EAGLE-style speculation already exist. The question for the field is whether looped models become common enough to matter, and the paper's own citations are the argument that they are on that path. Second, the global suffix tree is a cross-request cache, and it raises the usual questions: what happens with multi-tenant serving, where request A's completion text should not leak into request B's draft tree in a way that changes behavior — the drafts only affect speed, not the output distribution, because verification is exact, but the tree content still touches data isolation in a real deployment, and I would want to see how the authors handle per-tenant partitioning. Third, the 64-token suffix cap and the top-N draft size are hyperparameters with obvious workload sensitivity: on highly repetitive code or templated text, the suffix tree does the heavy lifting and the speedup should be larger; on free-form generation, the shallow-loop drafter carries more weight, and the 25 percent margin over LoopAhead on Huginn is the more conservative number to believe. Fourth, the shared batched block that computes candidates at different loop depths in one batch is the engineering heart of the method, and it is where the actual speedup is won or lost — the paper should be read as an algorithm, but the implementation details of batching heterogeneous-depth candidates are what determine whether the 5.85 times reproduces on your hardware, and I would benchmark the block in isolation before trusting the headline.

Engineering notes if you implement this. Build the global suffix tree as an append-only index over completed requests with a size cap; it is a cache, not a database. Keep the two drafters' scores on a common scale or the merge will favor one drafter silently. The shallow depth d is a per-model knob — too shallow and the model drafts are noise, too deep and you lose the pipelining benefit that is the whole point. And measure accepted-token length per step, not wall-clock speedup alone, because the speedup decomposes into acceptance rate times draft depth, and those move in opposite directions as you tune N.

Bottom line: LoopFill is a clean, training-free, distribution-preserving speedup for the decoding bottleneck of looped transformers, and the unified draft tree is a genuinely simple idea that the prior pipelined schemes were one step away from. I would trust the distribution-exactness by construction and the margin over LoopAhead, and I would verify the sustained throughput on my own hardware with mixed workloads before treating 5.85 times as the number to plan a serving stack around.
