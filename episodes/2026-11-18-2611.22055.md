Today's paper is Weight-Space Programming Doesn't Need Transformers, by Hyunjong Ok and Jaeho Lee at the Pohang University of Science and Technology. The setup is a small one, and the conclusion is a big one. In weight-space programming, a large language model writes the weights of a target model directly, by hand, with no gradient-based training and no data fitting. Transformers won the architecture race because they train well under gradient descent and run fast on GPUs. But in weight-space programming, those are not the selection criteria anymore. So the question is: should you still build a Transformer? The paper's answer, from three frontier models writing weights with minimal guidance, is no. They build tables.

Here is the experimental setup, because it is deliberately minimal. Each frontier LLM gets ten labeled examples, minimal guidance, and an execution sandbox where it can run its own target model and inspect results. The main testbed is the ARC multiple-choice science questions benchmark. Three frontier writers are used: Claude Opus 5.5, GPT-6.1 Sol, and GPT-6 Astra. Two regimes are evaluated. In the first, the LLM must write weights into a fixed, released architecture, and the released architectures include a standard Transformer, a state-space model, and an Elman RNN, all starting from random initialization. In the second, the LLM is free to design the target architecture from scratch.

The headline results. When free to design, all three frontier writers converge on the same structure: they compile the plain-text facts from the task into a sparse table, and query that table with a fixed procedure. The best of these LLM-designed models reaches 54.4 percent test accuracy on ARC. That is higher than the most accurate Transformer that the same LLM wrote in the fixed-architecture regime, while using about 1,800 times fewer parameters. Against the most accurate released architecture the same model wrote, the gap is about 680 times smaller in parameter count. The accuracy numbers sit in the 50 percent range, so none of this is a claim about solving ARC; the claim is about which structure to build when you are writing weights rather than fitting them.

Why a table, from the paper's analysis, is actually a rational choice in this regime, and this is the part worth absorbing. In gradient training, dense weights are fine, because the optimizer figures out where each fact goes. Without gradients, there is no signal telling the writer which weight should hold which fact, and dense weights are hard to write by hand. In a table, one row holds one fact. Every entry has a nameable meaning. Each wrong answer points at one row, so debugging is local: you can find the row and rewrite it. The paper quantifies the locality: removing a single table row changes about one other answer. That property does not exist in a dense Transformer, where one weight participates in many outputs. The writers also get credit for interpretability, in the sense that the LLM can state what each weight means, which is something it cannot do for a trained matrix.

There is a control that matters. If the LLM is forbidden from storing facts as rows, Claude Opus 5.5 does not fall back to a dense network. It builds a memory read by key, using superposed random high-dimensional vectors with more than 100 times more non-zero values than the table. So the table is not the only sparse structure that works, but it is what the models choose, and it is the simplest that works.

Now the efficiency study, which is where the paper earns its title. The LLM-designed table models, as the models write them, are slow on a GPU. A two-layer Transformer processes a batch of 64 questions in a few large matrix operations, roughly one kernel launch per question. The LLM-designed models launch anywhere from 2 to nearly 300 kernels per question. In eager execution, GPU time correlates more closely with kernels per question, correlation 0.95 on a log-log plot, than with the count of non-zero values. Across 46 LLM-designed variants, only one beats a same-sized Transformer at its fastest input mode, and the median is 9.4 times slower. Over generations, the LLM keeps adding scoring steps and rule modules, so the kernel count per question grows from 13 in Claude Opus 5.5's first generation to 118 in its fifth. Many of the designs build or transpose sparse tables inside the forward pass, which prevents capture as a CUDA graph, the optimization that removes kernel launch overhead. The cost grows with the number of facts times the number of scoring passes.

So the authors design their own model, an associative-memory-based design, that keeps the properties that make weights writable without gradients, a row as the unit, a nameable meaning for every entry, sparse keys, and stops scoring every fact for every question. On the GPU, at the model's fastest mode, it is up to 17 times faster than a same-sized Transformer. On quality, at generation 5 it reaches 52.6 percent test accuracy, competitive with the 54.1 percent of the fifth-generation LLM-designed table model.

One table deserves attention because it is a sharp diagnostic. The paper scores each written model against BM25, a plain search over the text the LLM wrote. The written Transformers score below a plain search over their own text: a written two-layer Transformer gets 36.1, versus 44.1 for BM25 over that Transformer's text. The written released architectures get 43.5 versus 46.2. But the LLM-designed table models score above the plain search: 54.1 versus 48.4 at generation 5. So the Transformer weights the LLM wrote are worse than just searching the prose it used to describe them, while the table structure beats the prose. That is a concrete, checkable way of saying the table is doing real work that dense weights are not.

The honest limits, which the paper states. Pretrained LLMs remain more accurate than any of these written models, so nothing here challenges using a frontier model directly. The claim concerns which structure to build when the writing task is the task. The ARC testbed is multiple-choice science questions, a narrow domain. And one alternative reading is left open: the models may choose the table because retrieval is the classic, familiar way to answer questions without training, not because the table is intrinsically best for writing. The data do not separate a structure chosen because it suits writing from one chosen because it is known.

So what would I trust, and what would I re-verify? I would trust the negative result about Transformers in this regime, and specifically the BM25 comparison, because it is a simple, reproducible probe and the mechanism is obvious: dense weights written without gradients are near-uninterpretable and near-undebuggable, so the writer has no way to place facts correctly. I would re-verify three things before generalizing. First, ARC with ten examples is a tiny task; the table works partly because the fact set is small and enumerable. The interesting question is where this breaks as the fact space grows, and the paper's 100-times-more-nonzero-values control hints at where the pressure appears. Second, the 17x speedup is against a same-sized Transformer, and the size matched to a table model is tiny; the comparison that matters for practice is against a small fine-tuned model, which the paper concedes is more accurate. Third, kernel-launch overhead dominates the efficiency story, so the results are a statement about current eager-mode GPU execution, not about what a compiler tuned for sparse table access would deliver.

Bottom line: this is a compact, well-controlled argument that the Transformer's advantages are properties of gradient training, not of the architecture, and that when an LLM writes weights by hand it rationally collapses to a sparse table. The practical takeaway is narrow but real: for weight-space programming, build interpretable, row-local structures, and expect dense weights to be worse than searching the writer's own notes.
