Today's paper is SPILLWAY: Separating Target Admission from Sanitization to Defend Tool-Using Agents against Prompt Injection, from Woosang Lim, Yeseul Chang, and Jaewoo Lee, at SAINT Machines, the Korea Advanced Institute of Science and Technology, and Chung-Ang University. The one-line pitch: the decision of whether an agent's outgoing action gets to proceed should not be made by a language model reading attacker-controllable text, because it can be made by looking at the types of the values involved.

Here is the threat model, stated plainly. A tool-using agent reads email, files, web pages, and documents, and it acts: it sends emails, makes payments, writes files. An attacker who cannot reach the user directly can reach the agent — hide an instruction in a web page the agent fetches or a shared document it opens, and the agent, trusting its context, may exfiltrate data or move money. The standard runtime defenses put a language model on the admission decision: a classifier or a judge reads the proposed action, decides whether it looks malicious, and lets it through or blocks it. The paper's objection is structural. That judge model is reading the very text the attacker wrote, and it adds model calls to every step of the agent. Provenance-based defenses get the model off the final check, but they need a model to plan or route each task first.

The observation SPILLWAY is built on is this: where an action goes is usually visible in typed data, not free text. An email's sender arrives in a typed field — an address, a URI, a UUID, a hostname, an IP. A payment's account is a typed field. The injected instruction arrives as free text in a body or a description. So the identity targets of a call — the recipient, the account, the URL — can be checked against a deterministic index without a model ever reading the attacker's payload.

The mechanism has three parts. First, a typed identity index. The executor captures the return of every read-only tool before it is serialized into text for the model, and it indexes a value only when the tool's declared field type is an identity format or the field has a routing role — recipient, sender, participant, channel. Bodies, subjects, and descriptions never enter the index. Two rules keep the attacker from polluting it: only read-only returns are indexed, so an allowed write cannot add a value, and a read whose own arguments are tainted adds nothing. A value is "taint-novel" if it appears in tool output but not in the user's original task. The floor admits a call when every taint-novel identity target is in the typed index and does not also occur in untrusted free text. It is a set lookup. The paper's phrase is that its refusals are the same under every backbone, and that is the whole point: the safety decision is deterministic.

Second, the grant and destruction gates. A grantee — the recipient of a permission or a transfer — must be named in the user's task; values the user named are never taint-novel, so replying to the sender of an email the task mentioned works even though the address is new to the conversation. Destructive calls that the task did not authorize are blocked before any recovery logic runs.

Third, the fallback judge, which is where a model finally appears — and only for the cases the deterministic floor refused and that a fixed delegation rule does not cover. The sanitizer removes instruction-like spans from untrusted content at ingress, and the judge is reached with those spans removed, in two views that each fail closed. So the model sees the attacker's text only in the narrow residue that the deterministic layer could not decide, and even then with the most dangerous parts already stripped.

The results are on AgentDojo and its harder successors, which is the standard benchmark suite for this problem: suites of banking, Slack, travel, and workspace tasks with injected attacks. The paper reports in-scope utility under attack alongside attack success rate, because a defense that blocks everything scores perfectly on safety and uselessly on utility. Against undefended baselines, SPILLWAY holds attack success at zero or near zero across the four attack regimes — the standard AgentDojo attack, ChatInject, AutoDojo, and PISmith — while keeping the highest in-scope utility of any defense in each shaded corner of the safety-utility plot. On the stress tests with a small local model, the ChatInject panel shows utility under attack jumping from 0.052 undefended to 0.396 with SPILLWAY on the workspace suite, with attack success at zero; on AutoDojo, written against the Progent defense, the composite utility is 0.625 against 0.342 undefended. The component ablation on the 8 billion parameter local model shows the floor alone already gets attack success to zero on most suites but costs utility — the floor on its own scores 0.333 utility on banking, and the full system recovers that to 0.438 by letting the judge and sanitizer handle the over-refused cases. Removing only the span veto barely moves the numbers, which suggests the typed floor is carrying most of the weight.

Now the skeptical assessment. First, the determinism depends on the tools' declared types, and the paper is explicit that tool and argument roles come from one fixed lexicon per benchmark: verb prefixes mark read-only, writing, destructive, and granting tools, and argument names mark targets and principals. That is a strong assumption. In a real deployment, tool schemas are heterogeneous, some values arrive in JSON blobs that are effectively free text, and an attacker who can influence how a tool's return is typed has found the seam. The defense is only as good as the type discipline of the tool layer, and that discipline is not a given in most agent frameworks. I would want to see this run on a tool suite whose schemas were designed for expressiveness rather than for this defense.

Second, the benchmark scores are suite means, and AutoDojo is optimized against a specific prior defense; the paper notes its AutoDojo row uses rules written on four failing pairs with held-out sets in the appendix. That is honest, but it also means the delegation rules are being tuned per regime. The question that matters for adoption is how much of the zero-attack-success result comes from the typed floor and how much from the hand-written delegation rules, and the ablation only partially answers it: the floor alone gets most of the way, but the rule layer is what closes the residual.

Third, the utility numbers are relative. A 0.438 in-scope utility under attack on banking means the agent still completes only about a third of what it would without an attacker. The paper frames holding "each ideal corner" of the plot, which is fair, but a defense that triples safety at a two-thirds utility tax is a trade-off your application has to accept, not a free lunch. And the judge fallback, while fail-closed, means a frontier or local model is still in the loop for the hard residue; a sufficiently good judge attack is out of scope here but not out of the world.

One more structural point worth weighing. The paper positions itself against two families of prior defense — the model-judge defenses and the provenance defenses — and the typed floor is a third family: it reads the executor's own bookkeeping rather than the model's context. That has a practical consequence the paper does not overstate but should. The defense inherits the executor's trust boundary. If the tool layer is compromised — a malicious dependency that reports a typed return it did not actually produce, or a serialization bug that promotes a free-text value into a typed field — the floor admits what the tool layer tells it is typed. In other words, SPILLWAY converts an inference-time problem into a systems problem, and systems problems have a much smaller blast radius to audit: you inspect a type schema and a set-lookup, not a model's judgment on arbitrary text. That is a real architectural improvement, and it is also why the fixed per-benchmark lexicon is the load-bearing wall.

Bottom line: SPILLWAY is the clearest articulation yet of a principle that should be obvious — the admission decision for an agent's outgoing actions is mostly a type-checking problem, and the language model should be demoted from gatekeeper to fallback judge. I would trust the architecture and the ablations, and I would re-verify the whole thing on a tool suite with real-world schema sloppiness before betting production traffic on it.
