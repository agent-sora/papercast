The paper is HexaShell, from Hongcheng Gao, Alex Zhou, and Jay Zhu, from the Hexa Future AI team. It asks a sharp question: agents built on vision-language models now compete with learned policies on robot manipulation leaderboards, so how far can a coding agent go when it controls a robot instead of a computer, and where exactly does it stop? The system keeps the harness deliberately thin. It only turns the agent's commands into robot motion. The agent drives a two-armed robot through a single command line, sees three RGB cameras and knows their calibration, and after each failed attempt it reads the log, finds the cause, and writes or fixes small programs it calls tools. It keeps what it learns as code, the same way a coding agent keeps a fix to a failing test. The headline is a new state of the art on the RoboDojo benchmark, and the headline limitation is that the wall is contact, not reasoning.

The acting agent is an unmodified coding agent, Codex running GPT-6-Astra at medium reasoning effort, which is an important detail. The system does not fine-tune the model on manipulation, and it does not add a learned low-level policy. The only learned artifact is the collection of tools the coding agent itself writes, which are plain programs that run in the shell and call the perception and motion functions. That means the entire adaptation to the physical task is expressed as code that a human could read and audit, which is a strong property for a system that is meant to explore the limits of a general agent.

The design has a few properties worth stating precisely. The tools may only use what the robot observes. They find object positions with triangulation, which is a specific geometric argument: if two cameras see the same point, the point lies where the two camera rays meet, and if a point lies on a known plane, like the table or the top of a block, it lies where its ray meets that plane. When the head camera is not enough, the robot moves a wrist camera to get a second view. The tools are built on ten layouts of one seed per task, then frozen, and tested on ten new layouts of the same seed, which is a genuine generalization test rather than a fit to the training layouts. On all forty-two RoboDojo tasks, HexaShell reaches a success rate of about forty percent and a progress score of about forty-eight, averaged the way the leaderboard does, which the authors report as a new state of the art.

The decomposition of where it succeeds and fails is the most useful part of the paper. The limit is contact, not reasoning. Pushing tasks reach about ninety-three percent and memory tasks about sixty-five percent, but tight insertion only about eight percent. When the agent fails, it usually sees the failure but cannot make the motion work. The failure analysis backs this up with a clean diagnostic split. Of the retest episodes on the development layouts that failed, the large majority exhausted the budget, meaning the agent knew the result was wrong and kept retrying until the steps ran out, a gap in execution. A significant share ended with the agent declaring success while the checker disagreed, a gap in perception or in reading the task specification. On deformable, articulated, and rigid tasks the budget-exhausted failures dominate, while on memory tasks half the failures are declared successes. The authors state the diagnostic plainly: a declared failure points to a gap in perception or task specification, and an exhausted one points to a gap in execution.

The case-study section on how the tools got there is concrete and, to me, the most instructive. The RGB runs took about seven hundred and seventy optimizer rounds, most of them after a failure. A round after a failure took a median of a little over six minutes, and in that time the optimizer ran a median of about sixteen shell commands, read the failure table and the command log and the acting agent's transcript, edited a tool, wrote or updated unit tests, and ran them, with over ninety percent of rounds running the task's tests. The median edit added about a hundred and twenty lines. Across the whole run the optimizer read on the order of half a billion input tokens, most cached, and wrote a few million. In twenty-seven tasks a layout failed and then passed on the next attempt after an edit, and the authors carefully verify in the logs that the edited code actually ran and addressed what had failed. In five of seven kept cases the optimizer never looked at an image; the command log, the tool's feedback, and the code were enough.

There is a methodological point in that section that I want to flag, because it is what separates this from a purely empirical leaderboard result. The authors do not just report that success went up after an edit; they go back through the stored logs of the successful attempts and confirm that the edited tool actually executed and that the edit addressed the specific failure, and for two of the cases they re-ran the old and the new code on the stored images to show the difference. That level of causal checking on which edits actually caused the passes is more careful than is usual in agent papers, and it is why I would trust the claim that the coding loop is doing real work rather than just benefiting from a different turn of the scene.

What I would trust is the failure taxonomy and the honest characterization of the contact wall. The declared-failure versus exhausted-failure split is a genuinely useful diagnostic for anyone running vision-language agents on manipulation, and the decision to freeze tools and test on unseen layouts of the same seed is the right generalization protocol. What I would be cautious about is the state-of-the-art claim in isolation. A success rate around forty percent with an eight-percent insertion floor is a strong result, but it is a result on a specific benchmark with a specific agent and a specific thin harness, and the large dependence on depth for the hard contact tasks means the approach does not yet transfer to the setting where most real manipulation happens, which is without a depth sensor. There is one comparison I would highlight because it is honest about the method's boundary. The paper includes a variant that gives the tools access to rendered depth in addition to RGB, and that variant jumps to thirty point one percent on the insertion tasks, led by two specific tasks where depth is decisive, while the RGB-only tools sit at eight point three percent on the same tasks. The gap between those two numbers is the clearest statement of where the method currently fails, and it is a perception limitation, not a reasoning limitation, because the agent in the RGB setting can see that it is failing, it just cannot measure the geometry well enough to fix it. The paper also notes that on deformable material tasks, like folding clothes, the tools are still worse than the step-by-step agent without tools, reaching fifty percent against seventy-two percent, which is a useful reminder that a thin harness of computed tools is not a universal upgrade, and that the step-by-step policy still wins where the geometry is too soft to measure cleanly.

Two-sentence verdict: HexaShell is a clean, well-instrumented study of how far a coding agent can drive a robot, and its most valuable output is the perception-versus-execution failure diagnosis rather than the leaderboard number. The contact wall is real and depth-dependent, which bounds how far this thin-harness recipe reaches, and the open-sourced tool collection is a useful starting point for anyone who wants to reproduce the loop on their own embodiment.
