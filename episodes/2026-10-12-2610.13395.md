ProgramGym: Scaling Training Environments for Long-Horizon Program Reproduction Agents, from Chengyi Yang, Renxu Bao, and Jue Hou at Xiamen University, Washington University in St. Louis, the Institute of Automation at the Chinese Academy of Sciences, and Unisound. The paper tackles a specific gap in coding-agent training. Today's dominant agent tasks come in two flavors. Issue resolution, like SWE-bench, hands the agent an existing repository plus a bug to patch. Repository generation, like NL2Repo-Bench, hands it a requirements document to implement. In both cases the agent starts from a given codebase or a specified feature. A human engineer building a program from scratch does neither of those. They keep asking what is actually required and how the system should be designed, discovering behavior by exploration. Program reproduction benchmarks, such as ProgramBench, capture that setting: the agent rebuilds a program's observable behavior from its usage documentation and a reference program, with no access to the source code or the network. The authors note that in the original ProgramBench evaluation, none of the tested models fully solved a single task. Training on that kind of long-horizon, from-scratch work therefore needs interactive environments with reliable behavioral supervision, and those environments are scarce. That is the problem the paper sets out to solve.
The system has two halves. Program-Env is a feedback-driven pipeline that turns public repositories into verifiable training environments. It builds the reference executable, sets up a runtime sandbox, and constructs black-box tests, then iterates on both: when a sandbox build fails or a generated test is flaky or wrong, the pipeline repairs it and retries, closing the loop until the environment is reliable enough to supervise an agent. The output is one thousand six hundred forty-eight training environments across four languages, with Go the largest share at eight hundred eighteen, roughly half the pool, followed by three hundred seventy-eight C++ environments, three hundred three Rust, and one hundred forty-nine in C. Program-Agent is the agent side. It runs a role-isolated workflow in which separate passes handle analysis, implementation, and review, rather than one monolithic agent doing everything, and it adds revision management for compilation checks and failure recovery, so when a build fails the agent can diagnose and retry within the same episode rather than collapsing the trajectory. For training data they collect trajectories by rejection sampling, generating candidate solutions with DeepSeek-V4-Flash-0731 inside Claude Code and keeping only trajectories that pass the environment's test cases, so the fine-tuning set is grounded in verified behavior rather than raw rollouts.
The construction of those environments is the real engineering work, and it is where most of the value sits. Program-Env does not just wrap an existing test suite; it builds a closed loop that repairs the training environment itself. For each candidate repository it first attempts to build the reference program inside a runtime sandbox and, when the build fails, iteratively patches the build configuration until it compiles. It then generates and quality-checks black-box test cases, filtering out tests that are flaky, trivially pass, or overfit to the reference implementation, so that the environment actually discriminates between a correct reproduction and a plausible-but-wrong one. This is the hard part of scaling program-reproduction training: the bottleneck is not model capacity, it is the cost of producing a large pool of environments whose success criteria are reliable. The pool lands at 1,648 environments, skewed toward Go at 49 percent, with C++ at 23 percent, Rust at 18 percent, and C at 9 percent, a language mix that tracks where real, buildable, testable open-source code lives. The trajectories are collected with a strong teacher, a rejection-sampled run of a frontier model inside a Claude Code harness, keeping only the rollouts whose test pass rate clears a threshold, so the SFT data is dense with successful long-horizon reproductions rather than noise.
Evaluation is on ProgramBench, scored by a tests-passed metric that macro-averages per-task test pass rates. The headline numbers are a clear progression. The base Qwen3.8-27B model scores thirty four point eight seven percent on ProgramBench. Fine-tuning on trajectories collected in the Program-Env environments raises that to forty two point eight four percent, a gain of about eight points from the environment and data alone, with no change to the agent workflow. Adding Program-Agent on top of the base model lifts it to fifty five point seven one percent, and on the fine-tuned model to fifty six point two five percent. Both of those clear Gemini 3.6 Flash at fifty seven point six eight, and sit above Kimi K2.7 Code at fifty three point six. For context, the frontier systems the paper includes as reference points are higher still: Claude Opus 4.8 at seventy point nine percent, GPT-5.6 Sol at sixty nine point nine, GLM-5.2 at sixty four point six, and Gemini 3.7 Flash at sixty one point two. So the claim being made is not that this matches the frontier, but that a twenty seven billion open model, trained in these synthesized environments with this workflow, reaches a level that was recently occupied only by much larger flagship models. The paper says it will release the environments and the full ProgramGym stack, which is the part worth watching for anyone who wants to reproduce this, because the recipe is a training-data pipeline plus an agent harness, not a new architecture. A detail from the results is worth keeping. The training environments and the evaluation benchmark are deliberately kept separate: ProgramGym is a training environment built from public repositories, while ProgramBench is the held-out evaluation, so the gain on the twenty-seven-billion base model is not the model memorizing its own training distribution. The larger relative jumps on the smaller models are the more useful number for a team without a frontier base to start from, because they show the environment transfers to the models that would otherwise spend the most wall-clock time reproducing a codebase. And the fact that the program-agent configurations, which use the environments for agentic rather than imitation training, sit at fifty five point seven one and fifty six point two five, above the direct fine-tuning numbers, is the signal that the environments work as a substrate for agentic training, not just as supervised data. For a team that does not have a frontier base model to start from, the more useful number is the one on the smaller open models, because those are the models that would otherwise spend the most wall-clock time trying to reproduce a codebase, and the same Program-Env data moves them the most in relative terms, which is the argument that the capability is coming from the environment-and-data recipe rather than from a specific large backbone.
The skeptical read has a few parts. First, the entire quality of the fine-tuning set is bounded by the rejection-sampling teacher, DeepSeek-V4-Flash inside Claude Code. If that teacher cannot solve a class of programs, the SFT data simply does not contain correct examples of it, and the student inherits the teacher's blind spots under a better-looking pipeline. Second, the environment pool is built from public repositories and the test suites are machine-generated and machine-repaired, so the behavioral supervision is only as faithful as the generated tests, and a test that passes is evidence the implementation matches the tests, not that it matches the original program's intent. Third, ProgramBench is a single benchmark from the from-scratch reproduction family, so the generalization claim to open-ended software engineering remains untested here, and the gap to Opus 4.8 is still fifteen points. Bottom line: ProgramGym is a solid, reproducible contribution on the environment side, and the evidence that verified-environment fine-tuning plus a role-isolated harness closes most of the gap between a small open model and the flagship agents on program reproduction is the real result. I would want the released environments and the test-quality audit before trusting the numbers beyond ProgramBench, and I would verify how often the machine-repaired tests changed the reference behavior.
