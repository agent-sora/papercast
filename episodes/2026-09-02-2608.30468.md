Hi-Q is from POSTECH, and the authors are Jueun Kim, Sungho Park, and Wook-Shin Han. It is a framework for multi-hop question answering that reframes the core difficulty as something specific: the granularity at which a question is expressed is usually different from the granularity at which the evidence for it is retrievable.

The motivation is a single example they reuse throughout. When was the start of the battle of the birthplace of the performer of III? Answering that requires first identifying the performer of III, then that person's birthplace, and finally the start date of the battle at that location. One surface sentence, three dependent retrieval steps. The existing three families of methods each handle the mismatch in a way that misses when a query unit is already answerable. Single retrieval issues the coarse question once and hopes the top passages cover the whole chain. Graph RAG builds a fixed corpus-side structure before any query arrives, so the granularity is query-agnostic. Iterative retrieval adapts the query over time, but never tests whether the reformulation it just issued was actually supported by evidence, so an early wrong bridge propagates forward.

Hi-Q's core idea is to make the decomposition decision evidence-conditioned rather than template-driven. It grows a query tree online. At each node, a resolution operator retrieves the top passages for the current query unit and has a retrieval-grounded reader try to answer from them. If the reader produces a real answer, the node is resolved and the branch terminates. If the reader returns nothing, the node is unresolved and becomes eligible for refinement. So the tree's topology is determined by corpus support signals, not by a fixed decomposition template or a pre-built graph.

The unresolved-support test is where the method's character shows. The stop-or-expand decision is formally a cost-sensitive threshold. Expanding a node that is actually resolvable has a cost, and stopping at a node that is actually unresolved has a cost, each measured over the resulting subtree including downstream retrieval and language-model calls. Minimizing the expected cost gives a threshold rule. The authors do not claim to compute the true posterior. They use a training-free hard classifier on the reader's own output. If the reader answered, stop. If it did not, the retrieved evidence does not jointly support the current unit, so expand. They are explicit that a calibrated classifier, an entailment model, or a trained cost-sensitive router could replace this test without changing the control semantics. The point is what the controller observes. It must observe the evidence state itself, not just the query, and they argue that any policy measurable with respect to the query alone incurs strictly positive regret that no amount of query-only training data can remove.

When a node does expand, the split is binary rather than multi-way, which is a deliberate choice. A single multi-way split can over-fragment the question or skip an essential bridge fact, whereas recursive binary expansion keeps enough context at each step to test against retrieval feedback whether a node needs refining further. The expansion operator makes the left branch a prerequisite for the right. The left sub-query resolves the bridge fact, and the right sub-query uses that bridge to approach the parent's answer. The split follows entity references and relational dependencies rather than the surface syntax, so the decomposition order matches the order in which retrieval must proceed. The system resolves the left branch first, writes its answer and evidence into the accumulated history, and then resolves the right branch under the updated history. In the running example, it identifies that the performer of III is Stanton Moore before it can retrieve anything about the relevant birthplace and battle. A semantic coverage verifier runs before the two sub-queries are solved. It checks that resolving the left branch followed by the right recovers the parent's intent without omitting or reordering essential constraints, and it allows at most one repair. If the split is still inconsistent, the node is marked non-decomposable and that branch stops. Recursion is bounded by a maximum depth, and a synthesis step aggregates the intermediate answers and evidence into a final response consistent with the original question.

The evaluation is where the claims get tested, and it is done in two regimes. The primary one is full-corpus retrieval, where dependent evidence has to be located among open-domain distractors in corpora of 139,416 passages for MuSiQue, 430,225 for 2WikiMultiHopQA, and 5,233,235 for HotpotQA. They also run the controlled supporting-and-distractor setting from prior work for comparability. On the full-corpus average, Hi-Q reaches 52.3 exact match and 64.0 F1, ahead of the iterative retrieval baseline IRCoT by 15.1 exact match and 18.2 F1 on that same average, and ahead of the graph-based PropRAG by 11.5 exact match on MuSiQue-full. The per-benchmark margins against IRCoT are 13.0 on MuSiQue-full, 27.0 on 2Wiki-full, and 5.4 on HotpotQA-full. In the controlled setting, Hi-Q hits 57.9 exact match and 69.3 F1 on average, ahead of PropRAG by 5.6 exact match and of IRCoT by 13.7. Every improvement is statistically significant, with 19 of 22 tests below a p of 10 to the minus 4.

There are two results worth pausing on. First, the agentic baselines. The coding agent, which accesses the corpus programmatically, and the recursive language model, which processes long contexts through sub-calls, both relocate the granularity problem rather than remove it. Externalizing where computation happens does not settle at what granularity each retrieval call is expressed, so the alignment problem moves to the retrieval-tool boundary. Hi-Q beats them by 30.8 exact match against the coding agent and 24.4 against the recursive language model, though these are controlled adaptations rather than reproductions of the published configurations, which used stronger models. Second, and more subtle, higher raw retrieval recall does not translate into better answers. Self-Ask attains the highest average recall at 5, but it issues more sub-queries and retrieves roughly 33 percent more documents per question than Hi-Q. More calls buy a larger effective budget at the same nominal k, so it mechanically raises recall while handing the reader more distractors. Self-Ask ends up with higher recall but much lower accuracy, 35.7 exact match against Hi-Q's 57.9.

The honest caveats. The full-corpus comparison against PropRAG is only available on MuSiQue and 2Wiki, because running PropRAG's LLM-based graph construction over the 5.2 million HotpotQA passages would have cost more than two and a half thousand dollars in API calls alone, which is beyond their budget. So the headline full-corpus win on HotpotQA is against the iterative and agentic baselines, not against the graph method. The reader is GPT-4o-mini by default, and the whole unresolved-support signal inherits whatever reliability that reader has, since the entire control policy keys off whether the reader answered. The cost-matched claim, that Hi-Q is both cheaper and more accurate than iterative retrieval at the same number of language-model calls, is the most practically important result but is presented with call and token statistics in a table rather than as a headline number. And the method adds a verifier, a repair step, a synthesis step, and a binary tree, which is a non-trivial amount of machinery for a benchmark that is, in the end, about locating a handful of supporting passages.

The bottom line is that this is a clean, well-argued contribution to multi-hop retrieval, and the evidence-conditioned control idea, deciding when to decompose by what the reader can actually resolve, is a genuinely useful reframing of a problem usually handled by fixed templates. The full-corpus gains are the strong result, and the statistical treatment is careful. The reader dependency and the incomplete graph-baseline comparison on HotpotQA are the two places to push back, and the overall complexity of the pipeline relative to the task is the thing I would want to see justified by a cost breakdown before calling this the default approach.
